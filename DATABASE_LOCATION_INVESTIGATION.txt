3. WRITABLE TEST ANALYSIS
================================================================================

Location: ElectronDatabaseManager.cjs:498-507

EXACT CODE:
  testFolderWritable(folderPath) {
    try {
      const testFile = path.join(folderPath, `.test_${Date.now()}`);
      fs.writeFileSync(testFile, 'test');
      fs.unlinkSync(testFile);
      return true;
    } catch {
      return false;
    }
  }

HOW IT WORKS:
  1. Constructs a temp filename: ".test_1712345678"
  2. Writes "test" to it using fs.writeFileSync
  3. Deletes it with fs.unlinkSync
  4. If BOTH succeed, returns true (writable)
  5. If EITHER throws (EPERM, EACCES), catches and returns false

WHY IT FAILS ON INSTALLATION DIRECTORY:
  The Electron app process runs with standard user privileges (no admin).
  Writing to "C:\Program Files\My POS\data\" with fs.writeFileSync throws
  an EACCES or EPERM error because Windows blocks writes to Program Files
  for non-elevated processes.

  Even though the installer ran icacls on the data folder, the test fails.
  This means icacls either:
    - Did not execute at all
    - Executed but failed
    - Executed and succeeded but Windows still blocks the write

UAC Virtualization NOTE:
  Windows has "UAC Virtualization" that silently redirects writes from
  non-elevated processes to %LOCALAPPDATA%\VirtualStore. However, this
  is only enabled for legacy 32-bit apps WITHOUT a manifest. Electron
  apps DO have an embedded manifest (from electron-builder), which
  disables UAC Virtualization. Therefore the write attempt gets a REAL
  ACCESS_DENIED and throws, causing the test to return false.

4. NSIS INSTALLER ANALYSIS
================================================================================

Location: pos-template\nsis-installer.nsh (all 70 lines)

EXACT icacls COMMAND (line 29):
  nsExec::Exec '"$SYSDIR\icacls.exe" "$INSTDIR\data" /grant:r "BUILTIN\Users:(OI)(CI)F" /T'
  Pop $0

WHAT THIS SHOULD DO:
  Run as admin (installer is elevated), grant BUILTIN\Users Full Control
  on $INSTDIR\data with inheritance (OI=Object Inherit, CI=Container Inherit).
  Exit code 0 = success.

POTENTIAL FAILURE REASONS:

  A. nsExec PLUGIN NOT AVAILABLE
     nsExec is a standard NSIS plugin, but the version of NSIS bundled with
     electron-builder may not include it. If the plugin DLL is missing,
     the line is silently ignored, Pop $0 returns garbage (not 0), and
     all three icacls attempts are skipped.

  B. nsExec::Exec DOES NOT WAIT PROPERLY
     Some NSIS documentation suggests nsExec::Exec returns immediately
     without waiting for the child process. If the installer continues
     before icacls finishes, Pop $0 may get the wrong value or the
     permissions may not be fully applied when the installer exits.

  C. icacls SYNTAX ISSUE WITH NSIS STRING PARSING
     The outer '...' in NSIS is the string delimiter. The actual command
     becomes:
       "C:\Windows\System32\icacls.exe" "C:\Program Files\My POS\data"
            /grant:r "BUILTIN\Users:(OI)(CI)F" /T
     If $INSTDIR contains special characters (parentheses, &, etc.),
     the quoting might fail.

  D. icacls /grant:r DOES NOT DISABLE INHERITANCE
     /grant:r replaces the specific user's permissions but does NOT
     disable inheritance from the parent. If Program Files has an
     inheritable "deny write" ACE (which it does NOT by default,
     but administrators could have added), the inherited deny would
     still block writes.

  E. WINDOWS DEFENDER / ANTIVIRUS
     Some antivirus software hooks file operations and may block
     icacls from completing, causing a non-zero exit code.

  F. INSTALLER BITNESS / WOW64 REDIRECTION
     The 32-bit installer on 64-bit Windows gets its System32 folder
     redirected to SysWOW64 by default. $SYSDIR in NSIS specifically
     addresses this by pointing to the native System32. However, if
     $SYSDIR is empty or points to a non-existent folder, icacls
     won't be found.

EXIT CODE CHECK (lines 30-34):
  Pop $0         ; Get exit code from nsExec
  ${If} $0 == 0
    DetailPrint "✅ Granted BUILTIN\\Users full access"
    Goto done_permissions
  ${EndIf}

  The check looks correct. If exit code is 0, it jumps to done_permissions.
  If not, it falls through to the next strategy.

THREE FALLBACK ATTEMPTS:
  Attempt 1: BUILTIN\Users with /grant:r
  Attempt 2: Everyone with /grant:r
  Attempt 3: Users (without BUILTIN\) with /grant (append)

  If ALL THREE fail, the installer prints a warning but continues.
  The data folder exists but has only inherited Program Files permissions.

5. INSTALLATION FOLDER PERMISSION ANALYSIS
================================================================================

WHAT SHOULD HAPPEN:
  After successful icacls execution, "C:\Program Files\My POS\data" should have:
    - BUILTIN\Users: Full Control (explicit)
    - Plus inherited permissions from parent (BUILTIN\Users: RX)

WHAT ACTUALLY HAPPENS (hypothesis):
  The data folder has ONLY inherited permissions from Program Files:
    - CREATOR OWNER: Full Control (inherited)
    - SYSTEM: Full Control (inherited)
    - Administrators: Full Control (inherited)
    - Users: Read & Execute (inherited)
  No explicit Full Control for Users.

  Therefore, the non-admin Electron process gets:
    - Read & Execute from inherited permissions
    - No Write permission
    - testFolderWritable() throws EACCES
    - AppData fallback is triggered

WHY STANDARD USERS CANNOT WRITE TO PROGRAM FILES:
  By default, Program Files is a protected system directory. Windows enforces
  this even for subdirectories unless explicit write permissions are granted.
  This is a key Windows security feature. The only way around it is:
    1. Explicit Full Control ACE on the specific subfolder
    2. Running the process as admin
    3. UAC Virtualization (disabled for Electron apps)

8. ROOT CAUSE — DEFINITIVE
================================================================================

ROOT CAUSE: The NSIS installer's icacls command does not successfully apply
write permissions to the data folder, despite the folder being created.

EVIDENCE:
  - The data folder EXISTS at C:\Program Files\My POS\data\ (installer created it)
  - A non-admin user CANNOT create a text file in this folder
  - testFolderWritable() throws EACCES and returns false
  - getDataFolderPath() therefore falls back to AppData
  - All 3 icacls attempts in nsis-installer.nsh fail (exit code ≠ 0), as
    evidenced by the fact that permissions are NOT applied after installation

MOST LIKELY REASON:
  The nsExec::Exec plugin in electron-builder's bundled NSIS silently fails
  to execute icacls.exe, or executes it but the exit code is captured
  incorrectly. The three fallback strategies all fail. The installer
  finishes with "All icacls attempts failed" (line 57) — a message the
  user never sees because the installer Details view auto-closes.

SECONDARY CONTRIBUTING FACTOR:
  The app code at getDataFolderPath() line 516-578 does NOT attempt any
  runtime permission fixing. It was intentionally simplified to rely solely
  on the NSIS installer. When the installer fails to set permissions, the
  app has no fallback mechanism to fix them at runtime — it just gives up
  and goes to AppData.

WHAT IS NOT THE ROOT CAUSE:
  ❌ Not the installation path detection — getAppInstallationRoot() correctly
     returns "C:\Program Files\My POS" via app.getPath('exe')
  ❌ Not the app code logic — testFolderWritable() correctly detects
     that the folder is not writable
  ❌ Not the SQLite initialization — it correctly uses whatever path
     getDataFolderPath() returns
  ❌ Not the ipc-auth-handlers.cjs dual DB connection — the shared
     databaseManager from electron-modular.cjs is passed correctly
  ❌ Not Windows UAC Virtualization — Electron has a manifest that
     disables it; the write attempt gets a real ACCESS_DENIED

10. RECOMMENDED FIX (NOT IMPLEMENTED)
================================================================================

The fix must ensure the data folder is writable WITHOUT requiring the user
to accept a runtime UAC prompt. Options:

  OPTION A: Fix the NSIS installer's icacls execution.
            Replace nsExec::Exec with ExecWait, which is a built-in NSIS
            command that does not require a plugin. Or use the standard
            nsExec plugin WITHOUT the outer single quotes, which may
            interfere with parameter parsing:
              nsExec::Exec '"$SYSDIR\icacls.exe" "$INSTDIR\data" /grant:r "BUILTIN\Users:(OI)(CI)F" /T'

  OPTION B: Use the icacls command directly in the installer with a .bat
            file workaround. Write a temporary batch file and run it
            with ExecWait instead of nsExec::Exec.

  OPTION C: Add a single silent runtime attempt (no UAC) that runs icacls
            WITHOUT elevation from the main process. This won't work for
            standard users (no admin rights), but will work for users who
            voluntarily run the app as administrator the first time.

  OPTION D: Move the data folder OUTSIDE Program Files entirely, while
            keeping it in a predictable location relative to the install
            dir. For example, use the install dir's parent or a well-known
            location like %PROGRAMDATA%\My POS\data\.
            Problem: This defeats the "in installation folder" requirement.

  OPTION E: Make the installer create the folder with a batch file that
            is guaranteed to work:
              ExecWait '"$SYSDIR\cmd.exe" /c "icacls \"$INSTDIR\data\" /grant:r \"BUILTIN\Users:(OI)(CI)F\" /T"'
            This avoids the nsExec plugin entirely and uses CMD as the
            execution host, which is always available.

  The most reliable approach: ExecWait with cmd.exe + icacls, eliminating
  reliance on the nsExec plugin which may not be available in the version
  of NSIS bundled with the current electron-builder.
