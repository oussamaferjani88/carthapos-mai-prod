FIX 1 DETAILED FINDINGS: Backfill shift_id for Legacy Sales
========================================================================

1A. MIGRATION SAFETY ──────────────────────────────────────────────────

File: src/electron/ElectronDatabaseManager.cjs (lines 1901-1924)

  UPDATE sales SET shift_id = (
    SELECT id FROM shifts
    WHERE shifts.user_id = sales.user_id
      AND shifts.opened_at <= sales.created_at
      AND (shifts.closed_at IS NULL OR shifts.closed_at >= sales.created_at)
    ORDER BY shifts.opened_at DESC
    LIMIT 1
  ) WHERE shift_id IS NULL
    AND EXISTS (...same subquery...)

Safety guarantees (all TRUE):
  ✓ WHERE shift_id IS NULL — never overwrites an existing shift_id
  ✓ Matches by user_id — sale by user A never links to user B's shift
  ✓ opened_at <= created_at — shift existed before the sale
  ✓ closed_at >= created_at — shift still active when sale was made
  ✓ ORDER BY opened_at DESC / LIMIT 1 — picks the correct (most recent)
    shift if multiple match (e.g., one shift per day)
  ✓ EXISTS guard — prevents running subquery when no match possible
  ✓ Idempotent — running twice is a no-op (shift_id already set)

1B. EDGE CASE ANALYSIS ────────────────────────────────────────────────

Edge case: Multiple shifts for the same user
─────────────────────────────────────────────
  Scenario: User opens shift on Monday (opened=Mon 09:00, closed=Mon 17:00),
            then opens another shift on Tuesday (opened=Tue 09:00).
  A sale on Monday at 14:00: both shifts match the user_id/time criteria.
  The ORDER BY opened_at DESC picks the Tuesday shift — WRONG!
  Wait — is that correct? Let me trace:
  - Monday shift:  opened_at='Mon 09:00', closed_at='Mon 17:00'
  - Tuesday shift: opened_at='Tue 09:00', closed_at=NULL (still open)
  - Sale at Mon 14:00: created_at='Mon 14:00'
  
  For Monday shift:  opened_at('09:00') <= created_at('14:00') ✓
                     closed_at('17:00') >= created_at('14:00') ✓
  For Tuesday shift: opened_at('Tue 09:00') <= created_at('Mon 14:00')? 
                     No — 'Tue' > 'Mon' lexicographically. So FALSE.
  
  The ORDER BY opened_at DESC ensures we pick the Monday shift
  (the one with opened_at closest to but not exceeding created_at).
  ✓ CORRECT behavior.

Edge case: Missing shifts (no shift data exists at all)
─────────────────────────────────────────────────────────
  If no shifts exist in the database, the subquery returns NULL.
  WHERE shift_id IS NULL AND EXISTS (false) → no update.
  ✓ SAFE — sales remain with shift_id = NULL.

Edge case: No matching shift for a legacy sale
────────────────────────────────────────────────
  Possible causes:
  a) Sale created before the shift system existed
  b) Sale created by a user who never opened a shift
  c) Sale created_at is before earliest shift's opened_at
  d) Sale created after the only matching shift was closed
  → shift_id stays NULL. Reports that filter by shift_id will
    exclude these sales. They remain visible in date-range reports
    (dashboard, sales-by-period, etc.).
  ✓ SAFE — no incorrect assignment.

Edge case: Clock/date inconsistencies
───────────────────────────────────────
  Scenario: opened_at is stored in local time (datetime('now','localtime'))
            but created_at is stored in UTC (DEFAULT CURRENT_TIMESTAMP).
  
  The comparison shifts.opened_at <= sales.created_at compares a
  LOCAL time string against a UTC time string. For machines with a
  POSITIVE UTC offset (UTC+1, UTC+2, etc.), the local time is AHEAD
  of UTC. A shift opened at the same real moment as a sale will have
  opened_at > created_at in string comparison, causing a FALSE NEGATIVE.
  
  For example (UTC+1):
    Shift opened:  09:00 local → opened_at = '2026-07-29 09:00:00'
    Sale created:  08:00 UTC   → created_at = '2026-07-29 08:00:00'
    Comparison: '09:00:00' <= '08:00:00' → FALSE → SALE NOT MATCHED!
  
  Risk: ⚠️ MEDIUM
  Impact: Some percentage of legacy sales will remain orphaned despite
          having a valid matching shift.
  False positives: ZERO — the comparison is only too strict, never too loose.
  False negatives per UTC+1 offset: ~1 hour window per day (the UTC hour
          vs local hour difference).
  
  ✓ NO false positives risk — the backfill can never link a sale to the
    wrong shift. The timezone issue only causes MISSED matches.

Edge case: Concurrent users
────────────────────────────────
  The migration runs at app startup, before any IPC handlers are
  registered (inside the database initialization flow). No concurrent
  writes can occur.
  ✓ SAFE.

Edge case: Legacy databases with different schema versions
────────────────────────────────────────────────────────
  The backfill references columns that have existed since the database
  was created (sales.user_id, sales.created_at, shifts.user_id,
  shifts.opened_at, shifts.closed_at). These are all original DDL
  columns, not added by migrations.
  ✓ SAFE for all schema versions.

FIX 2 DETAILED FINDINGS: Auto-close Previous Open Shift
========================================================================

2A. IMPLEMENTATION REVIEW ─────────────────────────────────────────────

File: src/electron/handlers/ipc-cash-register-handlers.cjs (lines 22-66)

  db.run(
    `UPDATE shifts SET status = 'closed', closed_at = datetime('now','localtime')
     WHERE user_id = ? AND status = 'open'`,
    [data.user_id],
    function(closeErr) {
      // then INSERT new shift
    }
  );

✓ User-specific scope: only closes shifts for the same user_id
✓ Only touches status and closed_at — leaves reconciliation fields intact
✓ Runs BEFORE insert — prevents race conditions
✓ Callback chain ensures sequential execution within a single connection

2B. ARCHITECTURE COMPARISON ───────────────────────────────────────────

Three possible designs were considered:

  Option A — Auto-close (IMPLEMENTED):
    Pro: Simple, matches real POS behavior (closing register for handover)
    Pro: User never blocked from starting a new shift
    Con: Previous shift is closed without reconciliation
          (cash_sales/card_sales left at whatever value they had)

  Option B — Reject (alternative):
    Pro: Forces proper closure workflow, no data loss
    Pro: Every shift is reconciled before a new one opens
    Con: User is stuck if previous shift can't be reconciled immediately
    Con: Requires the user who opened the shift to close it (inflexible)
    Con: UI already handles this client-side (Hides "Open" button)

  Option C — Auto-close with computed reconciliation (hybrid):
    Pro: Previous shift would have accurate cash_sales/card_sales
    Con: Complex — requires computing totals before closing
    Con: closing_actual can't be known without user input
    Con: Over-engineered for an edge case

  Recommendation: Option A (current) is correct for this POS design.
  The auto-close is a safety net / last resort. In normal operation,
  users close shifts properly via Z Report or the Close button.
  The auto-close only fires when a user explicitly opens a new shift
  despite an existing open one — a deliberate action that implies the
  previous shift is abandoned.

2C. IMPACT ANALYSIS ───────────────────────────────────────────────────

Shift reconciliation:
──────────────────────
  Before: Old shift remains open indefinitely (orphaned).
  After:  Old shift is closed with status='closed', closed_at=now.
          cash_sales/card_sales/other_sales remain at their last value.
  Risk: ⬜ LOW. The shift reconciliation fields were never updated by
         the add-sale handler anyway — they've always been 0 until the
         close-shift handler explicitly writes them. Reports query sales
         directly for totals, not these fields.

Closing expected/actual amounts:
──────────────────────────────────
  The auto-close does NOT touch closing_expected, closing_actual, or
  difference. These remain at whatever value they had (0 if never
  reconciled). A subsequent Z Report for this shift would store 0 for
  cash_sales/card_sales/other_sales in the z_reports row.
  Risk: ⬜ LOW. The Z Report's total_revenue comes from sales table
         (accurate). Only the payment-method split stored as
         cash_sales/card_sales/other_sales in z_reports would be 0.

Cash drawer events:
────────────────────
  The auto-close does NOT insert a cash_drawer_event row for the
  closure. Only the new shift's opening event is recorded.
  Risk: ⬜ LOW. The auto-close is an administrative cleanup, not a
         cash event. The old shift's shift_open event already exists.

Audit logs:
────────────
  The auto-close does NOT insert an audit_log entry for the closure.
  Only the new shift's SHIFT_OPEN entry is created.
  Risk: ⬜ LOW. The SHIFT_OPEN entry for the new shift implicitly
         documents that the previous one was closed.

X Report:
──────────
  Before: X Report could find the WRONG open shift (multiple open shifts
           per user). With auto-close, only ONE open shift exists per
           user, so X Report always finds the correct active shift.
  After:  ✓ IMPROVED — correct behavior.

Z Report:
──────────
  The Z Report finds the latest open shift, then closes it via:
    UPDATE shifts SET status='closed' WHERE id=? AND status='open'
  If the shift was auto-closed, this UPDATE affects 0 rows, but the
  z_reports INSERT still happens. The z_reports row stores shift's
  cash_sales (which may be 0 for auto-closed shifts).
  Risk: ⚠️ MEDIUM. If the Z Report is generated for a shift that was
         auto-closed (not the current active one), the stored
         cash_sales/card_sales/other_sales in z_reports will be 0.
  Workaround: This only happens if the user explicitly selects a closed
              shift for Z Report (via shift_id parameter), not in the
              normal "close current shift" flow.

  ⚠ NOTE: The close-shift handler (caisse:close-shift lines 68-108)
    does NOT check this.changes === 0 after the UPDATE. If the shift
    was already auto-closed, the handler still resolves success:true
    and attempts to insert audit_logs/cash_drawer_events referencing
    the now-closed shift. This is misleading but not data-corrupting.

BI Export:
───────────
  No BI export code was modified. The new datasets (audit_logs,
  vat_rates) are unrelated to the auto-close.
  Risk: ⬜ NONE.

4. DATA INTEGRITY REVIEW
========================================================================

Sales ↔ Shifts:
  FK: sales.shift_id REFERENCES shifts(id). SQLite enforces FK only
  if PRAGMA foreign_keys = ON. If enabled, the backfill maintains
  referential integrity (only sets shift_id to valid shift IDs).
  Risk: ⬜ LOW. FK enforcement depends on PRAGMA setting.

Sales ↔ Cashiers:
  Sales have user_id (FK to users). Shift_id links to a shift that
  was opened by the same user_id. The backfill maintains this
  constraint by matching user_ids.
  ✓ No orphan risk.

Shifts ↔ Cash drawer events:
  cash_drawer_events records a user_id and user_name but does NOT have
  a shift_id FK. The shift_open event references the shift through
  the notes field ("Ouverture de caisse #N"), not by FK.
  Risk: ⬜ LOW. No orphan risk because there's no FK to violate.

Reports ↔ BI datasets:
  BI exports read directly from tables, not from report handlers.
  All 21 datasets are verified to load correctly.
  ✓ No regression.

Orphan records:
  After the backfill, some sales may still have shift_id = NULL
  (no matching shift found). These are not orphans — they existed
  before the shift system. No FK violation.
  ✓ No risk.

Duplicate records:
  The auto-close ensures at most 1 open shift per user. The backfill
  does not create duplicate rows.
  ✓ No risk.

Race conditions:
  The auto-close runs inside a single SQLite connection's callback
  chain. SQLite serializes all writes within one connection. The
  backfill runs at startup before IPC handlers are registered.
  ✓ No race condition risk.
