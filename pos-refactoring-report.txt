───────────────────────────────────────────────────────────────────────────────
1. OBJECTIVE
───────────────────────────────────────────────────────────────────────────────

Eliminate the iframe-based POS Generator in the client portal and replace it
with a native React implementation that is 100% UI-identical to the Admin
frontend's POS Generator (admin/), while removing the runtime dependency on
the Admin build output.

The old architecture required admin/ to be built and its dist/ copied into
frontend/public/ so the client portal could iframe it. This was fragile,
complex, and prevented independent deployment of the two frontends.

4. KEY DESIGN DECISIONS
───────────────────────────────────────────────────────────────────────────────

  4.1 AccessModeContext — Dual-Mode Support
  ┌─────────────────────────────────────────────────────────────────────┐
  │ The POS Generator serves two user types:                           │
  │ • Admin mode: full access — select any client, any sector          │
  │ • User mode: restricted — auto-bound to own ID, own sector         │
  │                                                                     │
  │ AccessModeContext detects the mode by checking the URL for          │
  │ /user/<userId> prefix and currentUser cookie. Step1BasicConfig     │
  │ reads isUserMode to conditionally lock the client selector.        │
  └─────────────────────────────────────────────────────────────────────┘

  4.2 Step State Machine (usePOSGenerator hook)
  ┌─────────────────────────────────────────────────────────────────────┐
  │ Steps: 0=BasicConfig → 1=Modules → 2=Customizer → 3=License       │
  │        → 4=Results                                                  │
  │                                                                     │
  │ The hook manages:                                                   │
  │   - currentStep (0-4)                                               │
  │   - status: idle | generating | building | completed | error        │
  │   - buildProgress: { percent, message }                             │
  │   - error: string | null                                            │
  │   - generatePOS() → calls POST /api/pos/generate, then polls       │
  │     GET /api/pos/build-status/:licenseId until completion           │
  └─────────────────────────────────────────────────────────────────────┘

  4.3 Module Registry Pattern
  ┌─────────────────────────────────────────────────────────────────────┐
  │ POSComponentRegistry.tsx maps a module string ID to its preview     │
  │ component via a Record<string, React.ComponentType>. This allows:   │
  │   - New module previews added by importing + registering (1 line)   │
  │   - Dynamic lookup at runtime without switch/if chains              │
  │   - Lazy loading potential for large module sets                    │
  └─────────────────────────────────────────────────────────────────────┘

  4.4 Service Layer Isolation
  ┌─────────────────────────────────────────────────────────────────────┐
  │ Each backend domain has its own service file:                       │
  │   clientService  → /api/clients, /api/user/profile                 │
  │   moduleService  → /api/pos-modules?sector=                         │
  │   posService     → /api/pos/generate, /api/pos/build-status,       │
  │                     /api/pos/download                               │
  │   licenseService → /api/licenses (POST), /api/plans                │
  │   usbService     → /api/usb/drives                                  │
  │                                                                     │
  │ All services share the same axios instance from lib/api.ts          │
  │ with baseURL = http://localhost:3001/api and                         │
  │ withCredentials = true for cookie-based auth.                       │
  └─────────────────────────────────────────────────────────────────────┘

  4.5 Preview System
  ┌─────────────────────────────────────────────────────────────────────┐
  │ POSRealtimePreview renders a phone/tablet/desktop frame containing  │
  │ the selected module's preview component. Layout components:         │
  │   - POSNavbar: top bar with logo, time, battery, status icons       │
  │   - POSHeader: store name, cashier info                             │
  │   - POSContent: wraps the active preview component                  │
  │                                                                     │
  │ Each module preview receives a `config` prop (colors, fonts,        │
  │ business info) so live customization reflects instantly.            │
  └─────────────────────────────────────────────────────────────────────┘

  4.6 Step 3 (Customizer) Bypassed
  ┌─────────────────────────────────────────────────────────────────────┐
  │ The customization step exists in the step bar (step 3 of 5) but     │
  │ is currently bypassed: clicking "Suivant" on step 2 jumps to step 4 │
  │ (license). In the current stepDisplay logic:                        │
  │   if (stepDisplay === 2) generatorHook.goToStep(4)                  │
  │                                                                     │
  │ This preserves the 5-step visual flow while the POSCustomizer       │
  │ component is developed and tested further.                          │
  └─────────────────────────────────────────────────────────────────────┘
