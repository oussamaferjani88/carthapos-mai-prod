## 2. Critical Issues

### 2.1 JWT Authentication Disabled in Production [CRITICAL]

**Files:**
- `backend/server.js:70-87` — Auth middleware commented out
- `backend/server.js:87` — Comment: `// TODO: Re-enable before production deployment`
- `admin/src/lib/api.js:13-55` — JWT interceptors disabled
- `admin/src/App.jsx:28-52` — ProtectedRoute component commented out

**Impact:** All API routes including license management, POS generation, user management, and database operations are fully unauthenticated. Any external actor can create licenses, generate POS apps, and modify the database.

**Recommendation:**
1. Uncomment auth middleware in `server.js`
2. Implement role-based access control (RBAC) for admin routes
3. Add API key authentication for the POS generation endpoint
4. Remove the "TODO" comments and enforce auth in all environments

---

### 2.2 eval() / new Function() for User Input [CRITICAL]

**Files:**
- `pos-template/src/pages/Sales.jsx:408` — `new Function('return ' + keypadValue)`
- `admin/src/components/pos/preview/modules/POSSales.jsx:230` — `eval(keypadValue)`
- `admin/src/components/pos/preview/modules/POSCalculator.jsx:15` — `new Function('return ' + expression)`
- `frontend/src/components/pos/preview/modules/POSSales.tsx:179` — `new Function('return ' + expression)`

**Impact:** Arbitrary JavaScript execution from user input. While keypad input is typically numeric, a crafted input like `require('child_process').execSync('rm -rf /')` would execute in the Electron renderer process with full system access.

**Recommendation:**
1. Replace with a safe math expression parser (e.g., `mathjs`, `expr-eval`, or a simple custom tokenizer)
2. Use `Function` constructor only with sanitized numeric input
3. Add input validation before any expression evaluation

## 3. Security Concerns

### 3.1 CORS Wildcard in Production [HIGH]

**File:** `backend/server.js:50`

```js
origin: '*'  // Any website can make requests to the API
```

**Impact:** Cross-origin requests from any domain can access license management, POS generation, and database endpoints.

**Recommendation:** Configure CORS with explicit allowed origins from environment variables:
```js
origin: process.env.CORS_ORIGINS?.split(',') || ['http://localhost:5173']
```

---

### 3.2 Four Different JWT/Encryption Secret Fallbacks [HIGH]

**Files:**
- `backend/middleware/auth.js:4` — `'carthapos-secret-key-change-in-production-2025'`
- `backend/src/config/index.js:15` — `'your-secret-key-change-in-production'`
- `backend/utils/license.js:58` — `'default-signing-secret'`
- `backend/utils/license.js:33,45` — `'default-32-char-encryption-key-here'`

**Impact:** Tokens generated by one part of the system may not validate in another. If any env var is unset, the system silently falls back to a weak, well-known secret.

**Recommendation:**
1. Centralize all secrets in a single config module
2. **Fail on startup** if `JWT_SECRET` is not set in production
3. Remove all hardcoded fallbacks

---

### 3.3 Unauthenticated Database Seeding Endpoint [MEDIUM]

**File:** `backend/routes/seed-api.js:6-41`

The `POST /api/seed/run-seed` endpoint is publicly accessible and can create/modify database contents.

**Recommendation:** Add authentication middleware and restrict to admin role only.

---

### 3.4 Demo Credentials Displayed in Production Auth Form [MEDIUM]

**File:** `admin/src/components/auth/AuthenticationForm.jsx:302-314`

Demo credentials (`admin/admin123`, PINs `1234`/`5678`) are shown unconditionally.

**Recommendation:** Gate behind `NODE_ENV === 'development'` or a feature flag.

---

### 3.5 Production Console Methods Completely Disabled [MEDIUM]

**File:** `pos-template/src/main.jsx:52-57`

```js
console.log = () => {};
console.error = () => {};
console.warn = () => {};
```

**Impact:** Makes debugging and incident response impossible in production.

**Recommendation:** Use a structured logger (e.g., Winston, Pino) instead of silencing all output. Send errors to a remote logging service.

## 4. Architecture & Duplicated Logic

### 4.1 PrismaClient Instantiated 31 Times [HIGH]

**Impact:** Each `new PrismaClient()` creates a separate database connection pool. With 31 instantiations across routes and services, this creates connection pool exhaustion risk and wastes memory.

**Affected files (partial list):**
- `backend/server.js:9`
- `backend/routes/pos.js:12`, `users.js:6`, `clients.js:4`, `modules.js:4`, `licenses.js:7`
- `backend/routes/bi-requests.js:8`, `bi-uploads.js:22`, `bi-dashboards.js:5`
- `backend/services/warehouse-service.js:14`, `etl-pipeline.js:8`, `bi-insight-generator.js:4`
- ... and 20+ more files

**Note:** A centralized singleton exists at `backend/src/config/database.js` but is only used by `server-v2.js`.

**Recommendation:** Import the singleton from `database.js` everywhere. Remove all local `new PrismaClient()` calls.

---

### 4.2 Two Parallel Server Entry Points [HIGH]

**Files:**
- `backend/server.js` (v1, ~180 lines) — inline middleware, no auth, inline error handler
- `backend/server-v2.js` (v2, ~195 lines) — centralized config, rate limiting, Swagger, controller pattern

Both have separate npm scripts (`start`/`dev` vs `start:v2`/`dev:v2`). The v2 server still imports all legacy routes.

**Recommendation:** Migrate fully to v2, remove v1, consolidate scripts.

---

### 4.3 Dual Route Architecture (Old vs New) [HIGH]

Both old-style (raw Prisma inline) and new-style (controller/repo/service) routes coexist and are loaded simultaneously.

**Example pair:**
- Old: `backend/routes/pos.js` (946 lines, inline Prisma queries)
- New: `backend/src/routes/pos.js` (253 lines) → `src/controllers/posController.js` → `src/services/posService.js` → `src/repositories/posRepository.js`

**Recommendation:** Complete the migration to the controller/service/repository pattern. Remove old routes once new ones are verified.

---

### 4.4 Duplicated app-config.json Generation [MEDIUM]

Both `AssetManager.createConfigFile()` and `ThemeCustomizer.updateAppConfig()` write `public/app-config.json` with different schemas:
- `AssetManager` writes `license.licenseKey` (line 373)
- `ThemeCustomizer` writes `license.key` (line 349)

**Impact:** Config schema depends on which generator ran last. Runtime code must handle both variants.

**Recommendation:** Unify into a single config generation step with a consistent schema.

---

### 4.5 Duplicated `ensurePreloadFile` Method [MEDIUM]

**Files:**
- `backend/utils/generators/AssetManager.js:178-195`
- `backend/utils/generators/FilePatcher.js:206-239`

Both are called during generation by `index.js`.

**Recommendation:** Keep in `AssetManager` only (it runs first), remove from `FilePatcher`.

---

### 4.6 Duplicated Tailwind Safelist [LOW]

**File:** `backend/utils/config/TailwindConfigManager.js`
- Lines 111-129 and 163-181 — identical 18-line array

**Recommendation:** Extract to a shared constant.

---

### 4.7 Duplicated Demo Credentials in 7+ Locations [MEDIUM]

Hardcoded `admin/admin123`, `caissier/caissier123`, `manager/manager123` appear in:
- `pos-template/src/contexts/AuthContext.jsx:83-103`
- `pos-template/src/components/POSWithAuth.jsx:41-60`
- `admin/src/components/auth/AuthenticationForm.jsx:30,45-47`
- `admin/src/pages/Login.jsx:119`
- `backend/prisma/seed.js:316,334`
- `backend/utils/autoSeed.js:293`
- `backend/routes/seed-api.js:29`

**Recommendation:** Centralize demo credentials in a single constants file. Reference from all locations.

---

### 4.8 API_BASE_URL Default in 8+ Frontend Files [LOW]

Various `const API_BASE_URL = import.meta.env.VITE_API_URL || 'http://localhost:3001/api'` with inconsistent fallback values across admin and frontend projects.

## 5. Inconsistent Patterns

### 5.1 JWT Secret Defaults Differ Between v1 and v2 [HIGH]

- `backend/middleware/auth.js:4` — `'carthapos-secret-key-change-in-production-2025'`
- `backend/src/config/index.js:15` — `'your-secret-key-change-in-production'`

Tokens generated by one won't validate in the other.

**Recommendation:** Single source of truth for all secrets.

---

### 5.2 Hook Filenames Mix camelCase and kebab-case [LOW]

```
useAppConfig.js     (camelCase)  ← project convention
use-mobile.js       (kebab-case) ← shadcn/ui convention
use-toast.js        (kebab-case) ← shadcn/ui convention
```

**Recommendation:** Adopt one convention. Since most project hooks use camelCase, rename shadcn hooks or keep them isolated in a `shadcn/` directory.

---

### 5.3 Different Error Handling Between Old and New Routes [MEDIUM]

- **Old routes:** Inline `try/catch` + `console.error` + manual `res.json()`
- **New routes:** `asyncHandler` wrapper + centralized `errorHandler` middleware

**Recommendation:** Standardize on the new pattern.

---

### 5.4 Dual Bcrypt Libraries Installed [MEDIUM]

**File:** `backend/package.json:31-32`

Both `bcrypt` (native) and `bcryptjs` (pure JS) are listed as dependencies.

**Recommendation:** Remove one. Use `bcryptjs` everywhere for portability, or `bcrypt` for performance — not both.

---

### 5.5 CORS Configuration Inconsistency [MEDIUM]

- `backend/server.js:50` — Hardcoded `origin: '*'`
- `backend/src/config/index.js:20` — `process.env.CORS_ORIGIN || '*'`
- `backend/server-v2.js:50` — Uses `config.cors`

**Recommendation:** Use the centralized config module everywhere.

---

### 5.6 Metabase URL Handling Inconsistency [LOW]

- `admin/src/pages/AdminDashboardViewer.jsx:23` — Hardcoded `'http://localhost:3000'`
- `backend/routes/bi-dashboards.js:7` — `process.env.METABASE_BASE_URL || 'http://localhost:3000'`

**Recommendation:** Use env var consistently.

---

### 5.7 app-config.json Schema Differs Between Generators [MEDIUM]

- `AssetManager` writes `{ license: { licenseKey: "..." } }`
- `ThemeCustomizer` writes `{ license: { key: "..." } }`

**Recommendation:** Standardize on one schema. Check which field the runtime (`POSConfiguration.js`) actually reads.

## 6. Error Handling Gaps

### 6.1 Production Error Handlers Continue in Corrupted State [HIGH]

**File:** `backend/server.js:143-158`

```js
process.on('uncaughtException', (err) => {
  console.error('Uncaught Exception:', err);
  // Server continues running!
});
```

Compare with `server-v2.js:184-193` which properly calls `gracefulShutdown()`.

**Recommendation:** Implement graceful shutdown in v1, or migrate fully to v2.

---

### 6.2 Critical Module Filtering Operations Silently Fail [HIGH]

**File:** `backend/utils/generators/ModuleFilter.js`
- Lines 176-178: Navbar filtering — catches error, logs warning, continues
- Lines 286-288: Route cleanup — catches error, logs warning, continues

**Impact:** If these fail, the generated POS may have broken navigation or dead route imports.

**Recommendation:** At minimum, add the failing module name to a warnings list returned to the admin UI. Consider making these non-optional with proper error propagation.

---

### 6.3 optionalAuth Swallows ALL Errors [MEDIUM]

**File:** `backend/middleware/auth.js:101-103`

```js
catch (error) { next(); }  // Any error proceeds without auth context
```

**Impact:** Database errors, JWT library crashes, etc. are all swallowed.

**Recommendation:** Only catch `JsonWebTokenError` and `TokenExpiredError`. Let other errors propagate.

---

### 6.4 Empty Catch Block Silently Swallows Print Errors [MEDIUM]

**File:** `pos-template/src/pages/Kitchen.jsx:176`

```js
try { printWin.print(); } catch (e) {}  // Completely invisible failures
```

**Recommendation:** At minimum log to a local error file or show a toast notification.

---

### 6.5 PerfLogger File I/O Errors Silent [LOW]

**File:** `backend/utils/generators/PerfLogger.js:45-47`

```js
catch (err) { // silent }
```

**Recommendation:** Log to stderr or a fallback location.
