1. EXECUTIVE SUMMARY
-------------------------------------------------------------------------------
CarthaPOS already has a solid single-tenant-per-tenantId warehouse (PostgreSQL
via Prisma), a tenant-isolated analytics/cache service layer, and a Metabase
integration that currently only does discovery + public-link embedding. The BI
backend, ETL, templates, dashboard model, assignments, and both frontends are
all wired and verified end-to-end. What is missing is the Metabase-side
"duplicate a master dashboard per client with a tenant filter" capability --
the API client has no duplicate/collection-create/card/parameter/JWT methods.
Tenant isolation today is therefore weak at the Metabase layer: the embed is a
plain public iframe with no client_id binding, even though every BI view
already exposes client_id, so the correct per-tenant architecture is
structurally ready.


2. CURRENT BI ARCHITECTURE (AS BUILT)
-------------------------------------------------------------------------------
- Client uploads Excel/CSV -> BiUpload/BiUploadFile -> etl-pipeline.js
  (validation via bi-schema-registry.js, dims/facts built) -> warehouse tables
  dim_*/fact_*.
- ETL forces tenant = upload.clientId (etl-pipeline.js lines 53-64); DimClient
  is tenantId @unique; dim keys namespaced cust_${clientId}_...
- Phase 3 of ETL auto-creates a BiRequest (PENDING) per upload.
- BI views migration 20260611180000_create_bi_views creates v_sales,
  v_revenue_daily, v_inventory, v_appointments, v_suppliers, v_dashboard_kpis,
  v_peak_hours -- ALL expose client_id derived from fact/dim tenantId.
- warehouse-service.js queries are all tenantId-scoped; analytics-cache-service
  is clientId-keyed (snapshot per client).
- BiDashboard + BiDashboardAssignment (ACTIVE/SUPERSEDED) + BiDashboardTemplate
  drive the client-facing dashboard lifecycle.


3. WAREHOUSE / TENANT STRUCTURE
-------------------------------------------------------------------------------
- ONE shared PostgreSQL schema; tenancy is a tenantId column on every dim/fact
  (dim tenantId @unique on DimClient; facts carry tenantId). No separate
  schemas/DBs per tenant.
- Views join on client_id (e.g. fs.tenantId, dc.tenantId) -> per-tenant reads
  are trivially possible in SQL.
- analytics-cache metadata maps clientId -> uploadId -> COMPLETED snapshot.


4. CURRENT METABASE INTEGRATION
-------------------------------------------------------------------------------

  recursive listDashboards (filters model === 'dashboard'), GET/POST
  /api/dashboard/:id/public_link -> returns UUID.
- routes/bi-metabase.js: only GET /collections and GET /collections/:id/dashboards.
- METABASE_EMBED_SECRET empty -> no JWT/signed embedding. No dashboard

- Embed endpoint returns { available, enabled, metabaseDashboardId, iframeUrl,
  embedType, ... } with iframeUrl = {METABASE_PUBLIC_URL}/public/dashboard/{uuid}.

7. CURRENT TENANT ISOLATION -- CLASSIFICATION
-------------------------------------------------------------------------------
Against the A-E options, current state is closest to E (NO tenant filtering at
the Metabase layer):
- warehouse-service.js + analytics-cache = fully tenant-isolated (Strategy-B-
  style for the API side).
- BI views carry client_id -> Strategy A is structurally ready (dashboards can
  be filtered per tenant).
- But the embed served today is a BARE public iframe with no client_id param,
  and there is NO evidence the master dashboard cards filter by tenant.
  Isolation currently relies on obscurity of the public UUID, not on a real
  security boundary.


8. CURRENT METABASE DASHBOARD BEHAVIOR / DUPLICATION SEMANTICS
-------------------------------------------------------------------------------
- Duplicating a Metabase dashboard COPIES the dashboard definition + cards +
  saved-question SQL + visualizations -- NEVER data. The duplicate still
  queries the SAME shared warehouse.
- Consequence: if master SQL has no {{client_id}} param, every duplicate shows
  ALL tenants' data (Tenant A 1000 and Tenant B 2000 both visible -> breach).
  With a client_id param (views already support it), each duplicate becomes a
  clean per-tenant dashboard.
- Public links can pass parameters, but ANYONE with the UUID can alter the URL
  to switch tenants -> not secure. Correct options: LOCKED parameters on the
  public link (param pinned server-side at share time) or SIGNED JWT embed
  (Enterprise -- needs METABASE_EMBED_SECRET).

10. MISSING COMPONENTS (THE GAP)
-------------------------------------------------------------------------------
1. Metabase client: duplicate dashboard (POST /api/dashboard/:id/copy), create
   collection, list/create cards, configure parameters, locked-param public
   link (or signed JWT embed).
2. Per-client dashboard provisioning service (create collection -> copy master
   -> inject client_id param -> share/lock).
3. Persisting the per-client Metabase dashboard id on BiDashboard (field exists;
   no provisioning writer).
4. Signed-embed path (empty METABASE_EMBED_SECRET) for non-public-URL security.
5. Migration/mapping for already-onboarded clients.
6. Verification tooling (does dashboard X filter by tenant?).


11. ARCHITECTURAL RISKS
-------------------------------------------------------------------------------
- Public-link UUID + tenant param in URL = tenant-hopping vulnerability if not
  locked.
- Shared warehouse + unfiltered cards = cross-tenant data exposure
  (Tenant A 1000 / Tenant B 2000 scenario).
- METABASE_EMBED_SECRET empty blocks the enterprise-grade path; public-sharing
  must be enabled globally for the fallback.
- Stale template placeholder IDs (1001/... vs real id 3).
- Admin app token interceptor is currently commented out in
  admin/src/lib/api.js -> admin actions are effectively unauthenticated locally
  (accepted dev posture, but flag for prod).


12. DESIRED ARCHITECTURE (PER-CLIENT TENANT FILTER)
-------------------------------------------------------------------------------
Per client: OWN collection -> duplicated master dashboard -> tenant param
pinned to that client -> public link with locked client_id (or signed JWT
embed) -> store returned Metabase dashboard id in
BiDashboard.metabaseDashboardId -> existing embed route serves the
tenant-specific iframe. Master template remains the single source of truth;
clients inherit changes via re-provisioning.
