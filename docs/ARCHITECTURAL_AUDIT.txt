PART 1 -- PROJECT DESCRIPTION
================================================================================

CarthaPOS is a multi-tenant SaaS platform for generating customized Point-of-Sale
(POS) desktop applications for small businesses across Tunisia. The platform
comprises five major subsystems:

  A. Backend API         -- Express.js server: business services, Prisma ORM,
                            PostgreSQL, BI/ETL pipeline, POS generation
  B. Admin Dashboard     -- React SPA for CarthaPOS staff: client/license/module
                            management, POS generation, BI workflow monitoring
  C. Client Frontend     -- React SPA for business owners: registration, account
                            management, POS project access, BI workspace
  D. POS Template        -- Electron desktop app template; source for per-client
                            customized POS applications via an 8-stage generator
  E. Generated Client POS -- The final .exe desktop application installed on the
                            client's hardware, derived from the POS template

The platform supports 6 business sectors: restaurant, cafe, retail, bakery,
pharmacy, and beauty. Each generated POS is tailored to the client's sector
with only relevant modules enabled.

BI follows a GIMSI methodology: POS exports operational data as CSV+ZIP,
uploaded to the backend, processed through an ETL pipeline into a PostgreSQL
analytical warehouse, and visualized via Metabase dashboards.

3.1 ARCHITECTURAL STYLE
-----------------------

The CarthaPOS platform is a multi-application, multi-tenant SaaS architecture
combining:

  - Client-server architecture (admin + client frontends -> backend API)
  - Multi-application architecture (4 separate applications)
  - Electron desktop architecture (POS: IPC-based renderer/main-process split)
  - Modular backend architecture (domain-oriented route + service groups)
  - ETL / data warehouse architecture (BI pipeline)
  - Multi-tenant SaaS (per-client licensing, isolated data, dashboard assignment)

It is NOT a monolithic layered architecture. Each application is independently
buildable and deployable. The backend organizes functionality by domain
(licensing, clients, BI, etc.) rather than by technical layer.

           accesses BI dashboards, operates their generated POS application.

     Uses: Generated POS Application
     Role: Processes sales, manages products/customers/inventory,
           prints receipts, manages cash register.

  4. POS Manager
     Inherits from: POS Operator
     Additional use cases: manage users, security settings, view reports.
     Note: No formal inheritance in code; role-based permission hierarchy
           (MANAGER role has broader permissions than CASHIER).

  5. POS Administrator
     Inherits from: POS Manager
     Additional use cases: full user administration, system configuration.
     Note: ADMIN role in POS permission system.

EXTERNAL ACTORS (systems/devices):

  6. PostgreSQL Database
     Role: Persistent storage for backend data and analytical warehouse.

  7. Metabase
     Role: BI dashboard visualization, connected via REST API and direct PG.

  8. GitHub API
     Role: Release creation for generated POS installers (via @octokit/rest).

  9. USB License Device
     Role: Hardware-bound license storage and verification.

  10. Thermal Printer

PART 17 -- REPORT ARCHITECTURE SUMMARY
================================================================================

The CarthaPOS platform implements a multi-tenant Software-as-a-Service (SaaS)
architecture designed to generate customized Point-of-Sale desktop applications
for small businesses in Tunisia. The system comprises five primary subsystems:
a backend API server, an administration dashboard, a client-facing web portal,
a configurable Electron POS template, and the derived client-specific POS
applications.

The backend is built on Express.js with Prisma ORM managing a PostgreSQL database
containing 43 entity models organized across eight domain groups: user
authorization, client management, licensing, POS configuration, operational
entities, business intelligence management, ETL tracking, and an analytical
warehouse with five dimension tables and six fact tables. The API exposes 32
unique route groups handling authentication, client lifecycle, Ed25519-signed
license management, POS generation orchestration, and a comprehensive BI
workflow.

The POS generation pipeline follows an eight-stage sequential process: license
validation, project initialization, template asset management, module filtering
based on the client's business sector, dependency management with npm
installation, theme customization, post-copy file patching, and desktop
application compilation via electron-builder. The pipeline produces a Windows
NSIS installer distributed through GitHub releases.

The Electron POS application uses an IPC-based architecture separating the
renderer process (React, 27 page components, 70+ UI components) from the
main process (SQLite database management, authentication, license verification,
hardware integration). Local data persists in SQLite with 42 operational
tables. The application supports six business sectors -- restaurant, cafe,
retail, bakery, pharmacy, and beauty -- with sector-specific module
configurations.

Business intelligence follows the GIMSI methodology: the POS application
exports 19 operational datasets as CSV files within a ZIP archive, validated
against a versioned schema (v2.2.0). The backend ETL pipeline extracts,
validates, prepares, and loads data into a PostgreSQL analytical warehouse
within a database transaction. Metabase connects directly to the warehouse
for dashboard visualization, with per-tenant dashboard provisioning via the
Metabase REST API.

The platform is deployed on Render as three services (two static frontends
and one Docker container hosting the backend) with a managed PostgreSQL
database. No CI/CD pipeline is currently configured; deployments are
performed manually.
