13.6 Medium Priority Improvements
----------------------------------
1. Fact builder duplication: The fact-building logic is duplicated between
   _buildWarehouse (in-memory) and _loadFacts (DB). Consolidating into a shared
   mapper function would reduce maintenance risk.

2. Incremental loading: The current full-refresh approach (deleteMany + createMany)
   is appropriate for the current data volumes but could be replaced with incremental
   loading for larger datasets.

3. Connection pooling: The ETL pipeline does not configure Prisma connection pooling
   explicitly. For production workloads with concurrent uploads, explicit pool
   configuration would improve reliability.

4. Parallel dataset loading: The _loadFacts method processes fact tables sequentially.
   Parallel inserts (with proper transaction management) could improve load performance.

5. Reservations fact table: The current warehouse schema does not include a
   FactReservation table. Adding one would enable reservation KPIs for the
   Restaurant and Hotel business types.

13.7 Low Priority Improvements
-------------------------------
1. Magic numbers: The chunk size (1000) and reconciliation tolerances (0.01 absolute,
   0.005 relative) are not defined as named constants. Extracting them to a
   configuration file would improve clarity.

2. _loadFacts method size: The _loadFacts method is ~150 lines with 6 fact builders.
   Extracting each fact builder into a separate method would improve readability.

3. Preparation engine size: The data-preparation-service.js is ~500 lines. Splitting
   it into smaller modules (one per concern: validation, cleaning, reconciliation,
   profiling) would improve maintainability.

4. ETL pipeline size: The etl-pipeline.js is ~1300 lines. Extracting the fact-building
   logic into a separate module would reduce the file size.

5. Logging verbosity: The DEBUG logging in the ETL pipeline is useful for development
   but could be made configurable via environment variable for production use.
