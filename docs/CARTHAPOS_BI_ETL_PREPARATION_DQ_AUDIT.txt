1. EXECUTIVE SUMMARY
════════════════════════════════════════════════════════════════════════════════
The CarthaPOS BI ETL is architecturally sound at the extremes and weak in the
middle. What it does well: strict column-schema governance (single schema
registry, version-gated), faithful grain preservation (sale and item grains
stored as-is), a replace-not-append snapshot policy, and a manual-review wizard
that can block bad loads. What it does not do: real data cleaning in the sense
of Power BI/Talend class tooling — there is no case/value standardization, no
reconciliation or cross-field business-rule validation, no outlier detection,
no data profiling, and two live code paths with different quality behavior.

Headline findings (all empirically verified — see Appendix A):

  F1. Integer type validation is effectively broken.
      bi-schema-registry.js:233 — `if (!/^-?\d+$/.test(val) && !/\d+/.test(val))`
      accepts "12.5", "abc123", "1,200", "1e3", "--12", "+12", " 12 " as VALID
      integers. A `quantity` of "1.5" passes schema validation, then load-time
      `parseInt(row.quantity) || 0` (etl-pipeline.js:650) silently truncates it
      to 1. Real data corruption path.

  F2. Real (decimal) validation is inversely too strict.
      bi-schema-registry.js:239 — rejects scientific notation "1e3", thousand
      separators "1,200.50", "12.", ".5", "+12.5", and padded " 12.5 ". In the
      legacy run() path (strict mode) any such value FAILS the whole upload.

  F3. Datetime validation via Date.parse is extremely lenient.
      bi-schema-registry.js:245 — "2026-02-30", "02/08/2026" (US mm/dd),
      "2026-8-2", "2026-08-02 24:00:00" all PASS. The preparation engine's
      strict parseDate (data-preparation-service.js:21) then rejects them —
      but only in the WIZARD path, and only for columns listed in DATASET_RULES.

  F4. Impossible dates silently roll over in the timestamps path.
      etl-pipeline.js:733 `_toDate()` uses `new Date(...)`. Empirically
      "2026-02-30 00:00:00" becomes 2026-03-01T23:00:00Z (rolled into March)
      and is stored. Affects kitchen started_at/ready_at/completed_at and
      customer last_visit_date — no parseDate guard.

  F5. Two live quality paths. start-etl (routes/bi-uploads.js:529) fires the
      legacy `run()` (etl-pipeline.js:23) which performs NO data preparation:
      no dedup, no text normalization, no null-out of bad values, no ERROR
      gating. Only the wizard path (validate→prepare→preview→correct→confirm)
      uses data-preparation-service.js. Same file, two quality contracts.

  F6. Silent numeric coercion at load. etl-pipeline.js:574 `parseFloat(row.total)
      || 0`, :650 `parseInt(row.quantity) || 0`, :593 `parseInt(row.stock) || 0`
      convert null/invalid numerics to 0 with no flag. `tax: row.tax ? ... : null`
      (:575) maps a legitimate tax of 0 to NULL (falsy check). A unit_price of
      "x" can reach the warehouse as NaN in the run() path (:651).

  F7. Fact- and dimension-level reviewer corrections are silently discarded.
      POST /correct (bi-uploads.js:829) lets reviewers edit 'cleaned',
      'dimensions' OR 'facts' sections, but confirm-load re-derives every fact
      and dimension from cleanedDatasets via _loadDimensions/_loadFacts
      (etl-pipeline.js:1051,1054). Only edits to cleaned-dataset rows persist.

  F8. Referential-integrity handling is binary: hard-fail or silent null.
      fact_sale_items/fact_inventory FK to dim_products (schema.prisma:648-650,
      670); an item referencing a product absent from products.csv throws an FK
      violation inside the $transaction and FAILS the entire upload. An orphan
      sales.customer_id (schema.prisma:653) silently becomes NULL via
      `dimCustomerIds.get(...) || null` (etl-pipeline.js:573). No skip+warn.

  F9. dim_time is seeded ONLY from sales.created_at (etl-pipeline.js:388-416,
      and prepareWarehouse :786-808). Any kitchen_order, appointment, or
      sale_item date on a day with no sales breaks the dim_time FK and fails
      the whole load. (Passed in the test data only because all dates overlapped.)

  F10. No outlier detection, no data profiling, no cross-field reconciliation.
      Only four business checks exist in the entire engine
      (data-preparation-service.js:43-48): NEGATIVE_TOTAL, NEGATIVE_STOCK,
      NEGATIVE_PRICE, INVALID_QUANTITY. The known source anomaly — sale_items
      line-total grain (119,854.00) does not reconcile with the sales-total
      grain (139,869.52) — is stored faithfully but never surfaced or checked.

  F11. BOM/whitespace/CRLF handled correctly (verified). String.prototype.trim()
       strips the UTF-8 BOM, so a "\ufeffsale_id" header is matched cleanly.
       The only CSV-format risk is unescaped quotes / multiline fields, which
       the char-scanner parser (bi-schema-registry.js:176) does not support.

  F12. Duplicate business keys are handled only by DB constraints, silently.
      Exact duplicate ROWS are removed and counted by the preparation engine
      (data-preparation-service.js:167-173). Duplicate business KEYS (two rows
      with the same sale_id) rely on `@@unique([exportId, saleId])`
      (schema.prisma:653) + createMany `skipDuplicates:true` (etl-pipeline.js:697)
      — the second row is silently skipped and the inserted count diverges from
      the source row count with no user-facing warning.

4. MISSING-VALUE HANDLING
════════════════════════════════════════════════════════════════════════════════
Strengths:
  • Empty/whitespace/null are centralized in isEmpty() (data-preparation-service.js:1).
  • Required-field gaps produce structured ERROR issues that BLOCK load until a
    reviewer resolves them (bi-uploads.js:870-878).
  • Sensible defaults exist (tax/discount → 0; name/category → 'Unknown …').

Gaps:
  • Missing values are never imputed for analytics; the engine's contract is
    "flag, don't fix". That is defensible, but the LOAD layer then silently
    converts null numerics to 0 (F6), which contradicts the flag-don't-fix
    contract and hides the problem from dashboards.
  • Non-standard "N/A", "n/a", "-" placeholders are not recognized as null
    (M19); they flow in as free text and break numeric parsing downstream.
  • The falsy check on tax/discount/price (`row.tax ? parseFloat : null`)
    destroys a legitimate zero (M20).
  • There is no null policy for the item/kitchen facts (unit_price, vat_rate,
    line_total can be NULL with no KPI-level default).

5. BUSINESS-RULES VALIDATION
════════════════════════════════════════════════════════════════════════════════
Total rule set in the engine: FOUR (data-preparation-service.js:43-48)
  • NEGATIVE_TOTAL  (sales.total < 0)              WARN
  • NEGATIVE_STOCK  (products/inventory.stock<0)   WARN
  • NEGATIVE_PRICE  (products.price < 0)           WARN
  • INVALID_QUANTITY (sale_items/kitchen qty ≤ 0)  ERROR/WARN
All are single-column, range-style checks. None are cross-field, cross-row, or
cross-dataset. No reconciliation of: line_total vs qty×price (B34), item grain
vs sale grain (B35 — a real 119,854 vs 139,869.52 discrepancy exists in the
T1 snapshot), total vs tax+discount arithmetic (B36), VAT math (B37), duplicate
receipts by table+time, negative prep-time (started_at==ready_at ~66% of kitchen
rows), or inventory-stock-vs-times_sold sanity. Compare: Power BI/Fabric data
flows and Talend Data Quality ship catalogs of 100+ built-in rule templates and
a rule-evaluation scoring layer. The wizard's ERROR gate (bi-uploads.js:870)
is an excellent enforcement mechanism — it is just fed too few rules.

6. REFERENTIAL INTEGRITY
════════════════════════════════════════════════════════════════════════════════
The DB layer enforces FKs (schema.prisma:648-650, 670, 743, etc.), but the ETL
layer does no proactive referential checking. Consequences (all traced to code):

  • sale_items.product_id → dim_products FK (schema.prisma:742): if the POS
    export contains an item whose product is absent from products.csv, the
    createMany throws, the $transaction (etl-pipeline.js:1037) rolls back, and
    the ENTIRE upload fails. One orphan line kills the load (F8).
  • inventory.product_id → dim_products: same failure mode (schema.prisma:670).
  • sales.customer_id → dim_customers: handled in reverse — the FK column is
    silently NULLed (`dimCustomerIds.get(...) || null`, etl-pipeline.js:573),
    so orphan customer references are invisible in the warehouse.
  • sale_items.sale_id → fact_sales: NO FK at all (just a string column
    schema.prisma:745). Orphan items load without a parent sale — no check.
  • dim_time.date → any fact dimTimeId (schema.prisma:649,670,690,713,743,769):
    dim_time is seeded only from sales.created_at (F9), so a kitchen/appointment/
    item date on a sales-free day violates the FK and fails the load.
  Professional ETLs implement "graceful handling": skip-and-log orphans, or
  auto-create placeholder dimension rows, or quarantine a bad batch. CarthaPOS
  currently has hard-fail and silent-null only.

7. DIMENSION & FACT PREPARATION
════════════════════════════════════════════════════════════════════════════════
Dimensions:
  • Surrogate keys are deterministic (`prod_<client>_<product_id>`) —
    good for re-imports (etl-pipeline.js:444,477,514).
  • DimClient upsert is idempotent per tenant (:424-436) and uses the friendly
    business_name from metadata (:422) — good.
  • DimTime is derived at day grain with integer id YYYYMMDD (:713-719) and is
    correctly populated only from sales (:388-416) — the F9 gap above.
  • No attribute standardization on dimension columns (category/family/barcode
    kept verbatim — see §8).

Facts:
  • Grain fidelity is a real strength: sale grain (fact_sales) and item grain
    (fact_sale_items) are both stored with their own measures, and the known
    grain-level mismatch (119,854 vs 139,869.52) is preserved faithfully
    rather than "fixed" by fudging numbers. This is the correct ETL instinct;
    the missing piece is surfacing the gap to the analyst (F10).
  • Measure coercion is inconsistent with the flag-don't-fix contract (F6):
    `parseFloat(x)||0`, `parseInt(x)||0`, and `x ? parseFloat(x) : null`.
  • Wizard fact rows set dimClientId: null (etl-pipeline.js:962,989) while the
    run() path sets it (:570) — inconsistent link to DimClient.
  • transactionHour extraction is robust (guarded 0-23, :725-731, verified).

8. STANDARDIZATION
════════════════════════════════════════════════════════════════════════════════
  • Text: whitespace normalization only (:8). Case is NEVER folded. Empirically
    'CASH' and 'cash' both survive into fact_sales.payment_method. The same
    applies to status ('pending','Pending','PENDING'), priority, category,
    family, department, table_number, product_name. A payment-mix pie chart on
    this warehouse would show two "Cash" slices.
  • Dates: normalized to naive ISO YYYY-MM-DD[ HH:MM:SS] in the wizard (:25-40),
    but mixed ' ' and 'Z' timestamps are not converted to one timezone (S14).
  • Numbers: normalized to plain decimal (parseNumber) — but only for columns
    declared `numeric` in DATASET_RULES; a price arriving as "1,200.50" or "1e3"
    is flagged invalid rather than converted (F2). Currency/unit conversion: none.
  • Enums: no canonical value maps anywhere (M27/B40). Talend Data Quality /
    Power BI Dataflow "Replace values" & domain-rule normalization are absent.
  Impact on BI: any GROUP BY categorical dimension (payment, category, status)
  will silently split a single logical value into case variants.

9. OUTLIER DETECTION
════════════════════════════════════════════════════════════════════════════════
None. There is no z-score/IQR/MAD computation, no min/max band, no zero-price
sale, no huge-quantity, no negative-preparation-time, no midnight-shift check.
The only guards are the four column-range checks of §5, and three of them are
WARN-only (they still load). The observable anomalies in the archived T1 data —
stock=0 across every product, started_at==ready_at on ~66% of kitchen rows
(prep_minutes≈0), the item-vs-sale revenue gap — would be invisible to any
automated quality gate and are not flagged to the reviewer at confirm-load.

10. DATA PROFILING
════════════════════════════════════════════════════════════════════════════════
None in the ETL. The validation report contains only row counts, per-dataset
status, and a duplicate-row count (etl-pipeline.js:329-333, 361-363). There is
no missing-%, no distinct/cardinality, no min/max/mean/stddev, no null-rate per
column, no skew, no source-vs-staged delta. Post-load KPI extraction exists
(bi-insight-generator.js) but that is analytics, not profiling, and it only runs
on data that already passed the (weak) ETL gate. Professional tools generate a
Data Quality/Profiling Scorecard before load; CarthaPOS has no equivalent.

════════════════════════════════════════════════════════════════════════════════
11. WAREHOUSE & DASHBOARD READINESS
════════════════════════════════════════════════════════════════════════════════
Already-strong (validated in the prior warehouse-readiness audit):
  • Correct star schema (dims + 6 facts), int surrogate ids for dim_time,
    @@unique guards against intra-upload duplicate keys, snapshot replacement
    policy (deleteMany per tenant, etl-pipeline.js:552-557) prevents
    accumulation across re-imports.
  • 14 BI views are valid and the analytics/cache/dashboard layers consume the
    warehouse contract cleanly; dim_time (183 rows) was preserved intact.

Readiness caveats this audit adds:
  1. Categorical case-splits (§8) will produce misleading charts.
  2. Silent null→0 coercion (§4/F6) makes dashboards over-state sales for
     rows with bad totals (verified: total 'abc' → prepared null → loaded 0).
  3. Grain mismatch (§7/F10) must be documented on the revenue cards, or
     item-based revenue and sale-based revenue will disagree.
  4. FK fragility (F8/F9) means a single bad row can leave the warehouse
     EMPTY (rollback) instead of partially loaded — safe but operationally
     abrupt, and no alert reaches the operator.
  5. Fact/dimension corrections made in the preview UI are discarded (F7) —
     a reviewer can spend time fixing a fact row and have it silently vanish.

Verdict: the warehouse is safe for dashboard consumption on the happy path
(schema, FKs, views, load semantics are sound), but it is not yet trustworthy
for unsupervised professional BI because cleaning/rules/profiling gaps let
unclean values reach dashboards without any flag.

14. FINAL VERDICT (5 QUESTIONS)
════════════════════════════════════════════════════════════════════════════════
Q1. Is the ETL production-ready for unsupervised professional BI?
   NO. The gaps are in the layers that define professional data quality:
   cleaning depth, business rules, referential handling, profiling, and outlier
   detection (13-CRITICAL list). The wizard's manual review gate
   (bi-uploads.js:858) is a partial mitigation, but it only sees the four
   existing rule types and its corrections are partially discarded (F7).

Q2. How close is it to Power BI / SSIS / Talend-class preparation?
   Roughly half-way (5.3/10 overall). At its strengths (schema governance,
   version gating, grain fidelity, snapshot replacement, review gate) it
   matches or exceeds typical Power Query implementations. At cleaning,
   rules, and profiling it is materially below them.

Q3. Is the warehouse safe to build dashboards on TODAY?
   Yes for the happy path (star schema, FKs, views, load semantics validated),
   with four documented caveats: case-variant categorical splits (§8),
   silent null→0 totals (F6), item-vs-sale grain mismatch (F10), and FK
   fragility that can empty the warehouse on one bad row (F8/F9).

Q4. What is the single highest-impact fix?
   C4 + C7 (referential integrity + reconciliation rules) — they convert the
   two most dangerous failure modes (whole-load rollback on one orphan row;
   silent revenue divergence between grains) into visible, reviewable issues.
   C1 (integer regex) is the cheapest and should be done in the same pass.

Q5. Recommended path forward.
   Make the wizard the single production path (C3), land the CRITICAL list
   (C1-C7) first — they are additive and non-breaking — then add profiling +
   outlier detection (R1-R2). The architecture already rewards this investment:
   the schema registry, preparation engine, change-issue model, ERROR gate, and
   star-schema warehouse are all sound foundations that simply need deeper
   cleaning rules plugged in.
