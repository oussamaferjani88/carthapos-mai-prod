2. DATABASE CONNECTIONS - DETAILED ANALYSIS
================================================================================

BACKEND (PostgreSQL - License Tracking):
  • Stores: License, LicenseConfiguration, LicenseModule, Module records
  • Host: DATABASE_URL environment variable
  • Not used by generated POS apps (only admin/backend)

GENERATED POS APP (SQLite - Business Data):
  • Local file-based database (portable)
  • Database name: DYNAMICALLY generated from businessName
  • Location decision: Portable vs Installation mode

CONNECTION STRING GENERATION (NO HARDCODING):
  
  File: pos-template/src/electron/ElectronDatabaseManager.cjs
  
  Process:
    1. loadAppConfig() → reads public/app-config.json
       Returns: { database: { filename: "restaurant_le_gourmet.db" } }
    
    2. getConfiguredDatabaseFilename()
       Returns: "restaurant_le_gourmet.db"
    
    3. getTenantIdentifierFromConfig()
       Returns: License key from config (for multi-instance tracking)
    
    4. Determine directory:
       IF forcePortableMode = true
         → dbDir = app.getAppPath() + "/data"
       ELSE
         → dbDir = C:\Users\[User]\AppData\Roaming\[BusinessName]\data
    
    5. getOrCreateDbFilename()
       Handles collisions if multiple POS instances installed
       Persists mapping in .db-map.json
       Returns: "restaurant_le_gourmet.db" or "_2.db"
    
    6. Open SQLite database
       Path: C:\Users\[User]\AppData\Roaming\Restaurant Le Gourmet\data\restaurant_le_gourmet.db
       new sqlite3.Database(path)

KEY FINDINGS:
  ✅ NO HARDCODED DATABASE PATHS
  ✅ Database name DYNAMICALLY set from businessName
  ✅ Multi-tenant support with collision detection
  ✅ Portable and installation mode flexibility
  
  ⚠️ RACE CONDITION: .db-map.json has no file locking
  ⚠️ If two instances start simultaneously, both might write same DB

3. MODULE SYSTEM ARCHITECTURE
================================================================================

MODULE STORAGE:
  PostgreSQL Tables:
    • Module (id, name unique, displayName, category, isCore)
    • LicenseModule (licenseId, moduleId, isEnabled)

AVAILABLE MODULES (from backend/routes/modules.js):
  • sales, inventory, kitchen, tables, customers
  • loyalty, gift-cards, appointments, services
  • prescription, production, menu-management
  • quick-service, takeaway, barcode, suppliers
  • reports, user-management, settings

ADMIN SELECTION (admin/src/hooks/usePOSModules.js):
  • Loads modules by category
  • Prevents deselecting required/core modules
  • Supports sector-based defaults (restaurant, cafe, retail, etc.)

GENERATION (backend/utils/generators/AssetManager.js):
  • Backend reads license.modules from database
  • Stores in app-config.json: ["sales", "inventory", "kitchen"]
  • Creates LicenseModule records in database

RUNTIME CHECKING (pos-template/src/config/AppConfig.js):
  • POS reads window.__POS_CONFIG__.modules at startup
  • AppConfig.isModuleEnabled(moduleId) checks visibility
  • Components conditionally render based on check

BUNDLING: ⚠️⚠️⚠️ CRITICAL ISSUE ⚠️⚠️⚠️
  
  PROBLEM: All modules are INCLUDED in generated .exe regardless of license
  
  Evidence:
    • src/pages/ contains ALL module pages
    • src/components/ contains ALL module UI
    • Vite bundles all imports into dist/
    • Only RUNTIME VISIBILITY is controlled
    • No tree-shaking or code elimination
  
  Result:
    • 109 MB .exe contains code for ALL modules
    • User could extract and use unlicensed modules
    • Waste of 30-50 MB disk space per app
  
  Example:
    User licenses only "sales" module
    .exe still contains: sales, inventory, kitchen, loyalty, gift-cards, etc.
    Only sales shows in UI, but all code is present
  
  Impact:
    • Security: Unlicensed code in hands of user
    • Performance: Slower startup, larger download
    • UX: Confusing when user discovers hidden modules
  
  Fix Required:
    • Implement tree-shaking with dynamic imports()
    • Only bundle selected modules
    • Reduce .exe from 109 MB to 50-60 MB

4. PERFORMANCE BOTTLENECKS - DETAILED ANALYSIS
================================================================================

BOTTLENECK #1: GitHub Actions Build (6-8 MINUTES - 60% of time)
  
  Location: .github/workflows/build-pos.yml
  
  Steps:
    1. Checkout repo (30 sec)
    2. Setup Node.js (1 min)
    3. Install pos-template deps (2 min) ← npm install
    4. Copy template to generated-pos (10 sec)
    5. Install project deps (3 min) ← npm install again
    6. Build Vite (1-2 min)
    7. Electron-builder (4-5 min)
    8. Upload artifact (1 min)
  
  Why slow:
    • npm install downloads 300+ MB node_modules TWICE
    • No pre-installation in GitHub Actions
    • Vite bundles 2000+ files into dist/
    • Electron-builder packages entire Electron runtime
    • No parallelization

BOTTLENECK #2: npm install (3-5 MINUTES)
  
  Location: backend/utils/generators/BuildSystemManager.js:40-150
  
  Problem:
    • npm install --legacy-peer-deps is I/O intensive
    • 300+ MB node_modules on slow disk
    • Runs TWICE: template install + project install
  
  Solution attempt (partially implemented):
    • Copy from template's node_modules (fast)
    • Fallback to npm install if copy fails
    • But: No pre-installation guarantee
    • Still runs npm ci/install on GitHub Actions

BOTTLENECK #3: Asset Copying (5-20 SECONDS)
  
  Location: backend/utils/generators/AssetManager.js:37-90
  
  Problem:
    • fs.copyFileSync() copies 2000+ files synchronously
    • Blocks entire process
