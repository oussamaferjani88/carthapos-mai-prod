1.1 POS SQLite Database
------------------------
File: pos-template/src/electron/ElectronDatabaseManager.cjs
The POS runs an Electron app with a local SQLite database. Each POS instance
stores operational data in the following tables:
  - sales
  - sale_items
  - products
  - customers
  - restaurant_tables (if tables module enabled)
  - kitchen_orders    (if kitchen module enabled)
  - suppliers         (if suppliers module enabled)
  - services          (if services module enabled)
  - appointments      (if services/appointments module enabled)

---------------------------

File:    pos-template/src/pages/Reports.jsx (line 342)

The BiExportModal renders a file list + "Generate Export" button. When clicked:
  → window.electronAPI.exportBiData()

  → Electron main process receives IPC on channel 'bi:export'

1.3 IPC Export Handler
-----------------------
File: pos-template/src/electron/handlers/ipc-bi-export-handler.cjs
Class: IPCBiExportHandler.runExport()

Flow:
  1. Load app-config.json → clientId, businessType, enabledModules
  2. Collect data from SQLite via 9 _collect* methods:
     - _collectSales()     → SQL JOIN sales + customers
     - _collectProducts()  → SQL FROM products
     - _collectCustomers() → SQL FROM customers
     - _collectInventory() → SQL FROM products + subquery times_sold
     - _collectTables()    → SQL FROM restaurant_tables (if module enabled)
     - _collectKitchenOrders() → SQL FROM kitchen_orders (if module enabled)
     - _collectSuppliers() → SQL FROM suppliers (if module enabled)
     - _collectServices()  → SQL FROM services (if module enabled)
     - _collectAppointments() → SQL FROM appointments (if module enabled)
  3. Map raw DB rows via BiDataMapper (9 specific mappers)
  4. Validate via BiValidator (required fields, types, empty datasets)
  5. Generate CSV files using BiSchemaContract column order
  6. Build metadata.json with schema version
  7. Create ZIP archive (pure Node.js: zlib.deflateRawSync + custom CRC32)
  8. Write to Documents/CarthaPOS/BI_Exports/bi_export_<timestamp>.zip

1.4 Mapping Layer
------------------
File: pos-template/src/electron/bi/BiDataMapper.cjs

column names. If a DB column is renamed, only this file needs updating."

1.8 Upload to Backend
----------------------
Routes File:  backend/routes/bi-uploads.js
Server File:  backend/server.js (lines 105-107)

The ZIP is uploaded via HTTP POST to /api/bi-uploads:
  → multer middleware (100MB limit, .zip only)
  → clientId validated against Client table
  → SHA-256 hash computed for duplicate detection
  → BiUpload record created with status 'UPLOADED'
  → etlPipeline.run() called asynchronously (fire-and-forget)
  → 201 response returned immediately

Client-facing upload: frontend/src/pages/dashboard/BiExportDeploy.tsx
Admin upload:         admin/src/pages/BiUploadPortal.jsx

1.9 ETL Pipeline
-----------------
File: backend/services/etl-pipeline.js
Class: EtlPipeline (singleton)

Steps executed by run(uploadId, zipPath):
  1. Extract ZIP → temp directory (unzip CLI, fallback adm-zip)
  2. Inspect ZIP → log file names, row counts, sizes, headers
  3. Read metadata.json → clientId, businessType, biSchemaVersion, modules
  4. Schema check → compare bi_schema_version against server registry
  5. Validate datasets:
     - Check required columns exist (BiSchemaRegistry.validateCsvColumns)
     - Parse CSV rows (BiSchemaRegistry.parseCsvRow)
     - Type validation (BiSchemaRegistry.validateCsvTypes)
     - Duplicate row detection
  6. DB Transaction:
     a. Create BiProcessingJob record (status PROCESSING)
     b. Load dimensions: DimTime, DimClient, DimProduct, DimSupplier (upsert)
     c. Load facts: FactSale, FactInventory, FactAppointment, FactKitchenOrder (upsert)
     d. Mark job COMPLETED, update upload COMPLETED with totalRows
  7. On failure: mark upload + job FAILED with error message
  8. Cleanup: delete temp directory

1.11 Warehouse (PostgreSQL via Prisma)

Dimension Tables (star schema):
  dim_clients     → DimClient
  dim_products    → DimProduct
  dim_suppliers   → DimSupplier
  dim_time        → DimTime (composite date key: YYYYMMDD integer)

  fact_inventory       → FactInventory (FK: dimProduct, dimTime)
  fact_appointments    → FactAppointment (FK: dimTime)

  bi_upload_files    → BiUploadFile (individual CSV files in ZIP)
  bi_processing_jobs → BiProcessingJob (ETL job status)
  bi_processing_logs → BiProcessingLog (step-by-step audit log)

PART 4 — WAREHOUSE ANALYSIS
================================================================================

4.1 Dimensions
---------------

DimClient (dim_clients)
  PK:   id (cuid)
  UQ:   tenantId
  FK:   referenced by FactSale.dimClientId
  Key fields: tenantId, name, businessType

DimProduct (dim_products)
  PK:   id (cuid) — composite pattern: "prod_{clientId}_{product_id}"
  FK:   referenced by FactSale.dimProductId, FactInventory.dimProductId
  Key fields: productId, name, category, family, barcode

DimSupplier (dim_suppliers)
  PK:   id (cuid) — composite pattern: "supp_{clientId}_{supplier_id}"
  Key fields: supplierId, name, contact, phone, email

DimTime (dim_time)
  PK:   id (integer — YYYYMMDD format)
  UQ:   date
  FK:   referenced by FactSale, FactInventory, FactAppointment,
        FactKitchenOrder
  Key fields: date, year, quarter, month, day, dayOfWeek, isWeekend

4.2 Facts
----------

FactSale (fact_sales)
  PK:   id (cuid)
  UQ:   [exportId, saleId]
  FK:   dimClientId → DimClient.id
        dimProductId → DimProduct.id
        dimTimeId → DimTime.id
  Measures: total, tax, discount
  Dimensions: paymentMethod

FactInventory (fact_inventory)
  PK:   id (cuid)
  UQ:   [exportId, rowIndex]
  FK:   dimProductId → DimProduct.id
        dimTimeId → DimTime.id
  Measures: stock, price, timesSold

FactAppointment (fact_appointments)
  PK:   id (cuid)
  UQ:   [exportId, rowIndex]
  FK:   dimTimeId → DimTime.id
  Measures: duration
  Dimensions: customerName, customerPhone, serviceId, status

FactKitchenOrder (fact_kitchen_orders)
  PK:   id (cuid)
  UQ:   [exportId, rowIndex]
  FK:   dimTimeId → DimTime.id
  Measures: tableNumber
  Dimensions: items, priority, status

4.3 Relationship Diagram
-------------------------

DimClient ──┐
            │
DimProduct ──┼── FactSale
            │     (dimClientId, dimProductId, dimTimeId)
DimTime ────┘
  │
  ├── FactInventory (dimProductId, dimTimeId)
  ├── FactAppointment (dimTimeId)
  └── FactKitchenOrder (dimTimeId)

Missing links:
  - FactInventory does NOT link to DimClient (but has tenantId column)
  - FactAppointment does NOT link to DimClient (but has tenantId column)
  - FactKitchenOrder does NOT link to DimClient (but has tenantId column)
  - No DimCustomer table exists (customers.csv data is NOT loaded into warehouse)
  - FactSale does NOT link to DimProduct (dimProductId always null — the ETL
    does not populate it because sales.csv has no product-level detail;
    the sale_items table is not exported)

4.4 Tenant Isolation
---------------------
All warehouse tables have a tenantId column (String). Every query in
WarehouseService filters by tenantId. DimClient has a unique constraint on
tenantId ensuring one tenant record per client.

4.5 Business-Type Separation
------------------------------
The warehouse stores all business types in the same tables, differentiated
by the businessType field in DimClient and metadata. Query-time filtering
is done in getDashboardSummary() which conditionally calls restaurant/cafe
vs pharmacy/retail vs pharmacy-specific queries.

PART 9 — FINAL VERDICT
================================================================================

9.1 Is the BI architecture technically sound?
ANSWER: YES — with caveats

Strengths:
  ✓ End-to-end data pipeline exists from POS SQLite to warehouse
  ✓ Star schema design (dimensions + facts) suitable for OLAP
  ✓ Tenant isolation via tenantId column on all tables
  ✓ Idempotent ETL (upserts by composite keys)
  ✓ SHA-256 deduplication prevents duplicate processing
  ✓ Schema versioning prevents incompatible data ingestion
  ✓ Validation layer catches bad data before warehouse load
  ✓ Cancel/delete operations clean up completely (CASCADE)
  ✓ Business-type aware query dispatch

Weaknesses:
  ✗ Broken FKs: FactSale.dimProductId always null
  ✗ Broken FKs: FactSale.dimClientId always null
  ✗ Missing FK: FactInventory/Appointment/KitchenOrder → DimClient
  ✗ No DimCustomer: customer data exported but never loaded
  ✗ No line-item data: sale-level only, no product-level revenue
  ✗ Client-side aggregation: all warehouse queries load into memory

9.2 Is the ETL architecture sound?
ANSWER: YES — well-structured with clear steps

Strengths:
  ✓ 6-step pipeline with logging at each step
  ✓ Prisma $transaction for atomicity
  ✓ Upsert pattern prevents duplicate data
  ✓ Schema version enforcement prevents incompatible imports
  ✓ Proper error handling (FAILED status, error messages)
  ✓ Temp directory cleanup in finally block
  ✓ Debug mode with validation report

Weaknesses:
  ✗ Synchronous ZIP extraction (blocks event loop)
  ✗ Row-by-row inserts (slow for large datasets)
  ✗ No batch/streaming for large CSV files
  ✗ No ETL progress reporting (all-or-nothing)
  ✗ Fire-and-forget ETL call (promise lost on server restart)
  ✗ Retry endpoint exists but is not discoverable from UI

9.3 Is the warehouse architecture sound?
ANSWER: MOSTLY — but with notable gaps

Strengths:
  ✓ Standard star schema (works well with Metabase)
  ✓ Unique composite keys for idempotent re-import
  ✓ Time dimension with pre-computed attributes
  ✓ Business type stored in DimClient for routing
  ✓ All tables have tenantId for isolation
  ✓ Migration history tracked in Prisma

Weaknesses:
  ✗ No DimCustomer (critical for analytics)
  ✗ No FactSale.dimProductId linkage
  ✗ No FactSale.dimClientId linkage
  ✗ Missing FKs between DimClient and most fact tables
  ✗ FactInventory has no date/snapshot dimension
  ✗ No indexing beyond unique constraints and PKs
  ✗ No materialized views for common queries
  ✗ No aggregation tables for pre-computed metrics

9.4 Is the dashboard layer complete?
ANSWER: NO — 0% complete

There are ZERO warehouse-powered dashboards in the application. The admin
Dashboard.jsx shows mock data. BiUploadPortal.jsx is ETL management, not
analytics. The user's plan to use Metabase is correct — the warehouse schema
is designed for Metabase compatibility. But:
  - No Metabase instance is running
  - No dashboards have been created in Metabase
  - No embedding/integration exists between the app and Metabase
  - No automated dashboard provisioning per client/tenant
  - No client-facing analytics views

ANSWER: 40%

Breakdown:
  ├── POS Export Layer:      85% (mostly complete, missing sale_items)
  ├── Upload Pipeline:       90% (upload, validate, dedup, retry — robust)
  ├── ETL Pipeline:          80% (works well, but row-by-row, sync extract)
  ├── Warehouse Schema:      60% (good star schema, broken FKs, missing dims)
  ├── Query/Analytics Layer: 40% (exists as warehouse-service, no real dashboards)
  ├── Dashboard Layer:        0% (Metabase not connected, no embedded views)
  └── Client Delivery:       10% (BiExportDeploy works, no analytics shown)

The pipeline works. Data flows. But the final mile — converting warehouse
