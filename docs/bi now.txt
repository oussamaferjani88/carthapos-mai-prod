================================================================================
1.  OVERVIEW
================================================================================

The CarthaPOS BI module is a complete business intelligence pipeline that:
  - Accepts ZIP file exports from POS terminals (containing CSV data)
  - Validates and processes those files through an ETL pipeline
  - Loads cleaned data into a PostgreSQL warehouse (dimension + fact tables)
  - Creates dashboard records that are linked to Metabase Community Edition
  - Provides an admin workflow for managing BI requests, uploads, and dashboards
  - Provides a client portal for viewing published dashboards

The BI module is built in 4 phases across backend, admin frontend, and client frontend.
The latest phase (Phase 4) replaced custom React/Recharts dashboard generation with
a Metabase Community Edition association model.

2.  ARCHITECTURE
================================================================================

2.1 High-Level Flow

POS Export (ZIP/CSV)
       |
       v
  [BiRequest] -- Client submits a BI request (pending review)
       |
       v
  [Review & Approve] -- Admin reviews & approves/rejects the request
       |
       v
  [BiUpload] -- Client uploads ZIP file (linked to approved request)
       |
       v
  [ETL Pipeline] -- Validates, extracts, transforms, loads into warehouse
       |
       v
  [Warehouse DB] -- PostgreSQL (dim_* + fact_* tables, tenant-isolated)
       |
       v
  [Dashboard Generation] -- Admin creates dashboard:
       |   - Looks up BiDashboardTemplate registry
       |   - Associates Metabase dashboard ID with BiDashboard record
       |   - Sets status = DRAFT
       v
  [DRAFT] --> [IN_PROGRESS] --> [READY_FOR_REVIEW] --> [PUBLISHED]
       |              |                  |                    |
       v              v                  v                    v
  [Admin customizes  |  [BI specialist  |  [Admin reviews   |  [Client can view]
   in Metabase]      |   edits in MB]   |   & publishes]   |   dashboard]

2.2 Multi-Tenant Isolation

Every warehouse record carries a tenantId field set to the client's ID.
Dashboard generation respects this via the clientId on the BiUpload.
Metabase Community Edition does NOT have built-in row-level security, so
tenant isolation relies on database-level filtering (all queries include
WHERE tenantId = 'client_id').

4.  DATABASE / PRISMA MODELS
================================================================================

The Prisma schema (schema.prisma) currently defines 2 BI models:

  BiDashboard
    - id (String, cuid, PK)
    - clientId (String) -- FK to Client
    - licenseId (String?) -- FK to License
    - uploadId (String?) -- FK to BiUpload
    - businessType (String) -- restaurant, cafe, retail, pharmacy, salon
    - name (String)
    - description (String?)
    - status (String, default: "DRAFT") -- GENERATING, DRAFT, IN_PROGRESS, READY_FOR_REVIEW, PUBLISHED, ARCHIVED, FAILED
    - dashboardType (String, default: "custom") -- custom | metabase
    - dashboardConfig (Json?) -- Legacy dashboard configuration (backward compat)
    - generationSteps (Json?) -- Legacy generation progress steps (backward compat)
    - metabaseDashboardId (Int?) -- [NEW] Associated Metabase dashboard ID
    - createdBy (String?)
    - assignedAt (DateTime?)
    - createdAt (DateTime)
    - updatedAt (DateTime)
    - Relations: client, license, upload, notifications

  BiDashboardTemplate
    - id (String, cuid, PK)      -- [NEW MODEL]
    - businessType (String, UNIQUE) -- restaurant, cafe, retail, pharmacy, salon
    - metabaseDashboardId (Int)   -- Metabase internal dashboard ID
    - name (String)               -- Display name
    - description (String?)
    - active (Boolean, default: true)
    - createdAt (DateTime)
    - updatedAt (DateTime)

Additional BI models exist in the database (created via earlier migrations but
not currently defined in the Prisma schema file):

  BiUpload
    - id, clientId, requestId, filePath, fileName, fileHash, fileSize,
      businessType, status, errorMessage, totalRows, createdAt, updatedAt
    - Relations: biRequest, processingJob, dashboards

  BiRequest
    - id, clientId, licenseId, businessType, businessName, message,
      status (PENDING_REVIEW/APPROVED/REJECTED/REQUEST_INFO),
      paymentStatus (PENDING/VERIFIED/REJECTED),
      paymentMethod, paymentDate, reviewedBy, reviewedAt, createdAt, updatedAt
    - Relations: client, license, uploads, notifications

  BiAnalysisRequest
    - id, clientId, uploadId, businessType, status, insights,
      createdAt, updatedAt
    - Relations: upload

  BiNotification
    - id, clientId, dashboardId, type, title, message, isRead,
      createdAt, updatedAt
    - Relations: dashboard

  BiProcessingJob
    - id, uploadId, status, startedAt, completedAt, recordsLoaded,
      errorMessage, createdAt, updatedAt

  BiProcessingLog
    - id, jobId, level, step, message, createdAt

Warehouse tables (dimensions + facts):

  dim_time         -- Date dimension (id as YYYYMMDD, year, quarter, month, day, dayOfWeek, isWeekend)
  dim_client       -- Client dimension (tenantId, name, businessType, exportId)
  dim_product      -- Product dimension (tenantId, productId, name, category, family, barcode)
  dim_supplier     -- Supplier dimension (tenantId, supplierId, name, contact, phone, email)
  fact_sale        -- Sales fact (tenantId, saleId, total, tax, discount, paymentMethod, dimTimeId)
  fact_inventory   -- Inventory fact (tenantId, productName, stock, price, timesSold)
  fact_appointment -- Appointment fact (tenantId, customerName, serviceId, duration, status)
  fact_kitchen_order -- Kitchen order fact (tenantId, tableNumber, items, priority, status)

All warehouse tables use tenantId for multi-tenant isolation and have indexes
on tenantId for query performance.

6.  BACKEND SERVICES
================================================================================

6.1 etl-pipeline.js (613 lines)

The core ETL engine. Processes ZIP uploads into the warehouse.

Steps:
  1. Extract ZIP to temp directory (unzip or adm-zip fallback)
  2. Read metadata.json (client_id, business_type, schema_version)
  3. Override clientId with upload.clientId (fixes tenantId mismatch)
  4. Validate schema version against bi-schema-registry.js
  5. Validate all CSV datasets (required + optional)
  6. DB transaction:
     a. Create/update BiProcessingJob
     b. Load dimension tables (time, client, product, supplier)
     c. Load fact tables (sale, inventory, appointment, kitchen_order)
     d. Mark job + upload as COMPLETED
     e. Auto-create BiAnalysisRequest (non-fatal)
  7. On failure: mark upload FAILED, log error

6.2 warehouse-service.js (258 lines)

Query service providing pre-computed analytics. All methods are tenant-isolated.

Methods:
  - getRevenueByDay(tenantId, days, timezone)
  - getTopProducts(tenantId, limit)
  - getInventoryTurnover(tenantId)
  - getTableTurnover(tenantId)
  - getKitchenPerformance(tenantId, days)
  - getAppointmentSummary(tenantId)
  - getSupplierPerformance(tenantId)
  - getPeakHours(tenantId, timezone)
  - getAverageTicket(tenantId, days)
  - getDashboardSummary(tenantId, businessType, timezone) -- composite

6.3 bi-dashboard-templates.js (92 lines) -- [DEPRECATED]

Legacy JS template definitions for React/Recharts dashboard generation.
Kept for backward compatibility. The new source of truth is Metabase.

6.4 bi-schema-registry.js (236 lines)

Schema validation: defines expected CSV columns, types, and required datasets
for ETL import. Version-locked (BI_SCHEMA_VERSION = '1.0.0').

6.5 bi-insight-generator.js (117 lines)

Generates human-readable text insights from warehouse data:
revenue summaries, top products, inventory alerts, appointment trends.

9.  ETL PIPELINE (DETAILED)
================================================================================

9.1 Trigger

Manual only: POST /api/bi-uploads/:id/start-etl
Prerequisites:
  - Upload must have linked BiRequest with status = APPROVED
  - Upload must not already be COMPLETED or PROCESSING

9.2 Input Format

ZIP file containing:
  - metadata.json (client_id, business_type, bi_schema_version, enabled_modules)
  - sales.csv (required)
  - products.csv (required)
  - inventory.csv (required)
  - suppliers.csv (optional)
  - appointments.csv (optional)
  - kitchen_orders.csv (optional)

9.3 Processing Steps

Step 1 - Extract: Copies ZIP to temp dir, extracts via unix unzip or adm-zip fallback
Step 2 - Metadata: Reads metadata.json, overrides clientId with upload.clientId
Step 3 - Schema Check: Validates bi_schema_version against server registry
Step 4 - Validate: Checks all CSVs (columns, types, duplicates)
Step 5 - DB Transaction:
  5a - Create/update BiProcessingJob (status = PROCESSING)
  5b - Load dimensions: dim_time (unique dates), dim_client (upsert by tenantId),
       dim_product (composite PK), dim_supplier (composite PK)
  5c - Load facts: fact_sale, fact_inventory, fact_appointment, fact_kitchen_order
  5d - Mark job COMPLETED + upload COMPLETED
  5e - Auto-create BiAnalysisRequest (non-fatal on failure)
Step 6 - Cleanup: Delete temp directory (always runs in finally block)

9.4 Error Handling

  - Step tracking via 'step' variable, updated before each stage
  - On failure: upload set to FAILED with step prefix in errorMessage
  - BiProcessingJob also marked FAILED
  - Individual row P2002 (duplicate) errors caught and skipped per fact table
  - AnalysisRequest creation failure is non-fatal (logged only)

9.5 Tenant Isolation

  - All warehouse INSERTs use metadata.clientId (overridden with upload.clientId)
  - dim_client upserts by tenantId
  - All dimension/fact rows include tenantId column

10.  METABASE INTEGRATION
================================================================================

10.1 Architecture Decision

The BI module migrated from custom React/Recharts dashboard generation to a
Metabase Community Edition association model. The key decisions:

  NO:  Programmatic dashboard creation in Metabase (CE API doesn't support it)
  NO:  Direct SQL inserts into Metabase internal tables (unsupported)
  NO:  Automatic Metabase configuration
  YES: BI specialist manually creates dashboards in Metabase UI
  YES: BiDashboardTemplate registry stores businessType -> metabaseDashboardId
  YES: generate-from-upload looks up registry and associates the MB ID
  YES: "Open in Metabase" button links from CarthaPOS admin to MB dashboard

10.2 Current State

  - Metabase CE is installed at metabase/metabase.jar
  - Metabase uses its own PostgreSQL database ('metabase')
  - Metabase is configured with MB_PORT=3000, separate from CarthaPOS (3001)
  - start-metabase.bat starts Metabase with JDK 21
  - No dashboards have been created in Metabase yet (BI specialist task)

10.3 Template Registry

  - BiDashboardTemplate model stores: businessType, metabaseDashboardId, name
  - CRUD API at /api/bi/dashboard-templates
  - Admin UI in the Dashboard Templates modal from AdminBIDashboardManager
  - Active flag allows enabling/disabling templates without deletion
  - Dashboard generation auto-resolves template by businessType

10.4 Configuration Required

  Environment variables in backend/.env:
    - METABASE_BASE_URL=http://localhost:3000
    - METABASE_DASHBOARD_COLLECTION=1

  Manual steps needed (BI specialist):
    1. Start Metabase (start-metabase.bat)
    2. Complete Metabase setup wizard at http://localhost:3000
    3. Add PostgreSQL warehouse as data source:
       - Host: localhost, Port: 5432, DB: pos_system
       - User: metabase_reader (read-only, to be created)
    4. Create dashboard templates in Metabase for each business type
    5. Register each template in CarthaPOS via Dashboard Templates modal

10.5 Client Viewing

  The client portal (BIDashboardViewer.tsx) still uses legacy React rendering.
  The metabaseDashboardId is now stored on each BiDashboard record, ready for
  a future phase where the backend proxies Metabase API data to the React client.

11.  WORKFLOW SUMMARY
================================================================================

11.1 Complete Client Journey

  1. Client submits BI request (POST /api/bi-requests)
  2. Admin reviews and approves (POST /api/bi-requests/:id/approve)
  3. Client uploads ZIP file (POST /api/bi-uploads with requestId)
  4. Admin triggers ETL (POST /api/bi-uploads/:id/start-etl)
  5. ETL validates and loads data into warehouse
  6. Admin creates dashboard (POST /api/bi/dashboards/generate-from-upload)
  7. System looks up BiDashboardTemplate from registry
  8. BiDashboard created with metabaseDashboardId + status = DRAFT
  9. Admin opens dashboard in Metabase to customize (if needed)
  10. Admin sets status = IN_PROGRESS (editing)
  11. Admin sets status = READY_FOR_REVIEW
  12. Admin reviews and sets status = PUBLISHED
  13. Client sees dashboard in their portal (visible in BIDashboardViewer)

11.2 Status Transition Map

  GENERATING -> DRAFT (legacy only)
  DRAFT -> IN_PROGRESS
  IN_PROGRESS -> READY_FOR_REVIEW
  READY_FOR_REVIEW -> PUBLISHED | DRAFT
  PUBLISHED -> ARCHIVED
  ARCHIVED -> DRAFT
  (any) -> FAILED

13.  CURRENT STATUS & KNOWN ISSUES
================================================================================

13.1 What Works

  - Full ETL pipeline (ZIP -> warehouse), tested with 25 records in 0.2s
  - BI request creation + payment + approval/rejection workflow
  - Manual ETL trigger with progress tracking (polling + logs)
  - Dashboard generation (looks up template registry, creates BiDashboard)
  - Dashboard status workflow (DRAFT -> ... -> PUBLISHED)
  - Notifications (DASHBOARD_GENERATED, DASHBOARD_READY)
  - BiAnalysisRequest auto-creation after ETL
  - Admin quick approve for walk-in clients
  - Tenant isolation via tenantId on warehouse records
  - Metabase template registry CRUD (API + admin UI)
  - "Open in Metabase" links from admin dashboard manager
  - Legacy React/Recharts rendering (backward compat)
  - Simplified admin dashboard viewer (no chart rendering)

13.2 Known Issues

  1. Prisma schema is incomplete for older BI models
     - BiUpload, BiRequest, BiAnalysisRequest, BiNotification, BiProcessingJob,
       and BiProcessingLog models exist in the database but are not defined in
       the current schema.prisma file. Running prisma db push would drop them.
     - Workaround: use raw SQL for schema changes; prisma db push is not safe
     - Fix: add all BI models to schema.prisma

  2. Prisma schema has zone.tab file error
     - Running prisma db push fails with a zone.tab error
     - Workaround: apply schema changes via raw SQL in psql
     - Affects: adding new columns/models requires manual SQL

  3. DB unique constraints missing
     - The database lacks unique constraints defined in Prisma schema
     - ETL pipeline uses findFirst + create/update instead of upsert
     - Affects: potential duplicate rows if ETL re-runs

  4. Metabase dashboards not yet created
     - Template registry exists but no Metabase dashboards exist yet
     - Manual step: BI specialist must create dashboards in Metabase UI
     - Until then, generate-from-upload creates BiDashboard without MB link

  5. Client portal still uses legacy React rendering
     - BIDashboardViewer.tsx renders from dashboardConfig JSON
     - metabaseDashboardId is stored but not yet used for client display
     - Future: implement Metabase API proxy for client card data

  6. JWT authentication is disabled
     - All routes are publicly accessible
     - auth middleware exists but is commented out in server.js
     - Must be re-enabled before production

  7. No read-only database user for Metabase yet
     - Metabase currently connects as 'postgres' superuser
     - Should use metabase_reader with SELECT-only grants

  8. No per-tenant PostgreSQL schemas for Metabase
     - Metabase CE has no row-level security
     - Per-tenant views/schemas would be needed for production isolation
     - Current setup works because all queries filter by tenantId

13.3 Deprecated Code

  - backend/services/bi-dashboard-templates.js: Legacy JS templates, kept for
    backward compatibility. New dashboards no longer use it.
  - dashboardConfig JSON on BiDashboard: Legacy config storage. New dashboards
    set it to {} but still populate the field.
  - generationSteps JSON on BiDashboard: Legacy generation progress. New
    dashboard generation is synchronous (no background process).
  - AdminDashboardViewer chart rendering: Removed. Now just shows dashboard info.
  - Chart components (DashboardLineChart, DashboardBarChart, DashboardPieChart):
    Kept for backward compat in BIDashboardViewer (client portal).
