1. MULTI-TENANT ANALYSIS
================================================================================

1.1 How is tenantId determined?
─────────────────────────────────

  SOURCE 1 — bi-uploads.js (line 59):
    const { clientId, businessType } = req.body;
    The clientId is sent by the caller in the POST body when uploading a ZIP.

  SOURCE 2 — etl-pipeline.js (line 214):
    clientId: raw.client_id || 'unknown',
    The clientId is also extracted from metadata.json inside the ZIP file
    (field: "client_id"). This is the authoritative source during ETL.

  VALIDATION:
    bi-uploads.js lines 68-76: clientId is validated against the Client table
    in PostgreSQL. If the clientId doesn't match any existing Client record,
    the upload is rejected with 400.

  FILES:
    - backend/routes/bi-uploads.js (lines 59, 68-76)
    - backend/services/etl-pipeline.js (lines 44-48, 214)

1.2 How is tenantId stored?
────────────────────────────

  In the BiUpload table:
    model BiUpload {
      clientId  String  ← stored directly (NOT a FK, no @relation)
      ...
    }

  In the Warehouse tables (every fact and dimension has tenantId):
    DimClient:   tenantId  String  @unique
    DimProduct:  tenantId  String
    DimSupplier: tenantId  String
    FactSale:    tenantId  String
    FactInventory:    tenantId  String
    FactAppointment:  tenantId  String
    FactKitchenOrder: tenantId  String

  DimTime is the ONLY table without tenantId (global calendar).

  FILES:
    - backend/prisma/schema.prisma (all Dim* and Fact* models)

1.3 Does every warehouse table use tenantId?
─────────────────────────────────────────────

  Table              Has tenantId?   Filtered by tenantId in queries?
  ─────────────────  ──────────────  ─────────────────────────────────
  DimClient          YES (@unique)   YES (warehouse-service.js)
  DimProduct         YES             YES
  DimSupplier        YES             YES
  DimTime            NO              N/A (global calendar table)
  FactSale           YES             YES (all methods in warehouse-service.js)
  FactInventory      YES             YES
  FactAppointment    YES             YES
  FactKitchenOrder   YES             YES

  ALL warehouse queries in warehouse-service.js filter by tenantId.
  ALL SQL views (10 views) expose client_id from tenantId.

1.4 Risk of cross-client data leakage?
────────────────────────────────────────

  RISK LEVEL: LOW for warehouse queries, MEDIUM for upload acceptance

  PROTECTIONS IN PLACE:
    ✓ warehouse-service.js: Every public method takes tenantId as first param
    ✓ SQL views: All views include client_id column for Metabase filtering
    ✓ ETL: tenantId is consistently set from metadata.client_id
    ✓ DimClient: tenantId is @unique → one dim client per tenant

  GAPS:
    ✗ BiUpload.clientId is a plain String, not a FK to Client model
      → Can store orphan clientIds if Client record is deleted
    ✗ No auth middleware on bi-uploads POST
      → Anyone who can reach the endpoint can upload under any clientId
      → The validation just checks that the Client exists, not that the
        caller owns that client
    ✗ No auth middleware on bi-uploads GET
      → With no auth, any caller can list all uploads for any clientId
    ✗ bi-requests.js: licenseId is stored but not validated against License table
      → JSON-file store, no referential integrity at all

  RECOMMENDATIONS:
    1. Add @relation to BiUpload.clientId → Client.id
    2. Add auth middleware checking caller has access to the specified clientId
    3. Migrate bi-requests to PostgreSQL with proper FKs (Phase 1)
    4. Add tenant isolation to the GET /api/bi-uploads endpoint

4. EMBEDDING ANALYSIS (Metabase OSS)
================================================================================

4.1 Can we display a Metabase dashboard in our React frontend?
───────────────────────────────────────────────────────────────

  YES, with severe limitations:

  OPTION A: Public Sharing (OSS)
    - Metabase OSS allows "public sharing" of dashboards/questions
    - Generates a public UUID URL (e.g., /public/dashboard/abc123)
    - Anyone with the URL can view the dashboard
    - NO authentication required
    - NO session/cookie validation
    - If URL leaks, data is exposed

  OPTION B: Embedding via iframe
    - Same as public sharing, just wrapped in an iframe
    - No auth, no tenant filtering

  OPTION C: Signed Embedding (JWT)
    - Requires Enterprise license (paid)
    - Allows authentication and parameter passthrough
    - NOT AVAILABLE in OSS

  FILE: Metabase pricing/feature comparison (official docs)

4.2 Can we filter automatically by tenantId?
──────────────────────────────────────────────

  NO in OSS embedding mode:
    - Public dashboards show ALL data (no row-level restriction)
    - Parameters in public dashboards are visible in the URL and
      can be tampered with by the client
    - No server-side filtering without Enterprise

  POSSIBLE WORKAROUND (not recommended):
    - Create one Metabase dashboard per client (not scalable)
    - Use locked parameters with default values (still visible in URL)
    - Metabase "collections" + permissions requires Enterprise

4.3 Can we secure this without Enterprise license?
────────────────────────────────────────────────────

  NO. OSS embedding has no security mechanism:
    - No user authentication on public links
    - No session validation
    - No parameter signing
    - No CORS restrictions on public endpoints
    - Rate limiting only (not auth)

4.4 Exact limitations of Metabase OSS embedding
──────────────────────────────────────────────────

  ✓ What OSS CAN do:
    - Public dashboard sharing (unauthenticated)
    - Self-service analytics within Metabase UI
    - Dashboard subscriptions (email) — within Metabase itself
    - SQL queries and native query builder
    - API access (admin key required, not suitable for client-facing)

  ✗ What OSS CANNOT do:
    - Signed embedding (JWT) → Enterprise only
    - Row-level security / data sandboxing → Enterprise only
    - User-specific dashboard filtering → Enterprise only
    - SSO / SAML / OAuth integration → Enterprise only
    - Advanced permissions → Enterprise only
    - Audit logs → Enterprise only
    - Content moderation → Enterprise only
    - White labeling → Enterprise only

4.5 Conclusion
───────────────
  Metabase OSS embedding is NOT suitable for multi-tenant client-facing
  dashboards. The architecture decision to build a custom dashboard viewer
  (Chart.js/Recharts) inside the existing React client app is CONFIRMED
  as the correct approach.

  Metabase remains useful ONLY as an internal admin tool for:
    - Ad-hoc querying
    - Data exploration
    - Internal analytics (not client-facing)
    - Admin dashboard creation

  FOR CLIENT-FACING DASHBOARDS:
    - Use warehouse-service.js as the API
    - Custom React components with Recharts (already installed)
    - Tenant isolation handled server-side by warehouse-service.js

6.2 Required SQL schema
─────────────────────────

  Below is the exact schema needed (PostgreSQL / Prisma format):

  ────────────────────────────────────────────────────────────────────
  model BiDashboard {
    id          String   @id @default(cuid())
    name        String
    description String?
    businessType String  // restaurant, pharmacy, retail, salon, cafe
    source      String   @default("metabase")  // "metabase" or "custom"
    metabaseId  String?  // Metabase dashboard ID (nullable for custom)
    config      Json?    // Dashboard layout config for custom viewer
    isTemplate  Boolean  @default(false)
    createdAt   DateTime @default(now())
    updatedAt   DateTime @updatedAt

    assignments BiDashboardAssignment[]

    @@map("bi_dashboards")
  }

  model BiDashboardAssignment {
    id          String     @id @default(cuid())
    dashboardId String
    clientId    String
    licenseId   String?
    status      String     @default("ACTIVE")  // ACTIVE, ARCHIVED
    assignedAt  DateTime   @default(now())

    dashboard   BiDashboard @relation(fields: [dashboardId], references: [id], onDelete: Cascade)
    client      Client      @relation(fields: [clientId], references: [id], onDelete: Cascade)
    license     License?    @relation(fields: [licenseId], references: [id])

    @@unique([dashboardId, clientId])
    @@map("bi_dashboard_assignments")
  }

  model BiNotification {
    id          String   @id @default(cuid())
    clientId    String?
    licenseId   String?
    type        String   // "UPLOAD_COMPLETED", "UPLOAD_FAILED",
                         // "DASHBOARD_READY", "DASHBOARD_UPDATED"
    title       String
    message     String
    link        String?  // URL to relevant resource
    isRead      Boolean  @default(false)
    createdAt   DateTime @default(now())

    @@map("bi_notifications")
  }
  ────────────────────────────────────────────────────────────────────

  For Metabase-backed dashboards:
    - BiDashboard.metabaseId stores the dashboard ID from Metabase

    - Admin enters the Metabase dashboard ID in the admin panel
    - The assignment links the Metabase dashboard to a client

  For custom (non-Metabase) dashboards:
    - BiDashboard.config stores React component configuration

8.5 Architecture decision summary
───────────────────────────────────

  DECISION 1: Metabase usage
    Metabase is used ONLY as an internal admin tool for ad-hoc querying
    and data exploration. It is NOT used for client-facing dashboards.

  DECISION 2: Client-facing dashboards
    Custom React components using Recharts (already installed).
    Data served by warehouse-service.js via a dedicated API endpoint.
    Full tenant isolation at the database query level.

  DECISION 3: Dashboard storage
    Two modes:
      a) Metabase-linked: Admin creates in Metabase, records ID in
         bi_dashboards.metabaseId. Admin-only view in Metabase.
      b) Custom (client-facing): Config stored in bi_dashboards.config.
         Rendered in client portal using Recharts components.

  DECISION 4: Template system
    5 business templates (restaurant, pharmacy, retail, salon, cafe).
    Each template is a JSON config of which charts to show.
    Templates can be cloned and assigned to multiple clients.

  DECISION 5: Notification
    Hybrid approach:
      - In-app notifications via BiNotification table + polling API
      - Email notifications via Resend/Nodemailer for critical events
        (dashboard assigned, upload failed)

  DECISION 6: Multi-tenant isolation
    All warehouse queries filter by tenantId server-side.
    Auth middleware validates that caller has access to the requested tenant.
    BiUpload.clientId needs FK constraint to Client.
