BI ANALYTICS PLATFORM - IMPLEMENTATION REPORT
==============================================

Date: 2026-08-02
Scope: Hybrid Analytics Cache Architecture (enrichment cache + REST API + admin workspace)


1. ARCHITECTURE (approved plan)
-------------------------------
The analytics platform uses a hybrid approach:
  - Warehouse (Prisma, frozen/sealed) = official truth for aggregates
  - Enrichment cache service = single owner of ZIP access, loads granular
    datasets absent from the warehouse (sale_items, customers, products,
    kitchen orders, shifts, tables, reservations, z_reports, cash drawer)
  - Analytics API = additive REST endpoints combining warehouse + cache
  - Admin workspace = French UI with KPI cards, charts, filters, tabs, insights

ETL / upload wizard / warehouse remain frozen. All changes are additive.


2. WHAT WAS DONE (Step 1: enrichment cache service)
---------------------------------------------------
File: backend/services/analytics-cache-service.js

  - Reads the latest COMPLETED upload ZIP in backend/uploads/bi-zips/
  - Extracts CSVs purely in Node via adm-zip (single owner of ZIP access;
    no external unzip), reusing BiSchemaRegistry.parseCsvRow
  - Handles UTF-8 BOM on the first column (via trim / parseCsvRow)
  - Builds a JSON cache at backend/analytics-cache/<uploadId>.json plus a
    meta.json mapping clientId -> uploadId
  - Rebuilds only when the uploadId changes, the file is missing, or a
    force refresh is requested (POST /refresh)
  - In-memory LRU (max 32 clients) on top of the disk cache

3. WHAT WAS DONE (Step 2: analytics API)
----------------------------------------
File: backend/routes/bi-analytics.js
Mounted at: /api/bi/analytics (additive require + app.use in server.js,
            inserted between bi-analysis and bi-reviews)

  Endpoints (all verified HTTP 200 on real data):
    GET  /overview      - KPIs (revenue, orders, ticket moyen, clients actifs,
                          articles vendus, paiements) with change vs previous period
    GET  /trend         - revenue/orders per day or month (groupBy=day|month)
    GET  /payment-mix   - by payment method + byHour + byHourPerMethod
    GET  /weekday       - revenue/orders by day of week
    GET  /peak-hours    - orders by hour of day
    GET  /categories    - revenue by category
    GET  /products      - top products (sort revenue|units|profit|orders)
    GET  /customers     - top customers (sort revenue|orders|points)
    GET  /employees     - revenue per employee + byDate
    GET  /tables        - performance + reservations + utilization
    GET  /kitchen       - status / priority / departments / timings / cancelled
    GET  /inventory     - warehouse truth + reorder thresholds (minStock)
    GET  /shifts        - cash drawer closings
    GET  /reservations  - by status / by date
    GET  /insights      - 9 auto-generated recommendations
    GET  /filters       - available filter values + date range
    GET  /status        - cache status (builtAt, reason MEMORY|DISK)
    POST /refresh       - force rebuild of the cache
    GET  /drilldown     - per-sale / per-product / per-customer / per-employee
                          detail (Step 4, see section 6)

  Key implementation notes:
    - Warehouse date math always uses dimTimeId (never createdAt)
    - Product id derived as dimProductId.split('_').pop()
    - Response envelope: { success: true, data: {...} }
    - Errors: 400 "clientId is required", 500 on failure

6. REMAINING GAP (known, not blocking)
--------------------------------------
  Global filters in the filter bar are currently INERT.

  The workspace renders three filter selects (Catégorie / Employé / Paiement)
  and forwards their values as query parameters (category, employee,
  paymentMethod) to the analytics endpoints, but the backend parseQuery()
  only consumes clientId / from / to / limit / sort / groupBy. As a result:

    - Selecting a category / employee / payment method changes the URL
      parameters but does not change the numbers shown.
    - No server-side filtering happens on the cache aggregates (sales and
      sale_items are aggregated without any filter conditions).

  Options to close the gap:
    a) Implement server-side filtering in bi-analytics.js: accept category,
       employee, paymentMethod on the endpoints that aggregate sales /
       sale_items (overview, trend, payment-mix, products, customers,
       employees, drilldown, ...) and filter the cache records before
       aggregation. Most correct; touches several endpoints.
    b) Restrict the global filter to the endpoints where it is cheap to add
       (e.g. products, employees, drilldown) and label the controls as
       scoped to those tabs.
    c) Remove the three selects until the filtering is implemented (avoids
       showing controls that do nothing).

  Recommendation: option (a).

  Minor known limitation (non-blocking): the currency shown in charts falls
  back to "TND" because the clients list endpoint does not return a currency
  field per client; the warehouse metadata does contain currency (TND).
