SECTION 3 -- VERIFIED CARTH APOS PRODUCT DESCRIPTION
================================================================================

WHAT CARTH APOS IS (from repository evidence):
  A multi-tenant SaaS platform for generating customized desktop POS
  applications for small businesses in Tunisia. It combines:
  - A web-based administration platform (admin + client frontends)
  - A backend API with PostgreSQL
  - An Electron POS template that gets customized per-client
  - A BI/ETL pipeline with Metabase dashboards

WHO USES IT:
  - CarthaPOS administrators/staff (internal team)
  - Business owner clients (Tunisian small businesses)
  - POS operators/cashiers (end users of generated POS)

TARGET BUSINESSES:
  6 sectors: restaurant, cafe, retail, bakery, pharmacy, beauty

BUSINESS MODEL (from owner description, PARTIALLY verifiable from code):
  - B2B: CarthaPOS sells to business owners
  - Clients register, configure POS, receive generated desktop application
  - POS is distributed as Windows .exe installer
  - BI is an on-demand service: client exports data, uploads, requests
    dashboard, admin processes and provisions
  - Payment is manual (cash/bank transfer) -- admin verifies externally

LICENSING MODEL (from code):
  - Two types: SUBSCRIPTION (time-limited) and LIFETIME
  - Three binding modes: MACHINE, USB, HYBRID
  - Ed25519 cryptographic signing for offline verification
  - Machine fingerprint binding + activation/transfer limits

GENERATED POS:
  - Electron desktop application (Windows NSIS installer)
  - Local SQLite database
  - React frontend with 27 page components
  - Role-based access (ADMIN, MANAGER, CASHIER, KITCHEN)
  - Sector-specific module configuration
  - BI export capability (19 datasets, CSV+ZIP)

SECTION 6 -- PLATFORM ARCHITECTURE
================================================================================

ARCHITECTURAL STYLE:
  The platform is a multi-application, multi-tenant SaaS architecture:
  - Client-server (web frontends -> backend API)
  - Multi-application (4 separate deployable applications)
  - Electron desktop (POS: IPC-based renderer/main-process split)
  - Modular backend (domain-oriented route + service groups)
  - ETL / data warehouse (BI pipeline)

  NOT a monolithic layered architecture.

APPLICATIONS:
  1. Backend API (Express.js) -- business services + BI + generation
  2. Admin Dashboard (React SPA) -- CarthaPOS staff interface
  3. Client Frontend (React SPA) -- business owner interface
  4. POS Template (Electron) -- desktop POS source template
  5. Generated Client POS -- derived from template per-client

COMMUNICATION:
  Admin + Client Frontends --HTTP--> Backend API (REST)
  Backend API --Prisma--> PostgreSQL
  Generated POS --HTTP (license check only)--> Backend API
  Generated POS --IPC (local)--> SQLite
  Metabase --SQL--> PostgreSQL
  Backend API --REST API--> GitHub API (POS build)
  Backend API --REST API--> Metabase (dashboard provisioning)

DEPLOYMENT:
  Render cloud: 3 services (2 static + 1 Docker) + 1 PostgreSQL
  Client machines: locally installed Electron .exe + SQLite

SECTION 12 -- AUTHENTICATION & AUTHORIZATION
================================================================================

PLATFORM AUTHENTICATION:
  Registration: POST /api/auth/register (creates Client + User)
  Login: POST /api/auth/login (sets HttpOnly cookie + returns token in body)
  Token: JWT (HS256), contains id, username, email, role
  Delivery: HttpOnly cookie (sameSite: lax, secure in production) AND
            response body (undermines HttpOnly security claim)
  Header: Bearer token also accepted via Authorization header
  Password: bcrypt (10 rounds)

  CAVEAT 1: /api/users/login does NOT set HttpOnly cookie
            (inconsistent with /api/auth/login)
  CAVEAT 2: Token returned in response body makes HttpOnly pointless
  CAVEAT 3: AUTH_REQUIRED env var defaults to false -- all routes unprotected
  CAVEAT 4: JWT_SECRET has hardcoded fallback: 'carthapos-secret-key-change-in-production-2025'

ADMIN AUTHENTICATION:
  Same JWT system as platform
  Additional: permission checking via middleware/permissions.js
  SUPER_ADMIN bypasses all permission checks
  SUPER_ADMIN account is frozen (cannot delete, demote, or modify structural fields)

POS AUTHENTICATION:
  Local users stored in SQLite (ElectronAuthManager, 1,184 lines)
  Passwords hashed with bcryptjs
  Roles: ADMIN, MANAGER, CASHIER, KITCHEN
  Role-based permission sets (41 POS-facing permissions)
  Offline-capable (no backend connection needed)

LICENSE SECURITY:
  Ed25519 signature verification (offline)
  Machine fingerprint binding
  USB device binding
  Activation/transfer limits
  Expiration checking

AUTHORIZATION:
  Backend: 35 permission keys across 11 modules
  Admin frontend: PermissionRoute component wraps all 17 protected routes
  POS: Role-based permission sets per user
  SUPER_ADMIN: full bypass server-side

SECURITY WEAKNESSES IDENTIFIED:
  1. Auth disabled by default (AUTH_REQUIRED=false)
  2. Hardcoded JWT fallback secret
  3. Token returned in response body (not HttpOnly-only)
  4. Rate limiters exist but NOT applied in server.js
  5. Docker runs as root with chmod 777
  6. No ZIP content path traversal validation
  7. X-User-Id header spoofable when auth disabled
  8. Two inconsistent login endpoints

SECTION 17 -- ETL PIPELINE
================================================================================

FILE: backend/services/etl-pipeline.js (~897 lines)

ETL STEPS (in order):
  1. Extract ZIP file (adm-zip)
  2. Read metadata.json (client ID from upload record, not from ZIP)
  3. Discover CSV files in archive
  4. Schema version check (must match 2.2.0)
  5. Validate CSVs (columns, types, duplicates, empty datasets)
  6. Data preparation (coercion, normalization per DATASET_RULES)
  7. Mark BiProcessingJob = PROCESSING
  8. Database transaction:
     a. Upsert dimensions (DimTime, DimClient, DimProduct, DimSupplier, DimCustomer)
     b. Upsert facts (FactSale, FactSaleItem, FactInventory,
        FactAppointment, FactKitchenOrder, FactKitchenOrderItem)
  9. Mark BiProcessingJob = COMPLETED
  10. Mark BiUpload = COMPLETED

TRANSACTION: prisma.$transaction() wraps dimension + fact loading
ROW TRACKING: Records loaded rows, skipped rows, orphaned rows
ERROR HANDLING: Marks upload and job as FAILED with failure stage

NOT IMPLEMENTED:
  - Background job queue (synchronous processing)
  - Retry mechanism
  - Rollback beyond transaction rollback
  - Deduplication of re-uploaded data (SHA-256 prevents, but no merge)

PROVISIONING BEHAVIOR:

  Each client gets independent dashboard copy
