  For isFirstTime to be true at t=9:

  → SELECT finds no active admin with role='admin' AND is_active=1
  → OR SELECT finds admin(s) but all have NULL/empty password_hash

  → The user changed the password during first-time setup

  → OR the password_update on the first launch silently FAILED

  BOTH calls use the SAME:
    - authManager object

    - SQL query: SELECT ... FROM users WHERE role='admin' AND is_active=1

  The only way to resolve: needsAdminPasswordReset() returns TRUE at t=8.


3. VERIFICATION: Does needsAdminPasswordReset() incorrectly return true?
================================================================================

  Check ElectronAuthManager.cjs:56-81:

    async needsAdminPasswordReset() {
      const user = await this.db.getRow(
        'SELECT id, password_hash FROM users WHERE username = ? AND is_active = 1',
        ['admin']
      );
      if (!user) return false;
      if (!user.password_hash || String(user.password_hash).trim() === '') return true;
      if (String(user.password_hash) === 'admin123') return true;
      const isDefault = await bcrypt.compare('admin123', user.password_hash);
      return !!isDefault;
    }

  Scenario: First launch created admin with password "mypassword" via createAdminUser.
    → password_hash = bcrypt("mypassword")
    → bcrypt.compare('admin123', bcrypt("mypassword")) → FALSE
    → returns false ✓

  Scenario: First launch went through the ALREADY EXISTS catch path:
    1. createAdminUser threw "already exists"
    2. updateAdminPassword("mypassword") called
    3. UPDATE users SET password_hash = bcrypt("mypassword") WHERE id = ?
    → password_hash = bcrypt("mypassword")
    → bcrypt.compare('admin123', bcrypt("mypassword")) → FALSE
    → returns false ✓

  Scenario: The admin was seeded with password "admin123" DURING TABLE CREATION.
    But insertDefaultData() is EMPTY (ElectronDatabaseManager.cjs:982-985).
    No seed data exists in the code.

  CONCLUSION: needsAdminPasswordReset() correctly returns FALSE.
  → isFirstTime should be FALSE.
  → SetupWizard should NOT render.

  THE CONTRADICTION REMAINS.

6. SINGLE POINT OF FAILURE
================================================================================

  The ENTIRE decision reduces to ONE line (App.jsx:159):

    setIsFirstTime(needsSetup || needsReset);

  Where:
    needsSetup  = return value of IPC channel 'needs-first-time-setup'
    needsReset  = return value of IPC channel 'needs-admin-password-reset'

  For SetupWizard to show on second launch, AT LEAST ONE must be TRUE.

  needsSetup = true  → see 6a
  needsReset = true  → see 6b


6a. If needsSetup = true:
─────────────────────
  → needsFirstTimeSetup() returned TRUE
  → Means: SELECT FROM users WHERE role='admin' AND is_active=1 returned
    empty rows, OR all returned rows have NULL/empty password_hash

  → But then createAdminUser() would NOT throw "already exists"
    because it calls the SAME needsFirstTimeSetup() which would also return TRUE.
    The user reports createAdminUser DOES throw "already exists".

  → CONTRADICTION. needsSetup CANNOT be true.

6b. If needsReset = true:
──────────────────────
  → needsAdminPasswordReset() returned TRUE
  → Means: admin user found with password_hash matching bcrypt('admin123')

  → This CAN happen if the first launch's password update silently FAILED,
    leaving the original password as bcrypt('admin123').

  → But the user says authenticate-user on the second launch SUCCEEDS
    with the password they entered. If the stored hash was bcrypt('admin123'),
    then the user MUST have entered 'admin123' — but they entered a new password.

  → OR: on the first launch, the SetupWizard went through the "already exists"
    catch path, called updateAdminPassword, which actually UPDATED the hash,
    but then authenticateUser SUCCEEDS (with the new password).

  → On second launch, hash = bcrypt(newPassword), not bcrypt('admin123').
  → needsAdminPasswordReset returns FALSE.

  → CONTRADICTION. needsReset CANNOT be true.

8. ROOT CAUSE — DEFINITIVE STATEMENT
================================================================================

  This is NOT a logic bug in the code.

  The code correctly implements:
    - If admin exists with non-empty password_hash → needsFirstTimeSetup = false
    - If password_hash is not bcrypt('admin123') → needsAdminPasswordReset = false
    - isFirstTime = needsSetup || needsReset
    - If isFirstTime is false → Login page

  The reported behavior REQUIRES one of the IPC handlers to return a VALUE
  that contradicts the database contents.

  The definitive root cause can ONLY be identified by adding console.log
  to the seven locations listed in section 7, rebuilding, and observing
  the ACTUAL return values at runtime.

  Until then, the most likely candidate based on user report alone is:
  needsAdminPasswordReset() returns TRUE because the password_hash stored
  after the first-time setup still matches bcrypt('admin123'), suggesting
  updateAdminPassword() on the first launch may have targeted a different
  user row or the hash was not actually persisted.
