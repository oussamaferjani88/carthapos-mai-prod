1. EXECUTIVE SUMMARY
================================================================================
The pipeline POS -> ZIP export -> upload -> validation -> transformation preview
-> corrections -> confirm load -> warehouse -> dashboard generation is FUNCTIONAL
and has been exercised end-to-end with real data (restaurant client
cmoogzf95000xt2l5hk9yax74: 2,500 fact_sales, 19 dim_products, 402
fact_kitchen_orders, 181 dim_time, warehouse loaded in a single ~200 ms window).
The upload/validation/preparation/correction/load wizard works, tenancy is
enforced at the data layer (tenantId on every warehouse row), and a working
analytics API (bi-analytics.js) + an 8-tab analytics workspace already render
real dashboards from this data.

However, the platform is NOT production-ready and is NOT ready to start
building the three Phase-2 dashboard templates, for these headline reasons:

  A. Metabase is effectively UNINSTALLED. The Metabase catalogue tables exist
     in the pos_system database but contain 0 rows (metabase_database=0,
     report_card=0, report_dashboard=0, core_user=0, collection=0). The
     service does not respond (curl localhost:3000 -> 000). METABASE_EMBED_ENABLED
     is false and METABASE_EMBED_SECRET is empty. Templates (BiDashboardTemplate)
     number 0 rows. Dashboard "generation" today only creates a DRAFT database
     record — it never creates a Metabase dashboard, card, or chart.

  B. A known time-bucketing defect: warehouse-service.js getRevenueByDay/
     getPeakHours/getAverageTicket/getKitchenPerformance filter and group by
     fact_sales.createdAt (= DB LOAD time, verified all 2,500 rows loaded
     2026-08-02 12:08:39-40), NOT by dimTimeId (= real sale date, span
     2026-02-02 .. 2026-08-01). Every analytics answer built on those methods
     (bi-uploads/:id/summary, bi-analysis/:id/metrics, insight-generator) is
     wrong. The production analytics API (bi-analytics.js) already bypasses
     this and uses dimTimeId correctly, so the defect is contained but must be
     fixed or the bad path removed.

  C. JWT authentication is globally DISABLED (verifyToken commented out in
     server.js) with CORS origin '*'. Every BI endpoint (upload, delete,
     admin-approve, correction, warehouse summary, dashboard create/publish)
     is callable by anyone who can reach port 3001. Production credentials
     (postgres:oussama) and a hardcoded JWT fallback secret are committed.

  D. The warehouse is a per-upload SNAPSHOT REPLACEMENT store (delete
     tenantId, then insert). A 0-row or partial re-upload silently ERASES the
     previous good snapshot (observed live: client cmpb0pfd now has an empty
     warehouse after a 0-row COMPLETED upload).

  E. Schema/code drift: bi-dashboards.js reads dashboard.metabaseDashboardId
     but that column does not exist on bi_dashboards (only on
     bi_dashboard_templates); schema.prisma still declares dashboardType/
     dashboardConfig although the refactoring report says they were removed;
     the DB still has a legacy generationsteps column.

  F. Warehouse fact_sales never populates dimProductId / dimClientId (both 0%),
     so product-level analysis is impossible from the warehouse alone and
     depends entirely on the analytics-cache-service (the single allowed ZIP
     reader). This is a design fragility: if ZIPs are ever deleted or the
     cache is lost, product/customer/employee analytics vanish.

Scoreboard (Section 10) puts the platform at ~5.4/10 overall; template
readiness at "NOT READY" pending the remediation list in Section 15.

3. ETL ANALYSIS
================================================================================
Files: backend/services/etl-pipeline.js (873 lines),
       backend/routes/bi-uploads.js (974 lines),
       backend/services/bi-schema-registry.js (236 lines).

Pipeline entry (classic path):
  POST /api/bi-uploads -> multer (100 MB, .zip only) -> SHA-256 file hash
  -> duplicate detection (409 unless previous record was FAILED, then replaced)
  -> BiUpload status=PENDING_PAYMENT_VERIFICATION.

Classic run (POST /:id/start-etl, requires a linked APPROVED BiRequest):
  STEP 1 extract ZIP (execSync unzip 60 s timeout -> AdmZip fallback).
  STEP 2 read metadata.json (client_id, business_type, schema_version,
         enabled_modules, export_timestamp). clientId is then OVERRIDDEN by
         the upload.clientId (tenant attribution is correct).
  STEP 3 hard schema-version gate: export v must equal server v2.2.0.
  STEP 4 validate datasets: required = sales, products, customers, inventory;
         optional = tables, kitchen_orders, suppliers, services, appointments.
         Missing required file -> fatal. Column presence checked (required
         cols only). Type-check per row. Duplicate-row detection via
         JSON.stringify fingerprint (logged only, not fatal).
  STEP 5/6 in one $transaction (120 s timeout): create/update BiProcessingJob,
         load dims, load facts (snapshot replacement), mark COMPLETED,
         mark upload COMPLETED, auto-create BiAnalysisRequest (PENDING),
         write BiProcessingLog entries.
  On failure: upload + job marked FAILED with step-tagged message.

Wizard path (used by the UI):
  /:id/validate  -> extractAndValidate() (same gates, preview JSON saved)
  /:id/prepare   -> prepareWarehouse(): cleaning = exact-dup removal + empty-
                    string->null coercion; builds dims/facts in memory.
  /:id/correct   -> single-cell mutation of the preview JSON (no audit trail).
  /:id/confirm-load -> loadIntoWarehouse(): re-uses _loadDimensions/_loadFacts
                    on corrected data, marks upload COMPLETED.

Strengths:
  + Clean separation of raw/cleaned/dim/fact; preview JSON per upload.
  + Real validation: schema version gate, required columns, per-row types.
  + Tenant attribution forced from the upload record (not the ZIP).
  + Replacement semantics are deliberate ("wizard promises replacement").
  + BiProcessingLog gives step-level diagnostics.

Weaknesses / defects:
  - Server schema registry (bi-schema-registry.js) covers only 8 of the 21
    POS datasets. sale_items, kitchen_order_items, shifts, cash_drawer_events,
    z_reports, stock_movements, audit_logs, vat_rates, product_families are
    exported by the POS but never validated or loaded by the ETL.
  - Only 4 fact tables are ever loaded (sales/inventory/appointments/kitchen).
    sale_items (the grain needed for product analytics) is NOT loaded; it is
    only read later by the analytics cache service from the raw ZIP.
  - Type validation is weak: integer check passes "abc123" (regex fallback
    /\d+/); CSV parser handles quotes but not escaped quotes/embedded newlines
    reliably (naive state machine in bi-schema-registry.js parseCsvRow).
  - Classic and wizard paths are two parallel ETLs writing the same warehouse;
    the wizard path does NOT create a BiAnalysisRequest, so "analysis-ready"
    state differs depending on which path was used.
  - No chunked/streaming parse: whole CSVs are read into memory twice
    (validation + load). At 100 MB ZIPs this is a memory/time risk.
  - execSync('unzip') is a subprocess call; AdmZip fallback exists but the
    primary path shells out (spawn/timeout controls are present but fragile
    on Windows).
  - Snapshot replacement deletes by tenantId BEFORE insert with no staging/
    atomic-swap or point-in-time rollback.

4. DATA QUALITY
================================================================================
Verified live in pos_system:

  fact_sales   = 2,500 rows, ALL tenantId = cmoogzf95000xt2l5hk9yax74
                createdAt (load) all in one ~200 ms window 2026-08-02T12:08:39-40
                dimTimeId span 20260202..20260801  (real sale dates)
                dimProductId populated = 0 / 2500  (0%)
                dimClientId   populated = 0 / 2500  (0%)
                dimTimeId null = 0 / 2500 (all rows have a sale date)
  dim_products = 19, fact_inventory = 19, fact_kitchen_orders = 402,
  dim_time = 181, dim_clients = 1.

Interpretation:
  - The dimTimeId vs createdAt split (sale dates vs load timestamps) is
    demonstrable and is the root of the warehouse-service bug (Section 5).
  - fact_sales never links to dim_product or dim_client (dead relations in
    Prisma). v_sales compensates by joining dim_clients on tenantId, but
    product-level truth lives ONLY in the cache.
  - totalRows on uploads = sum of all fact records (e.g. 2921 = 2500 sales +
    19 inventory + 402 kitchen). It is a record count, not sales count.
  - Client cmpb0pfd has two uploads: one 25-row COMPLETED, then a 0-row
    COMPLETED. Because of snapshot replacement + "latest upload wins" cache
    logic, that client's warehouse is now empty. Confirms the silent
    data-loss path (an empty/partial ZIP destroys prior data).
  - The 0-row upload (cmqzgvu9) was accepted, validated (SKIPPED warnings),
    and marked COMPLETED — no hard rule rejects "empty" exports for a client
    that already has data.
  - POS-side validation (BiValidator) only samples the first 200 rows for
    required-null/type checks; referential-integrity/orphan warnings are
    advisory and not surfaced as fatal on the server.
  - Registry schema/column drift: the server schema declares a SUBSET of the
    POS columns; extra POS columns (e.g. cashier_name, table_id, shift_id on
    sales; loyalty_points/total_spent/visit_count on customers) are simply
    ignored by the ETL (they ARE used by the cache service). No harm today,
    but the "single source of truth" claim (registry mirrors contract) is not
    literally true.

Data-quality verdict: adequate for the single tested restaurant export;
not trustworthy for arbitrary retail/cafe/pharmacy exports because only 8 of
21 datasets are contract-validated and empty exports are not blocked.

5. WAREHOUSE
================================================================================
Schema (prisma/schema.prisma BI section; @map lowercase columns):
  DimClient / DimProduct / DimSupplier / DimTime (int PK YYYYMMDD, date
  unique) + FactSale / FactInventory / FactAppointment / FactKitchenOrder.
  Uniques: fact_sales(exportId,saleId), fact_inventory(exportId,rowIndex),
  fact_appointments(exportId,rowIndex), fact_kitchen_orders(exportId,rowIndex).

Grain & modeling:
  + DimTime is a proper surrogate key; facts carry dimTimeId.
  + Snapshot semantics are explicit (replacement per client).
  - No SCD2 / history: dim_product/dim_supplier are upserted (overwrite),
    so attribute changes silently rewrite history for the current snapshot.
  - dim_time is built only from dates present in the export (no full calendar
    table); holidays/week-labels absent.
  - FactSale is transaction-grain with NO product link (see Section 4) and no
    cashier/table dimension; those live only in the cache.
  - No aggregate/pre-aggregation tables (except the SQL views); group-bys run
    on the full fact table each call.
  - FactInventory rows carry timesSold (a lifetime aggregate) — semantically
    not a snapshot fact; drift between snapshots is not modeled.

Query layer:
  warehouse-service.js (258 lines):
    + All queries filter by tenantId (tenant isolation present).
    + getDashboardSummary is business-type aware (restaurant/cafe get table/
      kitchen/ticket/peak; pharmacy/retail get inventory/suppliers).
    BUG (confirmed, known, not patched per audit scope): getRevenueByDay,
    getPeakHours, getAverageTicket, getKitchenPerformance use fact_sales.
    createdAt / fact_kitchen_orders.createdAt (= load time) for both the
    date filter AND the day/hour bucketing, instead of dimTimeId (= sale
    date). Because all rows load in one ~200 ms window, "last 30 days" either
    shows everything loaded today or nothing; hour-of-day bucketing is the
    load hour, not the sale hour.
    Consumers of the buggy path: GET /bi-uploads/:id/summary,
    GET /bi-analysis/:id/metrics, bi-insight-generator.js.
  bi-analytics.js (the real analytics API, ~1,150+ lines):
    + Uses dimTimeId everywhere for range resolution and grouping (correct).
    + Combines warehouse (sales/revenue/payment/inventory) with the cache
      (products, customers, employees, tables, kitchen timings, shifts,
      reservations). Endpoints: /overview /trend /payment-mix /peak-hours
      /weekday /categories /products /customers /employees /tables /kitchen
      /inventory /shifts /reservations /insights /drilldown /filters (+/status
      in the truncated tail).
    This is the healthiest component in the BI module and is what the
    AnalyticsWorkspace consumes.

SQL views (migration 20260611180000_create_bi_views):
  v_sales, v_revenue_daily, v_inventory, v_product_performance,
  v_kitchen_orders, v_table_turnover, v_peak_hours, v_appointments,
  v_suppliers, v_dashboard_kpis. NOTE v_peak_hours uses
  EXTRACT(HOUR FROM fs."createdAt") — same createdAt bug as the service.
  (v_revenue_daily correctly groups by dt."date" via dimTimeId.) Also present
  are Metabase-internal views (v_databases, v_fields, v_dashboardcard, etc.)
  over the empty Metabase catalogue.

8. SECURITY
================================================================================
Critical (must-fix before production):
  - JWT auth DISABLED: server.js line 88 `// app.use('/api', verifyToken)`.
    ALL endpoints are anonymous (list all clients' uploads, upload, delete,
    cancel, admin-approve, correct, confirm-load, publish dashboards, read
    warehouse summaries).
  - CORS origin '*' with credentials: true (effectively open to any origin).
  - Database password `postgres:oussama` and the JWT fallback secret
    'carthapos-secret-key-change-in-production-2025' are committed in
    .env / auth middleware defaults.
  - /uploads is served statically (app.use('/uploads', express.static(...)));
    if a ZIP path leaks, raw export data is publicly readable. bi-uploads
    DELETE/cancel correctly unlink the file, but there is no authorization.
  - No rate limiting / upload flood protection (100 MB per file, unlimited
    count; multer writes to disk before validation).
  - bi-uploads POST only filters by extension (.zip), not MIME/content;
    contents are only validated after a full 100 MB upload.
  - Debug endpoint /api/bi/debug exists (audited) and should be gated.

Present / good:
  + helmet() enabled; express.json 10 MB; 20-minute server timeout.
  + Tenant isolation at the data layer (tenantId on every fact/dim; clientId
    overridden from the upload, never from the ZIP).
  + SHA-256 file hashing for duplicate detection.
  + Dashboard status transitions are validated (DRAFT->IN_PROGRESS->
    READY_FOR_REVIEW->PUBLISHED->ARCHIVED).
  + Metabase embedding is disabled by default and embed secret empty (not a
    live risk).
  + Metabase integration-report recommends read-only DB user + API proxy
    (design-only, not implemented).

9. PERFORMANCE
================================================================================
Verified: a 2,921-record export loads in ~1-2 s and the full 2,500-row sales
table committed in ~200 ms; ETL ran on 9 processing jobs without issue.
Positives: chunked inserts (1,000/batch), 120 s transaction timeout, index on
bi_requests status/paymentStatus, dim_time PK by int.

Concerns at scale:
  - Whole-file-in-memory parsing (validation + prepareWarehouse + load) — a
    true 100 MB ZIP with large CSVs can exhaust Node's default heap.
  - Snapshot replacement = DELETE all + INSERT all per client; large tenants
    cause long transactions and lock contention on fact tables (120 s cap).
  - warehouse-service / bi-analytics run full scans with no (tenantId,
    dimTimeId) index on fact_sales (only @@unique(exportId, saleId)); group-by
    queries will degrade as rows grow.
  - No worker/queue: ETL runs in-process (background .then()) — a second
    upload for the same client can interleave deletes/inserts.
  - analytics cache rebuild parses the ZIP synchronously on demand (bounded
    by LRU 32) — first dashboard hit per client pays the parse cost.
  - Multiple full joins in v_dashboard_kpis (5 LEFT JOINs over dim_clients)
    can blow up row counts for multi-tenant data.

11. RISKS
================================================================================
  R1 (Critical) Empty/partial re-upload erases the client's warehouse
     snapshot. Observed in production DB. Fix: block/merge or version
     snapshots before DELETE.
  R2 (Critical) Wrong analytics from warehouse-service createdAt bug —
     any report built on /bi-uploads/:id/summary, /bi-analysis/:id/metrics,
     or insight-generator is misleading. Confirmed with load-vs-sale dates.
  R3 (Critical) No authentication — full read/write/publish and upload
     control is anonymous. Publish path could expose fabricated dashboards.
  R4 (High) Metabase is not deployed; Phase-2 template work has no target.
  R5 (High) Product/customer/employee analytics depend on the retained ZIPs
     via analytics-cache-service; if ZIPs are purged or the cache deleted,
     those analytics vanish (no warehouse copy).
  R6 (High) Schema drift: bi_dashboards.metabaseDashboardId referenced but
     absent; schema.prisma vs DB vs refactoring-report inconsistencies
     (dashboardType/dashboardConfig/generationsteps). Migrations may diverge.
  R7 (Medium) Committed DB credentials + hardcoded JWT secret.
  R8 (Medium) Two ETL paths create divergent side effects (BiAnalysisRequest
