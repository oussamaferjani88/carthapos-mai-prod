FIGURE 2: fig:pos-generation-pipeline
-----------------------------------------------------------
Type: Pipeline / Flow Diagram
Filename: figures/ch5-pos-generation-pipeline.png
Caption: Design of the CarthaPOS POS generation pipeline

Description:
Draw the 8-stage generation pipeline as a horizontal or vertical flow.
Each stage is a box with input/output annotations.

STAGE 1: License Validation
  Input: licenseKey, machineFingerprint
  Process: Verify Ed25519 signature, check expiry, check machine binding
  Output: validated license payload

STAGE 2: Directory Initialization
  Input: outputPath, businessName
  Process: Create output directory structure
  Output: empty project skeleton

STAGE 3: Template Copy
  Input: pos-template/ source
  Process: Copy Electron template to output directory
  Output: full template copy

STAGE 4: Module Filtering
  Input: licenseModules (enabled/disabled list)
  Process: Remove code for disabled modules, update imports
  Output: filtered template with only enabled modules

STAGE 5: Dependency Installation
  Input: package.json from template
  Process: npm install in output directory
  Output: node_modules installed

STAGE 6: Theme Customization
  Input: LicenseConfiguration (colors, logo, businessName)
  Process: Inject CSS variables, replace logo, update config files
  Output: themed application

STAGE 7: File Patching
  Input: license payload, sector config, client info
  Process: Inject license into POS code, patch database config
  Output: configured application

STAGE 8: Build
  Input: configured application
  Process: electron-builder (optional asar, optional installer)
  Output: .exe installer or portable app

Use numbered boxes connected by arrows. Add a decision diamond after
stage 1 (valid license? yes -> continue, no -> abort).
Add a decision after stage 8 (build success? yes -> expose download, no -> error).

FIGURE 6: fig:admin-client-sequence
-----------------------------------------------------------
Type: UML Sequence Diagram
Filename: figures/ch5-admin-client-sequence.png
Caption: Sequence of client management in the administration interface

Description:
Draw a UML sequence diagram for a client management operation (e.g., create client).

LIFELINES:
  Operator -> Admin Frontend -> Backend API -> Middleware -> Client Service -> Prisma Client -> PostgreSQL

SEQUENCE (Create Client):

  1. Operator fills in client form (name, email, phone, address)
  2. Admin Frontend sends POST /api/clients
  3. Backend API receives request
  4. Middleware: JWT verification (extract userId from token)
  5. Middleware: Permission check (clients.create)
  6. Client Service: validate input data
  7. Client Service: check email uniqueness
  8. Prisma Client: INSERT into clients table
  9. PostgreSQL: execute INSERT
  10. Prisma Client: return created client
  11. Client Service: format response
  12. Backend API: return 201 with client object
  13. Admin Frontend: update client list, show success toast

ERROR BRANCH (if email already exists):
  Step 7 detects duplicate -> return 409 Conflict

Use activation bars. Show middleware as a combined activation.
Use alt fragment for the error branch.
