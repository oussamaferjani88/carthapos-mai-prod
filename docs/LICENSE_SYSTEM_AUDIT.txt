2. CURRENT LICENSE ARCHITECTURE (END TO END)
================================================================================

Admin creates license (wizard: POST /licenses)
  -> License row in Postgres (key, sector, type, expirationDate, isActive=true,
     isActivated=false, bindingType)
  -> LICENSE FILE: MOCKED in admin (SIG=BYPASSED-FOR-WEB-DEPLOYMENT); real
     generate-file endpoint bypassed. Backend real path (unused):
     AES(HMAC-signed JSON) -> license.key, HMAC with hardcoded secret.
  -> POS BUILD: POST /pos/generate {licenseId} -> AssetManager writes plaintext
     public/app-config.json {license{...}, security.requireUSBLicense:true}
     -> ThemeCustomizer OVERWRITES with {id,key,client} + requireUSBLicense:false
     -> electron-builder packages app.asar
  -> DELIVERY: Windows NSIS installer; license.key optionally written to USB
     (copy of a file)
  -> ACTIVATION: none (isActivated stays false; no activation endpoint/flow)
  -> MACHINE IDENTIFICATION: none at runtime (generateMachineId is backend-only,
     dormant, 5 coarse OS attributes)
  -> USB IDENTIFICATION: none (drive-letter scan; no serial/UUID captured;
     usbSerialNumber column never written)
  -> VALIDATION at startup: IPC handler returns config && config.license ? true : false
  -> GATE App.jsx:327 fires only if requireUSBLicense && !valid, but the flag is
     false in shipped builds -> NO GATE
  -> RUNTIME VALIDATION: none (dead crypto code in ElectronLicenseManager never wired)
  -> EXPIRATION: none enforced at runtime (expiry checks use local clock and are dead code)
  -> REVOCATION: none (no field, no endpoint, no check)

- Validation client-side or server-side?  NEITHER. The only "check" is a config
  presence check inside Electron. The backend is never consulted at runtime.
  Server-side, the only gate is posService.generatePOSApplication throwing if
  !license.isActive at BUILD TIME (backend/src/services/posService.js:28-30).
- Database involved: "licenses" (Postgres) for admin; generated POS uses a local
  SQLite (naruto.db) that contains NO license data.
- What happens on validation failure: in Electron with requireUSBLicense:true ->
  blocked by LicenseCheck screen (but flag is force-off). In web/preview mode ->
  license auto-granted. No other enforcement.

4. MACHINE-BOUND LICENSING AUDIT
================================================================================

4.1 What identifies a machine today
-----------------------------------
The ONLY fingerprint primitive is generateMachineId() (backend/utils/license.js:12-29):

    const machineInfo = { platform: os.platform(), arch: os.arch(),
                          hostname: os.hostname(),
                          cpus: os.cpus().length, totalmem: os.totalmem() };
    sha256(JSON.stringify(machineInfo)).substring(0, 16)   // 64 bits

- NO MachineGuid, MAC, disk serial, BIOS serial, motherboard ID, networkInterfaces,
  or any Electron-derived ID. No node-machine-id / systeminformation library is
  installed anywhere.
- This function is NEVER invoked by any API route or by the POS. license.machineId
  is a free-form string supplied by the admin/user and stored as plaintext.

4.2 Attack surface (realistic)
------------------------------
Attack                        Current protection  Why
----------------------------  ------------------  ----------------------------------------------------------
Copy license file to another  NONE                File is unbound to hardware; machineId not checked at runtime
Copy application to another   NONE                License is plaintext JSON inside app.asar (unpacked) or
  PC                                               resources/config.json
Modify machine ID             NONE                machineId is plaintext in app-config.json; nothing computes
                                                  or compares a fingerprint
Delete local activation data  NONE                Presence check only; deleting then re-adding "license":{} re-passes
Reinstall Windows             NONE                Weak binding is hostname-based; would break on any hostname
                                                  change - no stable hardware anchor
Change network adapter /
  disk / motherboard          NONE                Not part of the fingerprint anyway
Clone the machine             NONE
Modify configuration files    NONE                Unsigned JSON, no checksum verified at runtime

The mechanism is not merely spoofable - it is NEVER enforced at all. A fingerprint
built from hostname + CPU count + RAM is weak by design (collisions between similar
machines; unstable across hostname/RAM changes) and the 64-bit truncation halves
even that strength.

5. USB LICENSING AUDIT
================================================================================

USB licensing is NOT implemented. What exists is file-on-USB delivery, not
USB-bound licensing.

- Detection: backend "wmic logicaldisk where drivetype=2" returns only letter /
  size / freeSpace - NO serial, vendor, product, or volume UUID
  (backend/src/repositories/usbRepository.js:18). Electron scans drive letters and
  fakes isRemovable:true ("Simplified check", ElectronLicenseManager.cjs:35-39).
- Identification: NONE. usbSerialNumber column exists in DB but NOTHING ever
  writes to it - no device identity is ever captured.
- License file: a portable license.key written via fs.writeFileSync to whatever
  path is supplied. Server-side verify just reads the file back.
- Copying: trivial - the file is copied to any USB/directory. driveExists() is
  plain fs.existsSync.
- Impersonation: trivial - any drive letter can hold a copied file; there is no
  device-bound identity to forge.
- Hardware security token: NOT PRESENT. No USB HID device, no crypto token, no
  write-protected hardware, no WebUSB/serialport/libusb anywhere (verified: zero matches).

--- Normal USB flash drive vs real hardware dongle ---
Factor                  Normal USB flash drive                        Real hardware dongle/security token
----------------------  --------------------------------------------  -------------------------------------------
Identity                Volume/disk serial (readable, re-writable,     Unique ID burned into chip, cryptographically
                        clonable via drive imaging)                    enforced by on-device firmware
Copy resistance         Low - image the drive and it is cloned         High - secret never leaves the chip
Cost                    ~$2-10                                        ~$5-50+ (CodeMeter, HASP, YubiHSM, ...)
Detection in app        Standard OS volume enumeration (can be FAKED   Needs native driver/HID (node-usb, WebUSB,
                        by mapping any volume)                         or vendor SDK)

--- Can the architecture support both later? ---
PARTIALLY. The DB already has bindingType (MACHINE/USB/HYBRID) and usbSerialNumber.
But the runtime has NO USB abstraction, NO native USB access, and the current
file-on-drive model cannot authenticate a dongle. Supporting a real dongle requires
adding native USB access in the Electron main process (WebUSB in Chromium or a
libusb/HID binding) - a clean layering point, since all USB logic can stay behind
the existing IPC bridge.

6. CRYPTOGRAPHIC SECURITY
================================================================================

There is NO asymmetric cryptography anywhere - no RSA, ECDSA, Ed25519, no
crypto.sign/verify, no public/private key pairs. Verified by full-tree search.

What exists is symmetric:

  Scheme           Where                                                      Secret
  ---------------  ----------------------------------------------------------  ---------------------------------------------
  HMAC-SHA256      backend/utils/license.js:57-72                             JWT_SECRET || 'default-signing-secret'
  AES (CryptoJS)   backend/utils/license.js:32-54, scripts/generate-license.js ENCRYPTION_KEY || 'default-32-char-encryption-
                                                                               key-here' / '1234567890abcdef1234567890abcdef'
  HMAC-SHA256      backend/src/services/licenseService.js:169                 LICENSE_SECRET || 'default-secret' (base64
                                                                               "simulated encryption")
  HMAC-SHA256      ElectronLicenseManager.cjs:179-182                         'pos-license-secret-2024' (shipped in app)
  JWT (HMAC)       backend/middleware/auth.js:4                               'carthapos-secret-key-change-in-production-2025'

Findings:
- Private key location: N/A - there are no key pairs. All secrets are hardcoded
  constants, visible in source and extractable from shipped binaries.
- Signing happens: backend utils/CLI (admin-side) and (dead code) ElectronLicenseManager.
- Verification happens: only in validateLicenseFile / scripts/generate-license.js -
  and NEVER invoked in any production path.
- Because the "verifying" secret ships with the POS, anyone can mint valid licenses.
  The requirement that the POS contain only a public verification key and never the
  private signing key is NOT met. Switching to asymmetric signatures (Ed25519 via
  Node's built-in crypto - zero new dependencies) is required.

                        anchors like disk

and design the USB layer behind an interface so a hardware dongle can be added later
without touching POS UI. Asymmetric signatures (Ed25519, Node built-in) underpin both.

15. FINAL AUDIT REPORT
================================================================================

CURRENTLY IMPLEMENTED
- DB model for licenses, modules, configurations, client linkage, binding fields.
- Backend CRUD API (two stacks) for licenses; license key generation (random strings).
- Admin license list page with derived status, details dialog, file download.
- POS generator wizard: type/expiry/bindingType selection; license embedded into
  build config (plaintext).
- USBManager page: enumerate drives (letter only), write/verify license.key files.
- Electron app: real main process, preload, IPC; LicenseCheck block UI exists.
- No signing at all is truly "implemented" - the scheme is symmetric, dead, and inconsistent.

PARTIALLY IMPLEMENTED
- License lifecycle fields (isActivated, activatedAt, lastValidatedAt) - defined, never used.
- bindingType (MACHINE/USB/HYBRID) - selectable in UI, ignored at runtime.
- USB detection - drive-letter enumeration only, faked removability, no identity.
- Machine ID - weak dormant helper (generateMachineId), never enforced.
- License file generation - HMAC+AES with hardcoded secrets; MOCKED OUT in the web
  admin (SIG=BYPASSED-FOR-WEB-DEPLOYMENT).
- Backend auth - JWT exists but off by default (AUTH_REQUIRED !== 'true') and absent
  on v1 routes.
- Admin UI - read/list/download only; no management actions.

MISSING
- Real activation/deactivation/suspend/revoke/renew/extension/transfer/replace flows.
- Runtime license verification in the POS (signature, expiry, machine, USB).
- Any asymmetric crypto / public-key verification.
- Machine fingerprinting in Electron; USB identity capture.
- Offline grace period, last-validated storage, clock-rollback detection, trusted time.
- Validation/activation history tables & UI.
- Reset-machine/USB-binding operations, transfer limits.
- User-level endpoints (client activation/self-service) in backend & client interface.

SECURITY RISKS (most important)
1. License enforcement is effectively disabled in shipped builds (requireUSBLicense:false
   forced by ThemeCustomizer.js:479; stub IPC validator; DEV-LICENSE/VALID-LICENSE fallbacks).
2. Hardcoded symmetric secrets (6+ locations) forgeable by anyone with the source -
   including 'pos-license-secret-2024' shipped in the app.
3. Plaintext unsigned license data in app.asar/resources/config.json; asarUnpack ships
   unpacked Electron sources.
4. USB licensing is a copied file with no device binding.
5. Backend APIs are unauthenticated by default; license binding fields are client-editable
   via generic PUT.
6. Web admin mocks license files - generated POS licenses are fabricated.
7. No code signing, no integrity verification, no trusted time.

TECHNICAL DEBT
- Dual backend stacks (legacy routes/ vs src/) with different key formats, validators,
  and field names (expirationDate vs expiresAt).
- Conflicting generators: AssetManager (writes full license, requireUSB:true) vs
  ThemeCustomizer (wipes it, requireUSB:false).
- Dead code: ElectronLicenseManager crypto/USB validation, license:* preload channels,
  licenseService.verifyLicense (broken), validateLicenseFile/validateMachineBinding.
- 6 benchmark POS copies duplicating license logic; public dev license in seeds.

REQUIRED DATABASE CHANGES
- status enum + proper lifecycle columns (revokedAt, suspendedAt, renewedAt,
  activationCount, transferCount, maxTransfers).
- Real machineFingerprint + activatedMachineId (keep legacy machineId separate or migrate).
- usbDeviceId (real device identity: volume serial / hardware ID).
- signedLicensePayload (base64 signed token), licenseVersion, issuedAt.
- New tables: LicenseActivationHistory, LicenseValidationLog, LicenseTransferHistory
  (optionally LicenseRevocationList).

REQUIRED BACKEND CHANGES
- Single unified license module (drop legacy duplicates). Ed25519 signing service
  (private key from env, never shipped to POS).
- Dedicated endpoints: activate, deactivate, suspend, resume, revoke, renew, extend,
  transfer, reset-machine, reset-usb, plus activation/validation history, revocation
  list (for online check), and signed-time issuance.
- Remove client-writable binding fields from generic update; enforce server-side
  ownership of binding data.
- Auth middleware enabled by default; rate-limit & JWT on license routes.
- Wire adminCreateLicenseSchema (currently dead); remove module-upgrade JSON-file hack.

REQUIRED ELECTRON CHANGES
- Real verification in the main process: Ed25519 verify, expiry vs signed time,
  machine fingerprint compare, USB identity check.
- Native fingerprint (stable anchors: disk serial via systeminformation/WMI, plus
  fallbacks) and native USB access behind an abstraction (WebUSB/HID now, dongle later).
- Remove DEV-LICENSE/VALID-LICENSE fallbacks; fix the boolean-vs-object IPC contract;
  wire or delete dead license code; persist lastValidatedAt; implement grace-period +
  clock-drift detection (store last-good signed time).

REQUIRED ADMIN UI CHANGES
- Full management page: create/edit forms, lifecycle actions (activate/deactivate/
  suspend/revoke/renew/extend/transfer/reset-binding), machine & USB identity display,
  activation/validation history, real (non-mocked) license file generation.

RECOMMENDED FINAL ARCHITECTURE
1. Machine-bound licensing: Electron computes stable fingerprint -> sends to backend on
   activation -> backend signs {licenseId, fingerprint, expiresAt, modules, issuedAt}
   with Ed25519 -> returns signed token -> POS verifies with embedded public key each
   start, stores token locally.
2. USB licensing: same signed token written to USB; binding includes volume serial
   captured by Electron; POS checks presence + serial + signature.
3. Cryptographic signing: Ed25519 (Node crypto); private key backend-only; public key
   embedded in POS.
4. Offline validation: signature+expiry verified locally; lastValidatedAt persisted;
   configurable grace period after last success; clock-drift detection against
   last-known-good signed timestamp.
5. Online validation: on activation and, opportunistically, when network available -
   check revocation list, sync lastValidatedAt, refresh signed time.
6. Lifecycle: explicit status machine (CREATED->ISSUED->ACTIVATED->ACTIVE->
   {EXPIRED, REVOKED, SUSPENDED, RENEWED, REPLACED}) with history tables.
7. Transfer/replacement: admin reset + activation history + transfer counter/limits.
8. Admin management: full CRUD + lifecycle actions + monitoring (status, machine,
   USB, activation/validation history).
