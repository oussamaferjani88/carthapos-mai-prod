2. CRITICAL LIMITATIONS FOUND IN METABASE CE
----------------------------------------------
These are NOT implementation failures — they are inherent limitations of
Metabase Community Edition that directly affected the architectural design:

  A. NO CREATE/UPDATE DASHBOARD API
     CE does not expose POST/PUT endpoints for dashboards or cards.
     SOLUTION: Direct SQL inserts into Metabase's internal PostgreSQL tables
     (report_dashboard, report_card, report_dashboardcard, etc.).

  B. NO ROW-LEVEL SECURITY (SANDBOXING)
     CE cannot restrict which rows a user sees. All Metabase users with
     access to a data source see ALL rows.
     SOLUTION: PostgreSQL schema-per-tenant pattern. Each tenant gets an
     isolated schema (e.g., tenant_client_abc123) containing views that
     filter WHERE tenantId = 'abc123'. Each schema = separate Metabase
     data source. This is the only reliable isolation mechanism in CE.

  C. NO AUTHENTICATED EMBEDDING
     CE only supports public (unauthenticated) embedding via iframe with a
     UUID. There is no JWT/signed embedding — that is an Enterprise Edition
     feature.
     SOLUTION: API proxy pattern. The CarthaPOS backend authenticates the
     user, then fetches card data from Metabase API server-side and returns
     JSON to the React client. Existing Recharts components render the data
     with full CarthaPOS auth control.

3. ARCHITECTURE DECISIONS
--------------------------
  A. Hybrid Architecture (not full replacement)
     - Metabase becomes the admin's dashboard DESIGN tool
     - Client viewing stays React-based but sourced from Metabase data
     - Old React rendering path kept as fallback (graceful degradation)

  B. Schema-Per-Tenant for Isolation
     - CREATE SCHEMA tenant_client_X
     - CREATE VIEW v_sales AS SELECT * FROM public.fact_sale WHERE tenantId = 'X'
     - One Metabase database connection per tenant schema
     - Acceptable for PFE scale; production would need EE sandboxing

  C. Direct Metabase DB Inserts for Programmatic Creation
     - Since CE API cannot create dashboards, we insert into Metabase's own
       PostgreSQL database directly via Prisma
     - Dashboard generation creates: report_dashboard → report_card →
       report_dashboardcard rows
     - Template cards converted to Metabase-native dataset_query JSON

  D. API Proxy for Client Delivery
     - CarthaPOS validates user session
     - Server calls Metabase API to execute card queries
     - Returns structured JSON (not iframe) to React frontend
     - Existing Recharts components render line/bar/pie/table/scalar cards

7. RISK SUMMARY
----------------
  - Certain: Metabase CE lacks create/update dashboard APIs (mitigated by direct DB insert)
  - High: No RLS in CE (mitigated by schema-per-tenant pattern)
  - High: No authenticated embedding (mitigated by API proxy pattern)
  - Medium: Prisma migration failures (mitigated by raw SQL fallback)
  - Low: Race conditions between ETL completion and view creation (views refreshed at generation time)

8. KEY INSIGHT FOR PFE
-----------------------
  The final architecture is NOT a pure Metabase solution. It is a HYBRID:
    - Admin side: Metabase native UI for dashboard design
    - Client side: Custom React with Metabase-sourced data via proxy
    - Data isolation: PostgreSQL schema-per-tenant
    - Generation: Direct DB inserts into Metabase internals

  This hybrid approach is the CORRECT architectural response to Metabase CE's
  limitations. A pure Metabase CE solution would compromise either security
  (public embedding with no auth) or user experience (forcing clients to log
  into Metabase directly). The hybrid preserves both security and UX while
  leveraging Metabase's strengths in dashboard design and query building.
