2. NOUVEAU WORKFLOW
═══════════════════════════════════════════════════════════════════════

Produit (requires_kitchen=true)
  ↓
Ajout au panier
  ↓
Validation vente
  ↓
  ┌─ Si vente payée (status='paid') → createKitchenOrder() IMMÉDIATEMENT
  └─ Si vente en attente (status='pending') → AUCUNE commande cuisine
  ↓
  └─ complete-pending-sale → createKitchenOrder() UN SEULEMENT
  ↓
Broadcast IPC → kitchen:order-created
  ↓
Kitchen.jsx reçoit event → affiche la commande IMMÉDIATEMENT
  ↓
Préparation (pending → preparing → ready → served → completed)
  ↓
Chaque changement → sync sales.kitchen_status
  ↓
Annulation → cascade annulation + sync bidirectionnelle

3. PROBLÈMES CORRIGÉS
═══════════════════════════════════════════════════════════════════════

BUG CRITIQUE #1 — Commandes cuisine invisibles
  Cause racine: createKitchenOrder() n'appelait JAMAIS
  broadcastKitchenEvent(). Les commandes étaient créées en BDD
  mais jamais envoyées au renderer Kitchen.jsx.
  Fix: broadcastKitchenEvent('kitchen:order-created', payload)
  ajouté à l'intérieur de createKitchenOrder() lui-même.
  → TOUTES les commandes, quel que soit l'appelant, sont maintenant
  broadcast en temps réel.

BUG CRITIQUE #2 — Double création de commandes
  Cause: add-sale (pending) créait des commandes, puis
  complete-pending-sale en créait à nouveau.
  Fix: add-sale ne crée plus de commandes cuisine quand
  status='pending'. Seul complete-pending-sale les crée.
  → ZÉRO duplication.

BUG MOYEN #3 — Pas de synchronisation Vente ↔ Cuisine
  Cause: Aucun lien retour de la cuisine vers la vente.
  Fix: Nouvelle colonne sales.kitchen_status avec sync
  bidirectionnelle automatique à chaque changement d'état.
  Statuts: not_started → order_received → preparing →
  ready → served → completed → cancelled

BUG MOYEN #4 — Total accepté du client
  Cause: createKitchenOrder() utilisait total tel quel
  du caller (sales handler).
  Fix: Total calculé côté serveur depuis items[].price *
  items[].quantity. Le total du client est un fallback
  uniquement si le calcul serveur donne 0.

BUG MOYEN #5 — BI Schema incomplet
  Cause: BiSchemaContract.cjs ne connaissait que 8 colonnes
  de base. Les 10 colonnes ajoutées par migration étaient absentes.
  Fix: Schema kitchen_orders mis à jour avec les 18 colonnes:
  order_id, table_number, items, notes, priority, status,
  sale_id, total, server_name, customer_name, department,
  estimated_minutes, started_at, completed_at, cancel_reason,
  cancelled_by, created_at, updated_at

BUG MOYEN #6 — Pas d'annulation cascade
  Cause: Annuler une vente ne touchait pas les commandes cuisine.
  Fix: Nouveau handler cancel-sale qui annule TOUTES les
  commandes cuisine actives liées à la vente.

4. IPC UTILISÉS
═══════════════════════════════════════════════════════════════════════

Cuisine → Backend (invoke):
  get-kitchen-orders              — Toutes les commandes
  get-active-kitchen-orders       — Commandes actives (pending/preparing/ready)
  get-kitchen-order               — Une commande par ID
  add-kitchen-order               — Création manuelle
  update-kitchen-order-status     — Changement d'état (state machine)
  kitchen:batch-status            — Batch update
  kitchen:cancel-order            — Annulation avec raison
  kitchen:cancel-sale-orders      — Annulation cascade par sale_id
  get-kitchen-order-stats         — Statistiques du jour
  kitchen:get-department-stats    — Stats par département
  kitchen:delete-order            — Suppression (admin only)
  kitchen:get-history             — Historique filtrable
  kitchen:get-recent              — Dernières commandes

Backend → Cuisine (real-time events):
  kitchen:order-created           — Nouvelle commande
  kitchen:order-updated           — Mise à jour de statut
  kitchen:order-cancelled         — Commande annulée
  kitchen:order-deleted           — Commande supprimée
  kitchen:batch-updated           — Batch update

Vente → Backend:
  add-sale                        — Crée commandes SI status='paid'
  complete-pending-sale           — Crée commandes SI pending→paid
  cancel-sale                     — Annule vente + commandes cuisine

7. SYNCHRONISATION Vente/Cuisine
═══════════════════════════════════════════════════════════════════════

Bidirectionnelle:
  Vente → Cuisine: createKitchenOrder() à la création de vente
  Cuisine → Vente: syncSaleKitchenStatus() à chaque changement

Fonction syncSaleKitchenStatus():
  - Appelée dans update-kitchen-order-status
  - Appelée dans kitchen:batch-status
  - Appelée dans kitchen:cancel-order
  - Appelée dans kitchen:cancel-sale-orders
  - Appelée dans createKitchenOrder()
  - Mappe le statut cuisine → sales.kitchen_status

Mapping:
  pending   → order_received
  preparing → preparing
  ready     → ready
  served    → served
  completed → completed
  cancelled → cancelled

12. RISQUES RESTANTS
═══════════════════════════════════════════════════════════════════════

⚠️ Les commandes cuisine pour les ventes avec des produits
   requires_kitchen=false ne seront jamais créées (comportement
   attendu mais à documenter).

⚠️ Le nettoyage automatique des anciennes commandes cuisine n'est
   pas implémenté. La table peut croître indéfiniment.
   Recommandation: cronjob ou trigger SQLite pour archiver
   les commandes > 30 jours.

⚠️ Le son utilise AudioContext (Web Audio API). Sur certains
   appareils, le premier son peut être silencieux (autoplay policy).
   Le premier clic sur le bouton son débloque l'audio.
