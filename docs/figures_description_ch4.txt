Description:
Draw the full platform architecture showing all major components as labeled

COMPONENTS (arranged top to bottom):

  TOP ROW - Frontends (3 boxes):
    [Administration Frontend] - React + Vite + Tailwind, static site on Render
    [Client Portal] - React + TypeScript + Vite, static site on Render

    [Analytical Warehouse] - PostgreSQL star schema (5 Dim + 6 Fact tables)

  Admin Frontend --REST/HTTPS--> Backend API
  Client Portal --REST/HTTPS--> Backend API
  Backend API --generates--> Generated POS App
  Generated POS App --local--> SQLite (operational data)
  Generated POS App --exports ZIP--> BI Export
  Backend API --Prisma--> PostgreSQL
  Backend API --REST--> Metabase (provisioning)
  Metabase --SQL queries--> Analytical Warehouse

FIGURE 2: fig:communication-architecture
-----------------------------------------------------------
Type: Communication Diagram
Filename: figures/ch4-communication-architecture.png
Caption: Communication architecture of CarthaPOS

Description:
Draw a diagram showing the 5 communication paths between the applications.
Each path should be a labeled arrow between two component boxes.

PATH 1 - REST/HTTPS:
  Admin Frontend <---> Backend API
  - JWT authentication, cookie-based sessions
  - JSON payloads, standard HTTP methods

PATH 2 - REST/HTTPS:
  Client Portal <---> Backend API
  - Same JWT auth, limited routes (BI views, dashboards)

PATH 3 - IPC (Inter-Process Communication):
  Generated POS (Renderer) <---> Generated POS (Main Process)
  - electron IPC bridge (preload script)
  - Channels: sale, product, inventory, customer, kitchen, table, etc.

PATH 4 - SQLite (local file):
  Generated POS (Main Process) <--> SQLite Database
  - Direct SQL queries via better-sqlite3
  - Local operational data, no network dependency

PATH 5 - File Transfer (ZIP):
  Generated POS --> Backend API
  - BiSchemaContract ZIP export (20 datasets)
  - Uploaded via multipart/form-data (Multer)

Use different arrow styles: solid for REST, dashed for IPC,
dotted for file transfer, double-line for local DB.

SIDE BOXES (cross-cutting):

FIGURE 11: fig:sale-transaction-sequence
-----------------------------------------------------------
Type: UML Sequence Diagram
Filename: figures/ch4-sale-transaction-sequence.png
Caption: Sequence of the atomic sale transaction

Description:
Draw a UML sequence diagram for the atomic sale transaction.
All database writes happen inside a single SQLite transaction.

LIFELINES:
  Cashier -> POS UI -> Sale Module -> ElectronDB (SQLite) -> Kitchen Display

SEQUENCE:

  1. Cashier selects products and quantities in POS UI
  2. POS UI calculates subtotal, tax, discount
  3. Cashier clicks Complete Sale
  4. POS UI sends sale data to Sale Module
  5. Sale Module opens SQLite transaction (BEGIN)
  6. INSERT into sales table
  7. INSERT into sale_items table -- loop for each item
  8. UPDATE products SET stock = stock - quantity -- loop
  9. INSERT into stock_movements -- loop

  OPTIONAL BRANCH (if customer assigned):
    10. UPDATE customers SET loyalty_points + earned
    11. INSERT into loyalty_transactions

  OPTIONAL BRANCH (if table assigned):
    12. UPDATE restaurant_tables SET status = available

  OPTIONAL BRANCH (if kitchen module enabled):
    13. INSERT into kitchen_orders
    14. Send IPC notification to Kitchen Display

  15. COMMIT transaction
  16. Return success to POS UI
  17. Clear cart, show confirmation

Use alt/opt fragments for optional branches.
Use loop fragment for item iteration.
Mark the transaction boundary with a note (BEGIN/COMMIT).
