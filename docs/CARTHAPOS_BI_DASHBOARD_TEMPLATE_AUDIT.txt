1. DATABASE VIEW CONTRACT CHECK
================================================================================

All 14 views expose: client_id (= tenantId) + client_name + business_type where
relevant. Every view is single-tenant safe (see section 6).

--- v_dashboard_kpis ----------------------------------------------------------
PURPOSE   Tenant-level executive KPI header card.
GRAIN     One row per client (dim_clients). Scalar aggregates over full export.
FILTERS   client_id, client_name. No date dimension (only last_sale_date).
KPIs      total_sales, total_revenue, avg_ticket, total_products,
          total_kitchen_orders, total_appointments, total_suppliers.
LIMIT     No trend/date-range; static per-tenant header. avg_ticket = mean of
          sale totals (matches v_sales). last_sale_date is a point value.
          PERFORMANCE: rewritten 20260803100000 — 74 ms (was >120 s).

--- v_sales -------------------------------------------------------------------
PURPOSE   Transaction-grain sales ledger.
GRAIN     One row per sale (2,500).
FILTERS   client_id, client_name, business_type, sale_date, year, quarter,
          month, day, day_of_week, is_weekend, payment_method, sale_id.
KPIs      Revenue (total), tax, discount, avg ticket, payment-method mix,
          daily/weekly/monthly counts & revenue, weekend vs weekday.
LIMIT     No product/category, no customer, no hour-of-day. Uses dim_time.date
          which is a naive timestamp (timezone semantics — see finding F2).

--- v_revenue_daily -----------------------------------------------------------
PURPOSE   Time-series revenue.
GRAIN     One row per client + day (181 days).
FILTERS   client_id, client_name, business_type, date, year, month, day,
          day_of_week.
KPIs      Revenue by day/month/year, transaction_count, avg_ticket.
LIMIT     No payment/product segmentation.

--- v_product_performance -----------------------------------------------------
PURPOSE   Product & category performance from REAL sale line items (fixed from
          the old inventory snapshot).
GRAIN     One row per client + product (19).
FILTERS   client_id, product_name, category, family. NO DATE COLUMN.
KPIs      total_sold, order_count, unit_price, revenue, vat_amount; top
          products, category ranking, best seller.
LIMIT     F3: NO date/date-range filter — product trend-over-time and "top
          product in range" impossible through this view. Item-grain revenue
          (119,854) < sale-grain (139,869.52) — see section 4 note (source data).

--- v_customer_analysis -------------------------------------------------------
PURPOSE   Customer segmentation / loyalty.
GRAIN     One row per customer (14).
FILTERS   client_id, customer_id, customer_name, email, phone, loyalty_points.
KPIs      total_spent, visit_count, order_count, lifetime_revenue, avg_ticket,
          first/last_order_date; returning customers (visit_count>1).
LIMIT     Lifetime aggregates — no per-month customer activity. loyalty/total
          spend values come from source customers.csv (loyalty module enabled).

--- v_sales_hourly ------------------------------------------------------------
PURPOSE   Hourly sales time-series.
GRAIN     One row per client + day + hour (1,424).
FILTERS   client_id, sale_date, hour_of_day.
KPIs      Hourly order_count, revenue, tax; hourly heatmap.
LIMIT     No payment/product segmentation. Cross-checks to 2,500/139,869.52.

--- v_peak_hours --------------------------------------------------------------
PURPOSE   Peak-hour ranking (fixed: hour-of-day, not load date).
GRAIN     One row per client + hour (11 occupied of 0-23).
FILTERS   client_id, hour_of_day. No date.
KPIs      order_count, revenue by hour; peak-hours bar.
LIMIT     No date range; static overall profile. T1 peaks hours 1-4.

--- v_inventory ---------------------------------------------------------------
PURPOSE   Inventory snapshot + turnover.
GRAIN     One row per client + product (19).
FILTERS   client_id, product_name, category, family, barcode.
KPIs      stock, price, times_sold, turnover_ratio, inventory value (stock×price).
LIMIT     Single snapshot (snapshot_date = load time, no history/trend).
          F4: source stock = 0 everywhere → turnover_ratio = 0, value = 0.

--- v_inventory_status --------------------------------------------------------
PURPOSE   Stock alerting (NEW).
GRAIN     One row per client + product.
FILTERS   client_id, product_name, category, family.
KPIs      stock_status IN_STOCK/LOW/OUT_OF_STOCK; data_warning
          INVENTORY_DATA_NOT_AVAILABLE when max(stock)=0 (honest flag for F4).
LIMIT     Same single-snapshot limitation.

--- v_kitchen_orders ----------------------------------------------------------
PURPOSE   Kitchen order log.
GRAIN     One row per kitchen order (402).
FILTERS   client_id, order_date, year, month, day, day_of_week, is_weekend,
          priority, status, table_number.
KPIs      Orders by day/status/priority/table.
LIMIT     Restaurant/cafe only.

--- v_kitchen_performance -----------------------------------------------------
PURPOSE   Kitchen operational performance (NEW, order grain + prep time).
GRAIN     One row per kitchen order (402).
FILTERS   client_id, order_date, priority, status, table_number, order_id.
KPIs      prep_minutes (ready-complete − start), item_count, total_quantity,
          total_revenue; avg prep time, status funnel.
LIMIT     prep_minutes near 0 on ~66% rows (source started==ready — fabricated
          data). Timestamps stored faithfully.

--- v_table_turnover ----------------------------------------------------------
PURPOSE   Table usage.
GRAIN     One row per client + table (20).
FILTERS   client_id, table_number.
KPIs      order_count per table, first/last order date.
LIMIT     No per-visit duration (no seated/closed timestamps in source).

--- v_suppliers ---------------------------------------------------------------
PURPOSE   Supplier directory.
GRAIN     One row per supplier.
FILTERS   client_id, supplier_name.
KPIs      Contact info only.
LIMIT     F5: suppliers.csv empty in T1 export → 0 rows. Structure ready.

--- v_appointments ------------------------------------------------------------
PURPOSE   Appointments (salon/services).
GRAIN     One row per appointment.
FILTERS   client_id, appointment_date, year, month, day, status.
KPIs      Appointments by day/status/service.
LIMIT     F5: no appointments exported for restaurant type → 0 rows. Structure
          ready; intended for non-restaurant tenants.

6. MULTI-TENANT SAFETY
================================================================================

  - Every view SELECTs tenantId AS client_id. Verified no view omits it.
  - All joins that could leak are tenant-guarded:
      v_customer_analysis  joins fact_sales ON tenantId AND customerId.
      v_kitchen_performance joins fact_kitchen_order_items ON tenantId AND orderId.
      v_product_performance joins dim_products by global FK (dimProductId).
      v_sales/v_revenue_daily join dim_clients by tenantId, dim_time by FK.
  - dim_time and dim_products are shared reference data joined by globally
    unique FK ids (no name/date-key collisions); tenant scope is always
    introduced by the fact table.
  - Verified: T2 tenant has 0 warehouse rows, no NULL-tenant rows exist.
  - v_dashboard_kpis iterates dim_clients (per-client row) — by construction
    cannot cross tenants.
  VERDICT: SAFE. Every dashboard query is isolatable by client_id. Metabase
  must enforce a locked client_id filter (section 8).

8. METABASE EMBEDDING READINESS
================================================================================

FINDING: There is currently NO Metabase instance, config, or embedding code in
the repository (no .env entries, no packages, no integration). The warehouse is
served through the existing authenticated REST API (/api/bi-uploads/:id/summary
etc.), which is already tenant-bound via user auth.

Readiness of the data contract for embedding:
  - All views expose client_id → a Metabase param can enforce tenant scoping.
  - Views are deterministic SQL (no dynamic objects) → syncable, cacheable.
  - Naive timestamps (F2) → set Metabase report timezone to the tenant timezone
    (Africa/Tunis here) to avoid off-by-one-day date bucketing.

RECOMMENDATION — Option B (Custom BI frontend using existing APIs) is the
lower-risk default:
  - Tenant isolation already enforced at auth layer (user → tenant → upload),
    no risk of client_id leakage through a shared Metabase.
  - No new infra (Metabase instance, SMTP, secret key, dashboard IDs).
  - Template = parameterized React components bound to /summary and per-KPI
    endpoints (warehouse views); the same data contract is consumed.

Option A (Metabase signed embedding) is viable but requires:
  - Standing up Metabase + DB permissions for read-only on public views.
  - Signed embedding (JWT) with client_id as a LOCKED parameter so tenants can
    never change it (never use public/unsecured sharing).
  - Metabase report timezone = tenant timezone; a proxy endpoint that mints
    per-tenant signed tokens.
  - Dashboard-template "packaging" for Metabase (x-ray/json export) maintained
    separately from the repo.

     Metabase model over fact_sale_items + dim_time, which already supports
