## Architecture Overview

### Auth Flow Diagram

```
App Launch
    │
    ├── isPreviewMode()?
    │   ├── YES → POSWithAuth (2-step: role select → password)
    │   │         └── AuthContext.loginWithDemoUsers()
    │   │             └── Hardcoded demo credentials
    │   │
    │   └── NO (Production/Electron)
    │       ├── needsFirstTimeSetup() → true?
    │       │   └── SetupWizard → createAdminUser() → auto-login
    │       │
    │       ├── needsAdminPasswordReset() → true?
    │       │   └── SetupWizard → updateAdminPassword() → auto-login
    │       │
    │       └── Neither → POSWithAuth (username/password form)
    │           └── AuthContext.loginWithDatabase()
    │               └── authenticate-user IPC → bcrypt.compare
    │
    └── User authenticated → MainPOSApp routes
```

## Module 1: Login Page (`POSWithAuth.jsx`)

### UI Layout
- Card centered on screen with gradient background
- Business name/logo from config
- Welcome text from config
- Form fields: username (production only) + password
- Show/hide password toggle (Eye/EyeOff)
- Submit button with loading spinner
- Error message display (red banner)
- Business info footer (address, phone, email)

### Two Modes

**Preview Mode (Browser):**
1. Step 1: Role selection (Admin / Caissier buttons)
2. Step 2: Password entry (username is the selected role)
3. Demo credentials displayed on screen

**Production Mode (Electron):**
1. Single step: username + password form
2. Authenticates against SQLite database via IPC

### State Management
- `showPassword` — toggle password visibility
- `loginStep` — 1 or 2 (preview mode only)
- `selectedRole` — 'admin' or 'caissier' (preview mode only)
- `error` — error message string
- `loading` — submitting state
- Form is UNCONTROLLED (`formRef`) — browser manages input values natively

### IPC Calls
- `authenticateUser(username, password)` → `authenticate-user`
- `authSessionSet(userId, userData)` → `auth-session-set`

### Events
- None directly — parent `App.jsx` handles post-login routing

## Module 2: First-Time Admin Setup (`SetupWizard.jsx`)

### UI Layout
- Full-screen gradient background (blue/indigo)
- Card with gradient header (Shield icon)
- "Bienvenue dans votre POS!" title
- Info badge showing username "admin" (fixed, non-editable)
- Password field (type=password, autofocus)
- Confirm password field (type=password)
- Error display (red banner with AlertCircle)
- Submit button: "Créer mon compte et démarrer"
- Loading spinner during creation
- Footer: "Configuration sécurisée" with green pulsing dot

### Form Data
- `password` — the new admin password
- `confirmPassword` — confirmation

### Validation
1. Both fields required
2. Passwords must match
3. Minimum 6 characters

### Backend Flow
1. Call `createAdminUser({ username: 'admin', password })` via IPC
2. If "admin already exists" error → fallback to `updateAdminPassword(password)`
3. After password update → `authenticateUser('admin', password)` to get user payload
4. Call `onComplete(adminUser)` → parent calls `setUserDirectly(adminUser)`

### IPC Calls
- `createAdminUser(userData)` → `create-admin-user`
- `updateAdminPassword(password)` → `update-admin-password` (fallback)
- `authenticateUser('admin', password)` → `authenticate-user` (after reset)

## Module 3: Auth Context (`AuthContext.jsx`)

### State
- `user` — current user object or null
- `loading` — initial auth check in progress

### Key Functions

**`checkAuthStatus()`** — On mount:
1. Read `pos_auth` and `pos_user` from localStorage
2. If both exist → parse user JSON
3. In production: validate user exists in DB via `validate-user-exists` IPC
4. If invalid → clear localStorage, reject session
5. Set `user` state

**`login(credentials)`** — Delegates to:
- `loginWithDemoUsers()` in preview mode (hardcoded demo accounts)
- `loginWithDatabase()` in production (IPC `authenticate-user`)

**`logout()`**:
1. Call `logout(userId)` IPC (closes DB session)
2. Clear `authSessionClear` IPC
3. Clear `user` state + localStorage

**`setUserDirectly(userData)`** — For first-time setup auto-login:
1. Set `user` state
2. Save to localStorage

### Session Persistence
- User data stored in `localStorage` under keys `pos_auth` and `pos_user`
- On app restart, `checkAuthStatus()` restores from localStorage
- Production mode validates against DB on every restart

## Module 4: Backend Auth (`ElectronAuthManager.cjs`)

### `needsFirstTimeSetup()`
1. Query `users WHERE role='admin' AND is_active=1`
2. If no admins → return true (first-time)
3. If admins exist but none have a non-empty `password_hash` → return true
4. Otherwise → return false

### `needsAdminPasswordReset()`
1. Find admin user by username='admin'
2. If no admin → false
3. If `password_hash` is empty/null → true
4. If `password_hash` is literally 'admin123' (plain text) → true
5. If bcrypt.compare('admin123', hash) succeeds → true
6. Otherwise → false

### `createAdminUser(userData)`
1. Check `needsFirstTimeSetup()` — if false, throw "Admin user already exists"
2. Hash password with bcrypt (10 salt rounds)
3. INSERT into `users` table
4. Return user object (id, username, full_name, role, permissions)

### `updateAdminPassword(newPassword)`
1. Find admin by username='admin'
2. Hash new password
3. UPDATE `password_hash` in users table

### `authenticateUser(username, password)`
1. Find user by username
2. Check `is_active`
3. Check `locked_until` (brute-force lockout)
4. bcrypt.compare(password, hash)
5. On failure: increment `login_attempts`, lock if >= maxAttempts
6. On success: reset attempts, insert session, log audit event
7. Return user object with permissions

### Brute-Force Protection
- `max_login_attempts`: default 5
- `lockout_duration_minutes`: default 15
- Tracks `login_attempts` and `locked_until` on user row
- Audit logs: LOGIN_FAILED, ACCOUNT_LOCKED, LOGIN_SUCCESS

### Password Hashing
- bcrypt with 10 salt rounds
- `bcrypt.compare()` for verification
- `bcrypt.hash()` for creation/update

### Session Management
- `user_sessions` table: user_id, login_time, logout_time, session_duration
- `activeSessions` Map (in-memory, per WebContents ID)
- Set on login, cleared on logout

### Audit Logging
- All auth events logged to `audit_logs` table
- Events: LOGIN_SUCCESS, LOGIN_FAILED, ACCOUNT_LOCKED, PASSWORD_CHANGE, PASSWORD_RESET, USER_CREATE, USER_UPDATE, USER_DELETE

## Module 5: Routing & Guards

### App.jsx Flow
1. Check `isPreviewMode()` → skip setup in preview
2. `checkFirstTimeSetup()`:
   - Call `needsFirstTimeSetup()` IPC
   - Call `needsAdminPasswordReset()` IPC
   - If either true → `isFirstTime = true`
3. If `isFirstTime` → render `<SetupWizard onComplete={handleSetupComplete} />`
4. If not authenticated → render `<POSWithAuth config={config} />`
5. If authenticated → render `<MainPOSApp />` with routes

### Route Guards
- `ProtectedRoute` — wraps all main routes (redirects to login if not authenticated)
- `AdminOnlyRoute` — wraps `/user-admin` and `/user-management` (redirects non-admins to `/`)

### Auto-Login After Setup
1. SetupWizard calls `onComplete(adminUser)`
2. App.jsx calls `setUserDirectly(adminUser)` on AuthContext
3. AuthContext sets `user` state + saves to localStorage
4. App re-renders → `user` is set → shows MainPOSApp

## Security Analysis

### Strengths

| Area | Detail |
|------|--------|
| Password hashing | bcrypt with 10 salt rounds — industry standard |
| Brute-force protection | Configurable max attempts + lockout duration |
| Audit logging | All auth events recorded with timestamps |
| Session tracking | DB sessions + in-memory IPC sessions |
| Demo password detection | `needsAdminPasswordReset()` catches 'admin123' |
| User validation on restart | Production mode validates localStorage user against DB |
| Input validation | Username format, email format, phone format, role whitelist |
| Last admin protection | Cannot deactivate/delete the last admin |
| Self-deletion prevention | Users cannot delete their own account |
| Password validation | Configurable min length, uppercase, numbers, special chars |

### Issues Found

| Severity | Issue | Location |
|----------|-------|----------|
| **Critical** | Demo credentials displayed on login screen in preview mode — visible to anyone who opens the POS in browser | `POSWithAuth.jsx:246-263` |
| **Critical** | Demo passwords are hardcoded in TWO places: `AuthContext.jsx:82-103` AND `POSWithAuth.jsx:41-63` — if one is updated and the other isn't, they diverge | `AuthContext.jsx:82`, `POSWithAuth.jsx:41` |
| **Critical** | `setUserDirectly()` bypasses all authentication — any code that calls it can log in as any user without password | `AuthContext.jsx:187-192` |
| **High** | SetupWizard username is hardcoded to 'admin' — no way to change it during setup, but the field IS sent to backend (`userData.username`), so if someone modifies the IPC call they could create a different admin | `SetupWizard.jsx:44` |
| **High** | No rate limiting on `create-admin-user` IPC — could be called repeatedly if the first-time check has a race condition | `ipc-auth-handlers.cjs:76-84` |
| **High** | `needsAdminPasswordReset()` returns false on error (line 103) — if the DB query fails, the admin is NOT forced to reset, potentially leaving the default password active | `ElectronAuthManager.cjs:103` |
| **High** | `validatePassword()` is NOT called during SetupWizard — the setup only checks `length >= 6`, ignoring security settings (uppercase, numbers, special chars) | `SetupWizard.jsx:31-33` |
| **High** | `update-admin-password` IPC has NO auth check — anyone with IPC access can reset the admin password without knowing the old one | `ipc-auth-handlers.cjs:66-74` |
| **Medium** | `activeSessions` Map uses `event.sender.id` (WebContents ID) as key — if the renderer is destroyed and recreated (e.g., page reload), the old session is orphaned and never cleaned up | `ipc-session-store.cjs:6` |
| **Medium** | Session timeout (`session_timeout_minutes`) is configured but NEVER enforced — the `checkAuthStatus()` only validates user existence, not session age | `AuthContext.jsx:34-56` |
| **Medium** | `user_sessions` table has no cleanup — old sessions accumulate indefinitely, no purge mechanism | `ElectronAuthManager.cjs:344` |
| **Medium** | `login_attempts` counter is not incremented atomically — race condition if two login attempts happen simultaneously | `ElectronAuthManager.cjs:327-338` |
| **Medium** | Error messages differ between "user not found" and "wrong password" — attacker can enumerate valid usernames | `ElectronAuthManager.cjs:302` vs `326` |
| **Medium** | `admin-reset-password` IPC has NO role check — any authenticated user could potentially reset any other user's password | `ipc-auth-handlers.cjs:202-210` |
| **Medium** | `change-password` IPC has NO role check — any user can change any other user's password if they know the old one | `ipc-auth-handlers.cjs:192-200` |
| **Low** | `Login.jsx` is an empty file (0 lines) — dead code, should be removed | `Login.jsx` |
| **Low** | `AuthContext-new.jsx` is an empty file (0 lines) — dead code, should be removed | `AuthContext-new.jsx` |
| **Low** | Excessive `console.log` / `console.error` statements with `[DIAG]` prefixes — debug noise in production | `ElectronAuthManager.cjs` (throughout) |
| **Low** | `checkUserPermission()` uses string interpolation for SQL column name (`can_${action}`) — not a SQL injection risk (action is validated by caller pattern) but fragile | `ElectronAuthManager.cjs:552` |
| **Low** | `hasPermission()` in AuthContext checks `user.permissions.includes('all')` but permissions could be `undefined` if user object is malformed | `AuthContext.jsx:194-198` |

## Data Flow: Complete Auth Lifecycle

### First Launch (Production)

```
1. App.jsx mounts
2. checkFirstTimeSetup() calls:
   a. needsFirstTimeSetup() → IPC → ElectronAuthManager
      → Query: SELECT id FROM users WHERE role='admin' AND is_active=1
      → No rows found → returns true
   b. needsAdminPasswordReset() → IPC → ElectronAuthManager
      → Query: SELECT password_hash FROM users WHERE username='admin'
      → No user found → returns false
3. isFirstTime = true → renders SetupWizard
4. User enters password + confirms
5. SetupWizard calls:
   a. createAdminUser({ username: 'admin', password }) → IPC
      → needsFirstTimeSetup() check → true (no admin yet)
      → bcrypt.hash(password, 10)
      → INSERT INTO users (username='admin', password_hash=..., role='admin')
      → Returns { id, username, role, permissions }
   b. onComplete(adminUser) → App.jsx
      → setUserDirectly(adminUser) → AuthContext
      → Sets user state + localStorage
6. App re-renders → user is set → MainPOSApp shown
7. Admin is logged in without entering credentials again
```

### Subsequent Launch (Production, Admin Exists)

```
1. App.jsx mounts
2. checkFirstTimeSetup() calls:
   a. needsFirstTimeSetup() → admin exists with password_hash → false
   b. needsAdminPasswordReset() → admin exists, hash is bcrypt, compare('admin123') fails → false
3. isFirstTime = false
4. AuthContext.checkAuthStatus() runs:
   a. localStorage has pos_auth + pos_user
   b. Parse pos_user JSON
   c. Production: validate-user-exists IPC → true
   d. Set user state from localStorage
5. User is auto-logged in from previous session
```

### Login (Production, Existing User)

```
1. No user in state → POSWithAuth renders
2. User enters username + password
3. handleLogin() → login({ username, password })
4. AuthContext.loginWithDatabase():
   a. authenticateUser(username, password) → IPC
   b. ElectronAuthManager.authenticateUser():
      - Find user by username
      - Check is_active
      - Check locked_until
      - bcrypt.compare(password, hash)
      - On success: reset attempts, INSERT session, log audit
      - Return user object with permissions
   c. activeSessions.set(webContentsId, { userId, userData })
5. AuthContext stores user in state + localStorage
6. POSWithAuth re-renders → user is set → MainPOSApp shown
```

### Logout

```
1. User clicks logout
2. AuthContext.logout():
   a. logout(userId) IPC → UPDATE user_sessions SET logout_time
   b. authSessionClear IPC → activeSessions.delete(webContentsId)
   c. Clear user state + localStorage
3. App re-renders → no user → POSWithAuth shown
```

## Summary of Issues

### By Severity

| Severity | Count | Key Examples |
|----------|-------|-------------|
| **Critical** | 3 | Demo credentials on screen, duplicate demo user arrays, `setUserDirectly` bypasses auth |
| **High** | 4 | No auth on `update-admin-password`, no password validation in SetupWizard, error-based username enumeration, `needsAdminPasswordReset` swallows errors |
| **Medium** | 6 | Session timeout not enforced, orphaned sessions, no session cleanup, non-atomic login_attempts, no role checks on password reset, duplicate login_attempts race |
| **Low** | 5 | Dead files (Login.jsx, AuthContext-new.jsx), debug noise, fragile column interpolation, undefined permissions check |

### Top 5 Priorities

1. **Remove demo credentials from POSWithAuth.jsx** — Never display passwords on screen, even in preview mode. Use a single source of truth for demo users.

2. **Add auth checks to `update-admin-password`, `change-password`, `admin-reset-password`** — These IPC handlers have zero server-side authorization. Any renderer process can call them.

3. **Call `validatePassword()` in SetupWizard** — The setup wizard only checks `length >= 6`, ignoring all security settings (uppercase, numbers, special chars).

4. **Enforce session timeout** — The `session_timeout_minutes` setting exists but is never checked. Add validation in `checkAuthStatus()`.

5. **Unify demo user arrays** — `AuthContext.jsx` and `POSWithAuth.jsx` both define demo users independently. Extract to a single shared constant.
