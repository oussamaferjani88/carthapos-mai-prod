EXECUTIVE SUMMARY
================================================================================
The core "generate a POS from a config" flow exists and works end-to-end.
What is MISSING is the "save the generator state permanently + reload it into
the wizard + regenerate/modify/version" layer.

KEY FINDING: The generator config IS already persisted in the database, but
through a LOSSY typed-column whitelist (backend/routes/licenses.js
filterValidConfigurationFields). Every field not in the LicenseConfiguration
schema is silently dropped at license-creation time. So "save the full
generator state" does NOT currently work for ~50% of the wizard options.

There is NO PosProject / BuildHistory / Version model. "Regenerate" exists as
a one-shot dashboard action (POST /pos/generate with a licenseId) but there is
no way to reload a saved config into the wizard, no versioning, no "My POS
Projects" page, no drafts.

================================================================================
1. CURRENT ARCHITECTURE
================================================================================
Flow: Client opens /pos-generator (POSGeneratorPage.tsx) → completes a
5-step wizard → Generate → creates a License row in DB → POST /pos/generate
→ generator engine copies pos-template/ → patches config/theme/modules →
optional .exe build → download.

Frontend wizard (frontend/src/pages/pos/POSGeneratorPage.tsx):
  Step 1      Basic config (client + sector)
  Step 2      Module selection (grid of modules)
  Step 2.5    Template vs custom choice
  Step 2.7    Template gallery (4 hardcoded: café, restaurant, retail, pharmacy)
  Step 3      POSCustomizer (design studio, full-screen or inline)
  Step 4      License config (type, binding, USB)
  Step 5      Results / download (polls /pos/build-status/:licenseId)

State hooks (all React-memory only, NOT persisted):
  usePOSGenerator.ts   step, status, generationResult {license, licenseFile, posApplication}
  usePOSConfiguration.ts  configuration (Record<string,any>, ~95 fields)
  usePOSModules.ts     selectedModules: string[] (module ids)
  page-local formData  clientId, sector, licenseType, bindingType, expirationDate, selectedUSB, forcePortableMode

Generation trigger (usePOSGenerator.ts:84-177):
  1. POST /licenses            -> creates License + LicenseModule rows +
                                 LicenseConfiguration row (whitelist-filtered)
  2. POST /pos/generate        -> backend reloads license + modules +
                                 configuration, runs generatePOSApplication()
  3. optional USB write
  4. result set -> step 5

Backend generator engine (backend/utils/generators/*):
  index.js generatePOSApplication(license, outputPath, options)
    -> ProjectBuilder (copy template into generated-pos/pos-<client>-<key>)
    -> AssetManager (config files, asset refs)
    -> ModuleFilter (comment-out disabled module nav/routes)
    -> DependencyManager / BuildSystemManager (robocopy node_modules, vite +
       electron-builder -> .exe)
    -> ThemeCustomizer, FilePatcher
  POST /pos/generate (routes/pos.js:19) RELOADS the license from DB each time,
  so regeneration-from-DB already works mechanically.

Download: GET /pos/download?path=&licenseId= (routes/pos.js:415) serves the
.exe, or a source zip fallback when not built locally.

2. EXISTING PERSISTENCE
================================================================================
Database (the ONLY durable persistence):

                       buildProjectPath, buildProjectName, buildRunId, ...)
  LicenseModule        M:N License<->Module (isEnabled)

saved configs. Only auth keys + AccessMode keys + UI theme + a dead posLayout
key exist.

There is NO storage of:
  - the complete wizard state object
  - build history per license (only last buildStatus/path on the License)
  - versions of a configuration
  - a "project" concept

UserPosConfiguration model EXISTS in schema.prisma:316-329 but is DEAD CODE —
not referenced anywhere in backend JS. It only holds businessName/sector/
outputPath/buildStatus/lastBuiltAt (not the full config). It was partially
dropped by the BI migration (buildStatus column). Do NOT revive blindly.

6. EXISTING GENERATOR CONFIGURATION — SERIALIZABILITY
================================================================================
The full configuration object = { clientId, sector, licenseType, bindingType,
expirationDate, selectedModules: string[], configuration: {...} }.

It IS JSON-serializable (plain object; logo/favicon are base64 data-URL
strings). Proof: POSCustomizer already exports/imports the config as
pos-config.json via JSON.stringify/parse.

Restorability gap — THE CORE PROBLEM:
  backend/routes/licenses.js:137 filterValidConfigurationFields uses a whitelist
  of ~55 valid fields matching LicenseConfiguration columns. On license create/
  update, the config is reduced to ONLY those keys.

Fields the wizard has but that are DROPPED (never persisted):
  businessAddress/Phone/Email/Website/TaxId (present in ensureStringFields but
  NOT in validFields), footerText, receiptHeader/receiptFooter/receiptShowLogo/
  receiptShowQR, requireLogin, sessionTimeout, showUserInfo, allowGuestMode,
  allowRefunds, allowDiscounts, allowPriceOverride, requireManagerApproval,
  currencyPosition, dateFormat, timeFormat, numberFormat, cardBorderColor,
  headingFontSize, spacing, cardPadding, navbarWidth, navbarHeight, showNavbarBrand,
  contentMaxWidth, sidebarCollapsible, animationsDuration, buttonSize,
  buttonHoverEffect, cardCornerRadius, cardShadow, tableRowHover,
  tableCompactMode, statsCardStyle, highContrast, largeText, reduceMotion,
  lazyLoading, imageOptimization, cacheData, sales{}, inventory{}, reports{},
  previewDevice, features, businessLogo, forcePortableMode, requireUSBLicense,
  customFont, components, receipt* ...

Result: if a client toggles "Require login", sets receipt footer, uploads a
logo, chooses date/number formats, enables refunds, etc., then logs out and
logs back in — NONE of that survives. The generator engine even reads several
of these keys at build time (AssetManager/ThemeCustomizer reference features,
businessLogo, forcePortableMode, requireUSBLicense, customFont, receipt*), so
regenerating today reproduces only the ~55 whitelisted fields and everything
else silently falls back to defaults.

What must change (minimal):
  Persist the FULL config as a JSON snapshot alongside the typed row, e.g.
  add LicenseConfiguration.rawConfig Json? (or a small PosConfigSnapshot
  table) that stores the complete configuration + selectedModules + sector +
  licenseType + bindingType + expirationDate WITHOUT whitelist filtering, and
  include it in GET /licenses responses. Then the wizard can prefill by
  spreading that snapshot (usePOSConfiguration initialConfig already merges).

7. VERSIONING
================================================================================
Current architecture does NOT support versions. One License = one config.
Regenerate overwrites buildStatus/buildProjectPath on the SAME License; the
config is not versioned. Creating a modified config today = creating a NEW
License (duplicate).

Natural options (analysis only, NO implementation):
  A) New License per generate-from-modified config (each saved config =
     a new License row). Pros: zero schema change for versioning, every
     version already has its own download/build path, dashboard card already
     lists all licenses as separate rows. Cons: licenseKey proliferation,
     need a display grouping ("versions of same project").
  B) Add version + parentProjectId to License (or a PosProject parent table).
     Pros: proper project grouping. Cons: new model/migration, dashboard
     changes.
  RECOMMENDED for minimal change: Option A — treat each saved configuration +
  generate as its own License, and group them in the UI by businessName. Add a
  ConfigVersion counter only if strict V1/V2 labeling is required. Versioning
  can be decided after the audit as the task allows.

9. RISKS
================================================================================
- Lossy persistence is the #1 blocker: without P0, "modify & regenerate" will
  silently drop ~half the wizard options. Must ship P0 before P1/P2.
- rawConfig Json with base64 logo/favicon can be large; keep rawConfig bounded
  (cap logo size) or move logo to filesystem path. Acceptable for phase 1.
- Existing DB rows have no rawConfig: old POS projects can still regenerate
  (typed columns) but with reduced fidelity. Note in UI or accept.
- Dead legacy code (UserPosConfiguration, Generator.tsx iframe, v1 routes)
  must NOT be reused or revived.
- POS engine (pos-template + utils/generators + routes/pos.js) is on the
  DO-NOT-MODIFY list. P0 only touches licenses.js filtering + schema; do NOT
  change generator behavior.
- buildStatus semantics (source_ready/completed/building) reused as-is.
- The user-mode client filter (GET /licenses?userId=) uses clientId-prefix
  matching + email; with real auth the client is linked via Client.userId —
  verify the feed returns correct licenses for the authenticated client
  (may need the feed to also match Client.userId).
