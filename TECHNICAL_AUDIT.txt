3.1 SALES → INVENTORY Disconnect
─────────────────────────────────
CURRENT: Sale completed → nothing happens to stock
SHOULD: Sale completed → for each item: INSERT stock_movement (out) →
        UPDATE products.stock → if stock <= min_stock: trigger alert

───────────────────────────────
CURRENT: Sale completed → nothing sent to kitchen
SHOULD: Sale completed → if order_type is 'dine-in': INSERT kitchen_order →
        Kitchen display updates → audio alert
IMPACT: Waiters must manually enter orders into kitchen (double work)

3.3 SALES → CUSTOMER STATS Disconnect
──────────────────────────────────────
CURRENT: Sale linked to customer_id but no stats auto-update
SHOULD: Sale completed → if customer_id set: auto-update customer stats
        (total_spent, visit_count, last_visit, favorite_products)
IMPACT: Customer stats are stale unless manually recalculated

3.4 SALES → CASH REGISTER Disconnect
─────────────────────────────────────
CURRENT: Sale completed → no notification to cash register
SHOULD: Sale completed → if shift active: update shift totals
        (cash_sales/card_sales/other_sales based on payment_method)

3.5 SALES → RECEIPT Disconnect
───────────────────────────────
CURRENT: Sale completed → nothing printed
SHOULD: Sale completed → generate receipt from template → send to thermal printer
IMPACT: No receipt automatically generated. Cashier must reprint manually.

3.6 SALES → REPORTS Disconnect
───────────────────────────────
CURRENT: Sale completed → custom event emitted → Dashboard refreshes
SHOULD: Sale completed → Dashboard refreshes, Reports data is live
        (Reports currently uses demo data only, so it never updates)

3.7 CASH REGISTER → SALES Disconnect
─────────────────────────────────────
CURRENT: Shift open → sales happen independently
SHOULD: If no shift open: warn cashier "Open register first"
        Or: auto-require shift to be open before processing sales

3.8 TABLE → KITCHEN Disconnect
───────────────────────────────
CURRENT: Table assigned to sale → no kitchen order created

        with table_number, items, notes
IMPACT: Kitchen doesn't know which table to serve

4. ARCHITECTURE PROBLEMS
═══════════════════════════════════════════════════════════════════════════════════════

4.1 MEGA-COMPONENTS
────────────────────
Component           │ Lines │ Problem
──────────────────────────────────────────
Sales.jsx           │ 1157  │ ALL sales logic in one file. Cart, products, payment,
                    │       │ tables, search, calculator, held orders ALL in one component.
                    │       │ Should be split: SalesPage, ProductGrid, CartPanel,
                    │       │ PaymentModal, TableSelector, Calculator, etc.
Reports.jsx         │ 1013  │ ALL reports in one file. Structure is good but should be
                    │       │ split: ReportFilters, TransactionTable, ChartPanel, etc.
ReceiptDesigner.jsx │ 1082  │ Large but well-structured with tabs. Acceptable.
Dashboard.jsx       │ 551   │ Inline Card/Badge components shadow shadcn/ui.

4.2 DUPLICATE LOGIC
───────────────────
- Format price: Every page has its own formatPrice() function (Sales, Products,
  Dashboard, Reports, Customers, etc.). Should be a shared utility.
- Theme config: Every page repeats the same getConfig() pattern:
  ```
  const { config: electronConfig } = useAppConfig();
  const getConfig = () => {
    if (electronConfig?.theme) return POSConfiguration.createConfig(electronConfig.theme);
    return POSConfiguration.createConfig({});
  };
  ```
  This is copy-pasted in ~15 files. Should be a single useConfiguredTheme() hook.
- Currency: POSConfiguration has currency info but CashRegister.jsx hardcodes €.
- Error handling: Inconsistent — some pages use alert(), some use localNotification,
  some use console.error only. No centralized error handler.

4.3 DUPLICATE STATE
───────────────────
- Products are loaded from DB in both Products.jsx and Sales.jsx independently
  (separate IPC calls, separate state, no cache invalidation).
- Tables are loaded in Tables.jsx and Sales.jsx independently.
- No shared data layer / cache. Every page fetches its own data.

4.4 BAD FOLDER STRUCTURE
─────────────────────────
- /src/electron/handlers/ contains both class-based handlers (IPCAuthHandlers,
  IPCDatabaseHandlers, IPCAppHandlers) and function-based handlers
  (registerSalesHandlers, registerCustomerHandlers, etc.) — inconsistent pattern.
- /src/electron/managers/ contains only WindowManager.cjs — ElectronWindowManager
  is at /src/electron/ level. Inconsistent.
- /src/lib/ contains mixed concerns: POSConfiguration (config), utils.js (cn utility),
  hardware/ (I/O), keyboard/ (shortcuts), notifications/, system/ — too many
  responsibilities in one directory.

4.5 TIGHT COUPLING
───────────────────
- window.electronAPI is accessed directly everywhere. No abstraction layer.
  If electronAPI changes signature, every page breaks.
- All pages import POSConfiguration directly instead of through a central hook.
- Dashboard defines inline Card/Badge components instead of using shadcn/ui
  (tightly coupled to its own rendering).

4.6 POOR SEPARATION OF CONCERNS
────────────────────────────────
- ProductFormDialog.jsx contains form logic + validation + submission as a single component.
- Reports.jsx handles: data loading, filtering, sorting, pagination, chart rendering,
  export, detail modal — all in one file.
- Sales.jsx handles: product grid, cart, payment, table selection, calculator,
  held orders, notifications, animations.

RECOMMENDED ARCHITECTURE:
src/
  api/                  ← Data access layer (wraps electronAPI)
    client.js           ← Singleton electronAPI client
    products.js         ← productApi.getAll(), productApi.create(), etc.
    sales.js
    customers.js
    ...
  hooks/                ← React hooks (centralized data hooks)
    useProducts.js      ← Cached, invalidated on mutation
    useSales.js
    useCustomers.js
    useTheme.js         ← Single theme hook (replaces all getConfig() copies)
    ...
  components/           ← UI components
    ui/                 ← shadcn/ui primitives
    layout/             ← Layout, Header, Navbar, Content
    forms/              ← Form components (ProductForm, CustomerForm, etc.)
    charts/             ← Chart wrappers
    ...
  pages/                ← Page components (thin — orchestrate, no business logic)
  lib/                  ← Utilities
    format.js           ← formatPrice(), formatDate(), etc.
    constants.js
    validation.js
  electron/             ← Main process code
    handlers/           ← All class-based handlers (consistent pattern)
    managers/           ← All managers
    services/           ← Business logic services
  contexts/             ← React contexts

5.2 DUPLICATE / OVERLAPPING HANDLERS
─────────────────────────────────────
- ipc-database-handlers.cjs provides generic database:query + database:execute
  but specific handlers also exist (ipc-sales, ipc-customer, etc.) — security
  concern: generic query allows arbitrary SQL from renderer.

- ipc-sales-handlers.cjs and ipc-database-handlers.cjs both access the database
  via different patterns (class-based vs function-based, callback vs promise).

5.3 WRONG RESPONSIBILITIES
───────────────────────────
- ipc-database-handlers.cjs handles business logic (get-products, get-tables)
  instead of being a pure data access layer. This creates tight coupling.
- ipc-auth-handlers.cjs manages password resets, user creation, AND audit logging
  — too many responsibilities in one handler.

5.4 SECURITY ISSUES
────────────────────
- Generic database:query handler (line 53-60) accepts arbitrary SQL strings from
  the renderer. A compromised renderer could execute DROP TABLE or read any data.
  Mitigation: Remove or restrict to parameterized, whitelisted queries.
- No input validation/sanitization on any IPC handlers.
- user_id and user_name are sent from renderer (can be forged). Should be
  derived from the authenticated Electron session.
- password_hash for 'admin123' default may persist in some generated databases
  (the needsAdminPasswordReset check suggests this is a known issue).

5.5 MISSING VALIDATION
───────────────────────
- No handler validates that required fields are present.
- No handler validates data types (string, number, etc.).
- No handler validates that the requesting user has permission for the action.
- user_modules table supports permissions but they're never checked in handlers.

5.6 MISSING TRANSACTIONS
─────────────────────────
- database:transaction handler is a TODO stub (line 73-80).
- addSale in ipc-sales-handlers.cjs creates sale + sale_items + updates table
  status as separate non-transactional operations. If one fails, data is inconsistent.
- No rollback capability anywhere.

8.7 UNOPTIMIZED CHARTS

- Reports charts are wrapped in ResponsiveContainer — good practice.
- No chart memoization — if parent re-renders, charts re-render.

PERFORMANCE VERDICT: Acceptable for small datasets (< 10K sales).

═══════════════════════════════════════════════════════════════════════════════════════

WHY THIS IS THE #1 PRIORITY:
─────────────────────────────

1. Without settings persistence, NO configuration survives a restart.
   - Business name, currency, tax rate → lost
   - Theme customization → lost
   - Receipt template → lost
   - Printer configuration → lost
   - Backup schedule → lost
   This makes the application unusable for any real business.

2. Settings is a DEPENDENCY for EVERY OTHER MODULE.
   - Sales needs currency and tax rate
   - Receipt Designer needs paper size and header/footer
   - Hardware Settings needs printer and cash drawer config
   - Dashboard needs business name
   - Reports needs currency and tax info
   Without settings persistence, none of these modules can be configured.

3. It blocks ALL other improvements.
   - Before making Reports use real data: must store report preferences
   - Before connecting Receipt Designer to printing: must store template
   - Before making any configuration change: must be able to save it
   Every other module depends on Settings working.

4. It's the EASIEST fix with the HIGHEST impact.
   - Add a settings table to the database
   - Implement 3 IPC handlers (get, set, getAll)
   - Connect the Settings page save button
   - Total estimated effort: 2-3 days
   - Impact: Transforms the app from "demo" to "real"

5. It's a SINGLE POINT OF FAILURE.
   - The TODO stubs are clearly marked
   - The Settings page UI is already built
   - The only missing piece is 3 IPC handler implementations
   - No architectural changes needed
   - No refactoring needed
   - Straightforward implementation
