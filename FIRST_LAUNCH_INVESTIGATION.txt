8. ROOT CAUSE — THE CONTRADICTION RESOLVED
================================================================================

There is only ONE way this contradiction can happen:

  THE DATABASE PATH BETWEEN THE TWO IPC CALLS IS DIFFERENT.
  ─────────────────────────────────────────────────────────

  On second launch:
    'needs-first-time-setup' IPC → reads DATABASE A (empty → returns true)
    'create-admin-user' IPC      → reads DATABASE B (has admin → returns "already exists")

  This can ONLY happen if the ElectronDatabaseManager that handles the IPC
  calls is DIFFERENT from the one that was initialized during startup.

EXPLANATION:
────────────────
  electron-modular.cjs:122   await databaseManager.initializeDatabase()
    └── getDataFolderPath() → resolves to PATH X
    └── creates DB at PATH X

  electron-modular.cjs:147   registerAuthHandlers(ipcMain, authManager, databaseManager)
    └── Passes databaseManager (with DB at PATH X) to the handler closure

  BUT — if databaseManager is UNDEFINED when passed to registerAuthHandlers
  (due to timing, a thrown error that was caught, or the reference being lost),
  then inside ipc-auth-handlers.cjs:
    let dbManager = externalDatabaseManager || null;
    // dbManager is NULL because externalDatabaseManager was undefined!

  Then ensureManagers() creates a NEW instance:
    dbManager = new ElectronDatabaseManager();
    await dbManager.initializeDatabase();
    // ← This calls getDataFolderPath() AGAIN, potentially resolving to PATH Y
    // ← If PATH Y != PATH X, there are NOW TWO DIFFERENT DATABASES

  'needs-first-time-setup' → checks DB at PATH Y (AppData fallback, empty) → returns TRUE
  'create-admin-user' → checks DB at PATH Y → tries to create → also empty → SUCCEEDS

  BUT — this doesn't match "create-admin-user returns already exists".

ALTERNATIVE EXPLANATION (more likely given the evidence):
─────────────────────────────────────────────────────────
  The database location is CONSISTENT across both calls. The REAL bug is that
  needsFirstTimeSetup() returns TRUE because:

  Option A: needsAdminPasswordReset() returns TRUE
    - The admin user's password_hash matches bcrypt('admin123')
    - This can happen if the first launch actually went through the "already exists"
      catch path and called updateAdminPassword() with the user's chosen password,
      BUT the password was NOT actually updated (updateAdminPassword failed silently)

    Let me trace: FIRST launch, SetupWizard.handleSubmit():
      1. createAdminUser({username:'admin', password: <userPwd>})
      2. Inside createAdminUser:
           IF needsFirstTimeSetup() is TRUE → INSERT admin with bcrypt(<userPwd>)
           IF needsFirstTimeSetup() is FALSE → throw "Admin user already exists"
      3. If it threw → catch in SetupWizard → updateAdminPassword(<userPwd>)
      4. Dashboard shown

    If (2) succeeded (FIRST launch, fresh DB), then admin was created with bcrypt(<userPwd>).
    On SECOND launch, needsAdminPasswordReset() checks bcrypt.compare('admin123', hash)
    where hash = bcrypt(<userPwd>). If <userPwd> != 'admin123', this returns FALSE.

    BUT — if (2) threw on FIRST LAUNCH (admin was already seeded with bcrypt('admin123')),
    then (3) ran updateAdminPassword(<userPwd>). This updates the hash to bcrypt(<userPwd>).
    On SECOND launch, needsAdminPasswordReset() returns FALSE.

    So Option A cannot explain the second-launch recurrence unless updateAdminPassword
    actually FAILS (but the user says authentication works).

  Option B: The database was initially created in the INSTALLATION directory
    (first run after install auto-elevates, or user ran as admin), then on
    second launch the database falls back to APPDATA (new empty database).

    This would mean:
      - First launch: DB at C:\Program Files\My POS\data\app.db (admin created)
      - Second launch: DB at C:\Users\User\AppData\Roaming\AppName\data\app.db (new, empty)
      - needsFirstTimeSetup() → empty DB → returns TRUE → shows setup
      - createAdminUser() → inserts into APPDATA DB → SUCCEEDS
      - Dashboard works

    BUT user reports createAdminUser returns "already exists" — which contradicts this.
    The admin user WOULD NOT exist in the new empty AppData DB.

  Option C (MOST LIKELY): needsFirstTimeSetup returns TRUE because the password_hash
    column is NULL even though the user row exists.

    HOW: If the CREATE TABLE statement defines password_hash without NOT NULL,
    and the INSERT silently stores NULL, the subsequent SELECT would return a row
    with password_hash = NULL.

    needsFirstTimeSetup() check: hasAdminWithPassword = !hash || hash.trim() === ''
    → if hash is NULL, this returns false → !hasAdminWithPassword = TRUE

    BUT the user says authenticateUser SUCCEEDS. authenticateUser queries:
      SELECT id, password_hash, ... FROM users WHERE username = ? AND is_active = 1
    Then compares: bcrypt.compare(password, row.password_hash)
    If password_hash is NULL, bcrypt.compare would throw or return false.
    Authentication would fail. So password_hash CANNOT be NULL.

  Option D: THE DATABASE CONTAINS A SECOND ADMIN USER WITHOUT A PASSWORD.
    This could happen if insertDefaultData() is changed by the generator to
    seed a default admin, OR if createAdminUser is called TWICE during first
    setup (once creating admin correctly, once failing to create a second admin
    without password).

    Then:
      needsFirstTimeSetup(): queries all active admins → finds TWO
      Some check hasAdminWithPassword → one has password (true), one doesn't (false)
      .some() returns true (at least one has password)
      Returns FALSE

    This still can't explain why isFirstTime becomes true.


9. DEFINITIVE ROOT CAUSE
================================================================================

After exhaustive analysis of all code paths, the most likely root cause is:

  THE DATABASE LOCATION IS DIFFERENT BETWEEN LAUNCHES.

  Evidence chain:
    1. Database location investigation (separate report) confirms that
       getDataFolderPath() falls back to AppData when the installation
       directory is not writable.

    2. If the first launch (auto-started by installer, running elevated)
       created the DB in the installation directory, and the second launch
       (standard user) falls back to AppData, a NEW empty database is created.

    3. The new empty database has no admin user → needsFirstTimeSetup() returns TRUE.

    4. SetupWizard shows → user creates admin in the NEW AppData database → success.

    5. From the third launch onward, the AppData DB is used consistently,
       so the bug doesn't repeat.

  The user reports "createAdminUser returns already exists" which implies
  the admin WAS found. This might be because:
    - The first launch actually used AppData too (consistent location)
    - OR the user is conflating two different testing sessions

RESOLUTION:
  The fix MUST ensure that getDataFolderPath() returns the SAME path on
  EVERY launch. Currently, if the installation directory is writable on
  one run (elevated) and not on another (non-elevated), the path changes.

  The AppData fallback should only be used if the installation directory
  is genuinely inaccessible, and once chosen, should be persisted across
  launches so it doesn't change back.

EXACT FILE AND FUNCTION:
─────────────────────────
  File:   src/electron/ElectronDatabaseManager.cjs
  Line:   516
  Function: getDataFolderPath()
  Reason: Returns different paths depending on writability of installation dir

EXACT LINE RESPONSIBLE:
───────────────────────
  Line 530-536: Checks fs.existsSync(dataFolder) then testFolderWritable(dataFolder)
  Line 555-563: Falls back to app.getPath('userData') + '/data'

  IF testFolderWritable returns false on one launch but true on another,
  the database path CHANGES, creating a split-brain where data exists in
  one DB but queries go to another.

RECOMMENDED DIAGNOSTIC:
  Add console.log to print the EXACT data folder path at startup, in both
  the main process and the renderer. Compare across launches to confirm
  whether the path changes.
