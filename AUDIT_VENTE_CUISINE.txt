  3. FLUX VENTE → CUISINE (BACKEND)
═══════════════════════════════════════════════════════════════════════════════

  3a. add-sale (vente directe payée)
  ───────────────────────────────────
  Fichier: ipc-sales-handlers.cjs, lignes 20-222

  Étapes:
    1. Insérer l'en-tête de vente (sales)
    2. Insérer les articles (sale_items) + déduire le stock
    3. Libérer la table si assignée
    4. Mettre à jour stats client
    5. Mettre à jour totals du shift actif
    6. CRÉER LES COMMANDES CUISINE (lignes 152-218)

  Logique de création cuisine:
    a) Résoudre le numéro de table (table_id → table_number ou "Comptoir")
    b) Résoudre le nom du serveur (user.full_name)
    c) Chercher les paramètres cuisine des produits (requires_kitchen, preparation_department, preparation_time)
    d) Filtrer: ne garder que les produits avec requires_kitchen === 1
    e) Grouper par preparation_department
    f) Pour chaque groupe, créer UNE commande cuisine via createKitchenOrder()
    g) Le estimated_minutes = max(preparation_time) du groupe

  IMPORTANT: Les commandes cuisine sont créées même sans table assignée ("Comptoir").
  Les commandes cuisine sont créées même pour les ventes pending (mais le stock n'est pas déduit).

  3b. complete-pending-sale (paiement différé)
  ────────────────────────────────────────────
  Fichier: ipc-sales-handlers.cjs, lignes 351-458

  Étapes similaires:
    1. Marquer la vente comme "paid"
    2. Déduire le stock + mouvements
    3. Mettre à jour shift
    4. Mettre à jour stats client
    5. CRÉER LES COMMANDES CUISINE (lignes 406-454) — même logique que add-sale

  BUG IDENTIFIÉ: Les commandes cuisine sont créées deux fois
  ────────────────────────────────────────────────────────────
  Quand une vente est créée en "pending" via add-sale avec status='pending':
    - add-sale crée les commandes cuisine (ligne 152-218) CAR il n'y a plus
      de guard "if (table_id)" — cette protection a été supprimée
    - Ensuite, quand le paiement est confirmé via complete-pending-sale,
      les commandes cuisine sont créées ENCORE une fois (ligne 406-454)

  RÉSULTAT: Double création de commandes cuisine pour les ventes en attente
  de paiement. Les mêmes items apparaissent deux fois dans la cuisine.

  Voir section 13 pour les détails.

  Événement Sales → Products (via DOM):
    window.dispatchEvent(new CustomEvent('sale-completed'))
    → Products.jsx écoute et recharge les données (produits, families)

  VIDE: Aucun événement Sales → Kitchen ou Kitchen → Sales via DOM.
  La communication Sales ↔ Kitchen se fait UNIQUEMENT via la base de données.
  Quand la cuisine met à jour une commande, Sales ne reçoit aucune notification.

  VIDE: Aucun événement Kitchen → Sales pour signaler qu'une commande est "served".
  Il n'y a aucun lien retour: quand la cuisine termine une commande, la vente
  ne le sait pas automatiquement. Il n'y a pas de statut "cuisine_status" sur la vente.

  13. BUGS ET PROBLÈMES IDENTIFIÉS

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #1 — CRITIQUE: DOUBLE CRÉATION DE COMMANDES CUISINE               │
  │ Sévérité: CRITIQUE — Duplique les items cuisine                       │
  └─────────────────────────────────────────────────────────────────────────┘

  Description:
    Quand une vente est créée en statut "pending" puis payée via
    complete-pending-sale, les commandes cuisine sont créées DEUX FOIS.

  Étapes de reproduction:
    1. Créer un produit avec requires_kitchen = true
    2. Ajouter le produit au panier
    3. Cliquer "À payer" (crée une vente pending)
    4. Ouvrir la vente en attente, puis confirmer le paiement

  Résultat:
    • Étape 3: add-sale crée les commandes cuisine (lignes 152-218 de ipc-sales-handlers.cjs)
      Même pour les ventes pending, car la condition `if (table_id)` a été supprimée.
    • Étape 4: complete-pending-sale crée les commandes cuisine ENCORE (lignes 406-454)

  Cause racine:
    add-sale crée des commandes cuisine pour TOUTES les ventes (y compris pending).
    complete-pending-sale crée aussi des commandes pour TOUTES les ventes complétées.
    Il n'y a pas de garde pour éviter la double création.

  Fix recommandé:
    Option A: Ne pas créer de commandes cuisine dans add-sale si status === 'pending'
    Option B: Vérifier s'il existe déjà des kitchen_orders avec sale_id = sale_id
              dans complete-pending-sale avant de créer
    Option C (meilleure): Ajouter une colonne kitchen_orders.created_from_sale
              ou vérifier le double via sale_id unique index

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #2 — MOYEN: Pas de lien retour Vente ← Cuisine                   │
  │ Sévérité: MOYEN — Pas de visibilité sur le statut cuisine côté vente  │
  └─────────────────────────────────────────────────────────────────────────┘

  Description:
    Quand une commande cuisine passe à "completed", la vente correspondante
    ne reçoit aucune notification. Il n'y a pas de statut cuisine sur la vente.

  Impact:
    • Le serveur ne voit pas dans l'historique des ventes si la commande
      cuisine est prête ou non
    • Pas de dashboard montrant la relation vente → état cuisine
    • Pas de notification quand la cuisine a fini une commande

  Fix recommandé:
    • Ajouter un champ `kitchen_status` sur la table `sales`
    • Ou créer une vue/virtual table jointe
    • Ou un système de notification Sales ← Kitchen via IPC

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #3 — MOYEN: Schema BI incomplet                                    │
  │ Sévérité: MOYEN — Données exportées partiellement                     │
  └─────────────────────────────────────────────────────────────────────────┘

  Description:

    sale_id, total, started_at, completed_at, server_name, customer_name,
    department, estimated_minutes, cancel_reason, cancelled_by

  Impact:
    L'export BI ne contient que: id, table_number, items, notes, priority,

  Fix:
    Mettre à jour BiSchemaContract.cjs pour inclure toutes les colonnes

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #4 — FAIBLE: Pas de calcul automatique du total côté backend      │

  Description:
    Dans createKitchenOrder(), le champ `total` est accepté tel quel.
    Le total devrait être calculé côté serveur: sum(item.price * item.quantity)

  Fix:
    Calculer le total dans createKitchenOrder() à partir des items
    au lieu de se fier au paramètre passé par l'appelant.

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #5 — FAIBLE: Pas de nettoyage des anciennes commandes             │
  │ Sévérité: FAIBLE — Croissance indéfinie de la table                   │
  └─────────────────────────────────────────────────────────────────────────┘

  Description:
    La table kitchen_orders ne fait aucun nettoyage automatique.
    Les commandes completed/cancelled s'accumulent indéfiniment.

  Fix:
    Ajouter un mécanisme de purge (ex: supprimer les commandes > 30 jours)
    ou une option dans les paramètres de rétention.

  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BUG #6 — FAIBLE: Aucun feedback temps réel Sales ↔ Kitchen           │
  │ Sévérité: FAIBLE — UX limitée                                         │
  └─────────────────────────────────────────────────────────────────────────┘

    • Kitchen.jsx ne reçoit aucun DOM event de Sales
    • Sales.jsx ne reçoit aucun DOM event de Kitchen
    • La communication est 100% via DB (pas de push)

  Cela signifie que si un serveur modifie une vente pendant que la cuisine
  traite la commande, il n'y a aucune synchronisation.
