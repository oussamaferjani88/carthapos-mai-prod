PART 5: CAFE & RESTAURANT MODE — FULL WORKFLOW
═══════════════════════════════════════════════════════════════════════════════════════

5.1 MORNING: OPENING PROCEDURE
───────────────────────────────
1. Launch → Electron loads app-config.json
2. Auth check → needsFirstTimeSetup() → if no admin, show SetupWizard
3. Login → POSWithAuth → AuthContext.login() → bcryptjs validation
4. Cash Register → CashRegister.jsx → caisse:open-shift IPC
   - Opens new shift with opening float (100 TND default)
   - Records user_id, opening_float, timestamp
   - Shift status set to 'open'

5.2 SERVICE: ORDER FLOW (DINE-IN)
──────────────────────────────────
1. Table Selection → Tables.jsx
   - Visual grid of tables with status colors
   - Click available table → assign to sale
2. Menu → MenuManagement.jsx or Sales.jsx category grid
   - Products displayed by category with images (if enabled)
3. Order Taking → Sales.jsx
   - Add items to cart with quantities
   - Apply modifiers (from MenuManagement: radio/checkbox)
   - Customer assignment (search/create)
   - Discount application
4. Kitchen Order → Kitchen.jsx & ipc-kitchen
   - add-kitchen-order IPC → kitchen_orders table
   - Priority assignment (normal/high)
   - Items stored as JSON
5. Payment → Sales.jsx checkout
   - Payment method selection (cash/card/mobile)
   - Cash: calculate change
   - Card/mobile: mark as paid
6. Receipt → ReceiptDesigner.jsx layout + print
   - Thermal printer integration (lib/hardware/thermalPrinter.js)
   - Auto-print toggle

5.3 SERVICE: ORDER FLOW (TAKEAWAY/DELIVERY)
─────────────────────────────────────────────
1. Takeaway.jsx → order creation
2. Customer info capture (name, phone, address)
3. Order type: takeaway or delivery
4. Same sales flow, but no table assignment
5. Estimated time + preparation tracking

5.4 KITCHEN: PREPARATION FLOW
──────────────────────────────
1. Kitchen.jsx polls for orders (or receives via IPC)
2. Orders grouped by status: pending → preparing → ready
3. Staff clicks to advance status
4. Visual indicators: priority, elapsed time, table number
5. Order completion notification

5.5 EVENING: CLOSING PROCEDURE
───────────────────────────────
1. Cash Register → Close Shift
   - Count each denomination (200, 100, 50, 20, 10, 5, 2, 1, 0.50, 0.20, 0.10, 0.05, 0.02, 0.01)
   - System calculates expected total from sales
   - Actual total from manual count
   - Difference = actual - expected
   - Shift status changes to 'closed'
   - Summary: cash_sales, card_sales, other_sales
2. Reports → Reports.jsx
   - Daily sales report with charts
   - Compare with previous days
3. Optional: BI Export → BiExportModal
   - Export all data as CSV+ZIP with schema validation

5.6 GAPS IN WORKFLOW
────────────────────
❌ No integrated payment terminal communication (EMV, NFC)
❌ No kitchen order display auto-refresh (no WebSocket/SSE)
❌ No offline mode when network/Electron IPC is unavailable
❌ No order splitting or merging
❌ No course management (appetizer → main → dessert timing)
❌ No tip management
❌ No multi-currency support (TND only, configurable currency)
❌ No tax rate configuration per product (global tax only)
❌ No floor plan editor for table layouts

10.3 KEY STRENGTHS
─────────────────
1. Broad feature coverage: 28 pages covering retail, restaurant, and specialized verticals
2. Strong backend foundation: 12 IPC handlers, SQLite with proper schema design
3. BI/analytics module with schema versioning and validation (enterprise-grade)
4. Comprehensive configuration system (200+ properties)
5. Clean separation of Electron main process and renderer
6. Preview mode enables browser-based development without Electron

8. Audit logging for compliance

10.4 KEY WEAKNESSES
───────────────────
1. ~40% of pages use local/hardcoded data instead of persistent storage
2. Settings IPC handlers are TODO stubs (no persistence at all)
3. Notification and error recovery systems forcibly disabled
4. Two files are empty stubs (Login.jsx, UserContext.jsx)
5. Four DB tables used by handlers but missing from schema initialization
6. No TypeScript, no tests, no CI/CD
7. No payment processing integration (manual only)
8. No online ordering, no mobile app
9. Settings/theme changes are not persisted across restarts
10. Error recovery is non-existent (disabled in production)

10.5 FINAL VERDICT
──────────────────
CarthaPOS is a robust, feature-rich POS template with an impressive 28-page UI
and solid Electron/SQLite architecture. It achieves ~69% overall completion with
core functionality (Sales, Products, Customers, Tables, Kitchen) at 80-95%.

The most critical gaps:
  1. Data persistence for 40% of features (local state only)
  2. Missing DB schema for 4 tables (kitchen_orders, appointments, services, suppliers)
  3. Disabled critical systems (notifications, error recovery)
  4. No testing infrastructure

With 3-4 months of focused engineering on Phase 1-2 (stabilizing core + data
persistence), CarthaPOS could reach 85% completion and be production-ready for
small to medium cafes, restaurants, and retail businesses.

Full professional competitiveness (vs Lightspeed/Toast/Square) would require
11-16 months of additional development, primarily for payment processing,
online ordering, mobile apps, and third-party integrations.
