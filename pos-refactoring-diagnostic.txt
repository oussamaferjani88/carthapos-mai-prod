4. ACCESSMODE / LOCALSTORAGE COUPLING
───────────────────────────────────────────────────────────────────────────────

  The AccessMode context is designed to work in both frontend and admin apps
  via shared localStorage keys:

  Key                  Used in frontend/          Used in admin/
  ─────────────────────────────────────────────────────────────────
  accessMode           AccessModeContext.tsx      AccessModeContext.jsx
                       api.ts                     api.js
  currentUserId        AccessModeContext.tsx      AccessModeContext.jsx
                       api.ts                     api.js
                       useClients.ts              useClients.js
                                                  usePOSGenerator.js
  currentUserName      AccessModeContext.tsx      AccessModeContext.jsx
  currentUserEmail     AccessModeContext.tsx      AccessModeContext.jsx

  File:      frontend/src/contexts/AccessModeContext.tsx
  What:      Parses URL params (mode, userId, userName, userEmail) from the
             admin's query string, stores them in localStorage.
  Why admin: The URL params come from the admin redirect (mode=user&userId=...).
             These same keys exist in admin/src/contexts/AccessModeContext.jsx
             with identical parsing logic.
  Mandatory: For the new native route — NO, because the user wouldn't come
             via admin redirect. However, the URLs used by the client portal
             (e.g., /pos-generator?mode=user&...) do include these params
             because the admin app generates them. If the client portal
             navigates to its OWN /pos-generator natively, it wouldn't need
             URL params — it could use the localStorage `user` object directly.

  File:      frontend/src/lib/api.ts:18-30
  What:      Axios interceptor reads localStorage('accessMode') and
             localStorage('currentUserId'), then adds X-User-Id and
             X-Access-Mode headers.
  Why admin: Designed to match admin/src/lib/api.js:69-79 which does the
             same thing — ensuring consistent behavior whether the API
             call comes from admin or client portal frontend.
  Mandatory: YES for user-mode filtering — the backend checks these headers
             (backend/routes/licenses.js:52, 426, 438).

5. API LAYER — SHARED HEADERS / CORS
───────────────────────────────────────────────────────────────────────────────

  The frontend API layer (api.ts) and admin API layer (api.js) are structurally
  identical — both inject the same custom headers and call the same endpoints.
  This is INTENTIONAL (by design) and not a bug.

  However, the CORS issue already fixed (X-Access-Mode, X-User-Id headers now
  allowed) means this coupling is now functional — not a blocker.

9. ANSWER TO THE CORE QUESTION
───────────────────────────────────────────────────────────────────────────────

  "If I stop the Admin application and leave only Backend + Frontend running,
   exactly what fails and why?"

  WHAT FAILS:
  The POS Generator feature is completely inaccessible to the end user.

  WHY:
  The user enters the POS Generator through the sidebar link "Générateur" at
  DashboardLayout.tsx:44 which navigates to /dashboard/generator. This renders
  Generator.tsx which:
    a) Tries to fetch http://localhost:5173 (admin dev server) as a health check
       → fetch fails → sets iframeError = true
    b) Shows an error screen saying "POS Generator not available"
       with a button to "Open admin section" (Generator.tsx:156-164)
    c) The iframe never renders because the admin is down

  WHAT DOES NOT FAIL (but is also not useful):
  The new native route /pos-generator (POSGeneratorPage.tsx) exists and loads
  correctly when accessed directly via the URL bar. It would work because it
  makes API calls directly to the backend (localhost:3001) — not through the
  admin. But there is no navigation link or button that leads users to this
  route, so it is effectively invisible.

  WHAT ABOUT THE CORS ERRORS SEEN EARLIER:
  Those were caused by the X-Access-Mode header not being in the backend's
  allowedHeaders list. This was already fixed (backend/server.js:53 and
  backend/src/config/index.js:22 were updated). These errors would also occur
  on the native route without the fix, but after the fix they should work.
