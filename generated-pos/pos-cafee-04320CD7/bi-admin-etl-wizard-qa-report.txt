2. CONFIRMED BUGS
-----------------

CRITICAL 1 — Schema-version metadata key mismatch (breaks EVERY real export)
  POS v2 export writes metadata key "schema_version": "2.2.0"
  (ipc-bi-export-handler.cjs), but etl-pipeline.js::_readMetadata reads the
  legacy key "bi_schema_version". Every real v2.2.0 ZIP therefore fails at
  extractAndValidate:
      BI Schema version mismatch: export v0.0.0 ≠ server v2.2.0
  Reproduced with a real export ZIP through both the direct pipeline call
  and POST /api/bi-uploads/:id/validate (500).
  FIX: read "schema_version" as well, or write "bi_schema_version" in export.

CRITICAL 2 — Dashboard generation is unreachable through the wizard
  confirm-load leaves the upload in status LOAD_CONFIRMED. Both dashboard
  entry points require COMPLETED (or a completed BiAnalysisRequest):
      POST /bi/dashboards/generate-from-upload → 400
        "Upload status is LOAD_CONFIRMED. Only COMPLETED uploads..."
      POST /bi/dashboards (manual) → 400
        "Dashboard creation requires a completed BI analysis or a COMPLETED upload."
  The wizard never creates a BiAnalysisRequest, and nothing in the load path
  sets COMPLETED → Step 8 is a dead end.
  FIX: set COMPLETED at the end of confirm-load, or accept LOAD_CONFIRMED.

CRITICAL 3 — bi_dashboard_templates table is missing from the live database
  schema.prisma declares model BiDashboardTemplate (line 357), but the
  migration was never applied: pg_tables shows bi_uploads, bi_dashboards,
  bi_requests, bi_analysis_requests, bi_processing_logs/jobs, bi_upload_files,
  bi_notifications — NO bi_dashboard_templates.
  Even if the status guards of bug #2 pass, both dashboard routes 500:
      prisma.biDashboardTemplate.findUnique/findMany
      → "The table `(not available)` does not exist in the current database."
  Affects POST /bi/dashboards/generate-from-upload, POST /bi/dashboards,
  and ALL /api/bi/dashboard-templates routes (CRUD).
  FIX: apply the missing migration (prisma migrate deploy).

CRITICAL 4 — Frontend wizard steps don't match the backend contracts
  (Step2, Step3, Step5, Step6, Step7, Step8)
    - Step2Validation.jsx:50  reads report?.datasets[] with d.valid →
      backend returns {validation:{<dataset>:{status,rows,...}}}; the step
      shows 0/0 and cannot advance.
    - Step3RawPreview.jsx:45 / Step5TransformationPreview.jsx:45  read
      data?.datasets[] as an array (tabs map over d.name) → backend returns
      a keyed object → crash/empty.
    - Step6Corrections.jsx:40  posts {corrections:[{dataset,field,oldValue,
      newValue,reason}]} → backend /:id/correct requires {section, table,
      rowIndex, changes} → 400 "section, table, rowIndex, and changes are
      required"; the dataset dropdown is also fed by preview?.datasets[]
      (array) which the API never returns.
    - Step7LoadConfirm.jsx:74  checks result?.datasetsLoaded (never set;
      backend returns recordsLoaded) → success text never shown (cosmetic).
    - Step8Dashboard.jsx:19  reads upload?.dashboards from GET /bi-uploads
      → field absent → empty list.
  Net effect: a user cannot complete the wizard UI beyond Step 2, even
  though every backend endpoint works.

MAJOR 5 — Reload duplicates rows instead of replacing
  Step 7 promises the import "remplace les données existantes", but
  loadIntoWarehouse does INSERTs without delete/upsert keyed to the export.
  A second identical load grew fact_sales 2500 → 5000. Observed accumulation
  across QA runs: fact_sales 10025 → 12525, fact_kitchen_orders 1608 → 2010,
  fact_inventory 86 → 105.

MAJOR 6 — Cross-tenant dimProduct corruption
  The dim_products upsert has no tenant/sector scope. Products with codes
  matching another tenant's rows are UPDATEd in place while keeping the
  original tenantId/exportId. Result: client "Le Gourmet"
  (cmoogzf95000xt2l5hk9yax74) has 17 dim_products instead of 19, and the
  "test" tenant (cmpb0pfd...) carries Le Gourmet's product data in its rows.
  Verified directly in PostgreSQL: dim_products grouped by tenantId =
  {cmoogzf…: 17, unknown-client: 7, cmpb0pfd…: 2}.

MAJOR 7 — Scale failure on 8000-sale load
  confirm-load of a stress export (8000 sales) → 500
      "Transaction API error: Transaction already closed… timeout for this
       transaction was 5000 ms… Consider increasing the interactive
       transaction timeout"  (etl-pipeline.js ≈ line 501)
  Upload remains stuck in PREPARED. The default Prisma interactive
  transaction timeout is insufficient for production volumes.

MINOR 8 — Non-zip file upload → 500 instead of 400
  Uploading a .txt file returns HTTP 500 {"error":"Something went wrong!"}
  because the multer fileFilter error isn't mapped to a 4xx.


3. SUMMARY
----------

                      scale (upload → validate → preview → prepare →
                      corrections → load → report), with correct DB isolation.
  Blocking issues:    bugs 1–4 must be fixed before the wizard is usable in
                      production (real exports fail validation; UI cannot
                      advance; dashboards unreachable and 500).
  Data-integrity:     bugs 5–6 (row duplication, cross-tenant corruption)
                      must be fixed before any production load.
  Scale/UX:           bugs 7–8.

  QA verdict: FAIL — the wizard is NOT production-ready.
  The warehouse DB also holds accumulated test data (fact_sales ~12.5k)
  from QA runs and should be reset before further testing.
