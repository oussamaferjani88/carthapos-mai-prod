                    6. PROBLÈMES TROUVÉS
═══════════════════════════════════════════════════════════════════════════════

── CRITIQUES (5) ─────────────────────────────────────────────────────────────

#U1  [CRITIQUE] Désalignement des rôles DB ↔ UI
     DB CHECK : admin, cashier, manager
     UI UserManagement : + viewer
     UI SecuritySettings : administrator, readonly (valeurs inexistantes)
     → Sélectionner 'viewer' ou 'administrator' = échec DB ou violation CHECK

#U2  [CRITIQUE] Handler change-password appelle méthode inexistante
     ipc-auth-handlers.cjs:83,234 — authManager.changePassword()
     ElectronAuthManager.cjs n'a PAS de méthode changePassword()
     → Ce handler PLANTERA à l'exécution

#U3  [CRITIQUE] SecuritySettings.jsx est entièrement factice
     Aucun appel IPC, aucune interaction backend
     → Fausse impression de contrôle pour l'utilisateur
     → Les changements de mot de passe ne sont JAMAIS appliqués

#U4  [CRITIQUE] Aucune protection brute-force
     authenticateUser n'a ni rate limiting, ni compteur d'échecs, ni lockout
     SecuritySettings définit loginAttempts:3 et lockoutDuration:15
     → MAIS ces valeurs ne sont JAMAIS appliquées nulle part

#U5  [CRITIQUE] Aucune authentification/autorisation sur les IPC handlers
     delete-user, update-user, add-user — tout renderer peut les appeler
     createdBy est hardcodé à 1 (pas la session réelle)
     → Un attaquant avec accès renderer peut créer/supprimer des users

── MOYENS (11) ──────────────────────────────────────────────────────────────

#U6  [MOYEN] Double logging d'audit crée des doublons
     Frontend activityLog.js écrit dans audit_logs via electronAPI.execute()
     Backend ElectronAuthManager.logAuditEvent() écrit aussi
     → Chaque création/modification/suppression est loggée DEUX fois

#U7  [MOYEN] Incohérence get-users handler
     Version classe (line 136) : NE sélectionne PAS phone/is_server
     Version fonction (line 257) : sélectionne phone/is_server
     → Selon la version appelée, données incomplètes

#U8  [MOYEN] Collision d'IDs en preview mode
     UserManagementAdvanced.jsx:271 — ID = users.length + 1
     Si des users ont été supprimés, collision possible

#U9  [MOYEN] Pas de confirmation avant suppression utilisateur
     handleDeleteUser appelle directement l'API sans confirm()
     → Contrairement à la suppression des logs qui utilise confirm()

#U10 [MOYEN] Admin peut être désactivé mais pas supprimé
     Le bouton delete est masqué pour admin, mais toggleUserStatus ne vérifie pas
     → Un admin peut désactiver TOUS les comptes admin = lockout système

#U11 [MOYEN] alert()/confirm() utilisés partout
     7 occurrences dans UserManagementAdvanced.jsx
     → UI bloquante, pas stylable, UX pauvre

#U12 [MOYEN] Session non validée en cours de session
     Validée une fois au démarrage (AuthContext.jsx:39)
     → Si user supprimé/désactivé pendant session = accès maintenu jusqu'au restart

#U13 [MOYEN] Potentiel fuite mémoire
     loadUsersFromDB, loadLogs, cleanupOldLogs sont async dans useEffect
     → Pas d'abort/cleanup si le composant se démonte avant completion

#U14 [MOYEN] full_name pas éditable
     Toujours assigné à username (line 240)
     → Pas de champ dédié pour le nom complet

#U15 [MOYEN] double enregistrement IPC handlers
     Classe (line 32-160) et fonction (line 165-408) enregistrent les mêmes canaux
     → Si les deux sont appelés, conflit ipcMain.handle

#U16 [MOYEN] is_server potentiellement perdu lors de l'édition
     handleSaveEdit envoie les données selectedUser mais
     le mapping backend peut ne pas inclure is_server correctement

── BAS (9) ──────────────────────────────────────────────────────────────────

#U17 [BAS] "En ligne" hardcodé à 2
     UserManagementAdvanced.jsx:491 — pas de vrai suivi de statut en ligne

#U18 [BAS] Méthode change-password absente du preload
     Le handler IPC existe mais le preload ne l'expose pas
     → Aucun frontend ne peut l'appeler

#U19 [BAS] Rôles SecuritySettings jamais fonctionnels
     'administrator' et 'readonly' ne matchent pas le CHECK constraint DB

#U20 [BAS] Pas d'unicité email sur soft-deleted users
     email UNIQUE bloque les nouvelles inscriptions même après suppression logique
     → Le path de réactivation ne met pas à jour l'email

#U21 [BAS] badge_id et pin jamais montrés dans l'UI
     Ces colonnes existent en DB mais sont invisibles dans le frontend

#U22 [BAS] Cleanup logs à 48h trop agressif
     Les logs sont définitivement supprimés après 48h sans archivage

#U23 [BAS] availableModules par défaut = tous les modules
     Si config est null, les 14 modules sont affichés (même non licenciés)

#U24 [BAS] Aucun index sur users.role et users.is_active
     Requêtes filtrant par rôle ou statut ne profitent pas d'index

#U25 [BAS] Les permissions modules sont simplifiées
     Toggle on/off met can_read/can_create/can_update/can_delete à la même valeur
     → Pas de granularité CRUD réelle
