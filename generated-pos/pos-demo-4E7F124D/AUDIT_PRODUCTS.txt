BUG #1: getSettings() — WRONG IPC METHOD NAME [SEVERITY: HIGH]
  File:     Products.jsx:347
  Code:     if (window.electronAPI?.getSettings) {
              const settings = await window.electronAPI.getSettings();
  Problem:  preload.cjs exposes `getAllSettings` and `getSetting(key)` but NOT
            `getSettings`. The method `window.electronAPI.getSettings` is always
            `undefined`.
  Effect:   `loadTaxSettings()` silently fails. `taxEnabled` stays at its
            default `true` — the VAT fields in ProductFormDialog always show,
            even if the user disabled tax in Settings. If the user has NO VAT
            rates configured but tax is disabled, the form still shows the
            empty VAT dropdown.
  Fix:      Change to `window.electronAPI.getAllSettings()` and extract
            `settings.taxEnabled` from the result, OR add `getSettings` to
            preload.cjs.

BUG #2: formatPrice() — NO NULL SAFETY [SEVERITY: HIGH]
  File:     Products.jsx:61-66
  Code:     const formatPrice = (price) => {
              if (config.currencyPosition === 'before') {
                return `${config.currency}${price.toFixed(2)}`;
              }
              return `${price.toFixed(2)} ${config.currency}`;
            };
  Problem:  `price.toFixed(2)` crashes if `price` is `undefined`, `null`, or
            `NaN`. Product cards call `formatPrice(product.price)` on line 759.
            If any product in the DB has a NULL price (edge case, but possible
            via direct SQL edit), the entire products page crashes with
            "Cannot read property 'toFixed' of undefined".
  Effect:   White screen of death if any product has null/undefined price.
  Fix:      `const val = parseFloat(price) || 0;` before calling `.toFixed(2)`.

BUG #3: getStockBadge() — WRONG DEFAULT min_stock [SEVERITY: MEDIUM]
  File:     Products.jsx:589
  Code:     const getStockBadge = (stock, minStock = 10) => {
  Problem:  Default `minStock` is `10`, but the DB schema default for
            `min_stock` is `0`. If a product has `min_stock = 0` (never set),
            the function receives `0` which is falsy, and the default `10`
            kicks in via the default parameter. Actually, `0` is falsy BUT
            `min_stock` is a number, so `= 10` only triggers if `undefined`.
            However, on line 760: `getStockBadge(product.stock, product.min_stock)`
            — if `product.min_stock` is `null` from DB, it passes `null` which
            IS falsy, and the default `10` triggers, showing false "Stock faible"
            badges for products that should be fine.
  Effect:   False "Stock faible" alerts for products with null min_stock.
  Fix:      `const minStockVal = minStock ?? 10;` or handle null explicitly.

DATA #1: DUPLICATE `family` AND `category` COLUMNS [SEVERITY: MEDIUM]
  File:     ElectronDatabaseManager.cjs:709-710, ipc-database-handlers.cjs:124
  Schema:   products has BOTH `category TEXT` and `family TEXT`
  Handler:  INSERT sets `category || family` and `family` — so category = family
  Problem:  Two columns serve the same purpose. The `category` table exists in
            the DB (line 723-730) but is never used by the UI. The Products page
            only shows "families". This dual-column design is confusing.
  Effect:   `category` always equals `family`. Wasted column. If someone edits
            `category` directly in DB, the UI filter won't work correctly
            (filter checks `product.family === selectedFamily || product.category ===
            selectedFamily` on line 385).
  Fix:      Deprecate `category` column, use only `family`. Or merge them.

DATA #2: IMAGES STORED AS BASE64 IN SQLITE [SEVERITY: MEDIUM]
  File:     ProductFormDialog.jsx:186-188, ElectronDatabaseManager.cjs:713
  Schema:   `image TEXT` — stores base64-encoded image data
  Problem:  Base64 images are ~33% larger than binary. A 5MB image becomes
            ~6.7MB of text in SQLite. Over time, with many product images,
            the database file can grow to hundreds of MB, slowing ALL queries.
  Effect:   Performance degradation as product count + images grow. Backup/
            restore becomes slow. SQLite has a practical limit of ~1GB for
            efficient operation.
  Fix:      Store images as files on disk, keep only the file path in DB.

DATA #3: OPTIMISTIC UPDATE WITH FAKE ID [SEVERITY: LOW]
  File:     Products.jsx:433-434
  Code:     const newProduct = { id: Date.now(), ...productData, created_at: new Date().toISOString() };
  Problem:  `Date.now()` as temp ID. If two products are created within the
            same millisecond (unlikely but possible in fast batch entry),
            they'd share the same ID. The reconciliation on lines 460-464
            fixes the ID after DB save, but the temporary duplicate could
            cause a brief React key collision.
  Effect:   Minor React rendering glitch in edge cases.
  Fix:      Use `crypto.randomUUID()` or a counter.

DATA #4: CREATED_AT FORMAT MISMATCH [SEVERITY: LOW]
  File:     Products.jsx:436 vs ElectronDatabaseManager.cjs:718
  Optimistic: `created_at: new Date().toISOString()` → "2026-07-18T14:30:00.000Z"
  DB Default: `DATETIME DEFAULT CURRENT_TIMESTAMP` → "2026-07-18 14:30:00"
  Problem:  The optimistic product has ISO format, but the DB-reloaded version
            has SQLite format. After `loadProducts()` on line 474, the timestamp
            format changes, which could cause display glitches if timestamps
            are shown to the user.
  Effect:   Inconsistent timestamp format for ~1 second until DB reload.
  Fix:      Use the same format as DB in optimistic update.

DATA #5: NO FOREIGN KEY CASCADE FOR SALE_ITEMS [SEVERITY: MEDIUM]
  File:     ElectronDatabaseManager.cjs:188 (delete-product handler)
  Problem:  `DELETE FROM products WHERE id = ?` — but `sale_items` has
            `product_id` referencing `products(id)`. If a product has been
            sold, deleting it orphans the sale_items rows. SQLite doesn't
            enforce foreign keys by default (PRAGMA foreign_keys must be ON).
  Effect:   Orphaned sale_items. Reports that join sale_items with products
            will silently miss these items. Historical sales data is
            partially lost.
  Fix:      Either: (a) Block deletion if product has sale_items, or
            (b) Set PRAGMA foreign_keys=ON and use ON DELETE SET NULL,
            or (c) Soft-delete products instead of hard delete.

DATA #6: BARCODE COLLISION RISK [SEVERITY: LOW]
  File:     Products.jsx:99-108 (generateLocalBarcode)
  Problem:  Generates random 13-digit EAN-13 codes. With ~1 trillion possible
            codes and a small product catalog, collision probability is low.
            But: (a) DB has UNIQUE constraint, so collision causes a silent
            error, (b) no UI-level validation before sending to DB.
  Effect:   If collision occurs, `add-product` handler rejects with a SQLite
            UNIQUE constraint error. The optimistic update already added the
            product with the duplicate barcode, but the error rollback on
            line 467 removes it. User sees product appear then disappear.
  Fix:      Check barcode uniqueness before optimistic update, or retry
            with a new barcode on collision error.

SEC #1: NO INPUT SANITIZATION ON PRODUCT NAME [SEVERITY: LOW]
  File:     ProductFormDialog.jsx:167, ipc-database-handlers.cjs:117
  Problem:  Product name is passed directly to SQL via parameterized query

  Risk:     Low — React auto-escapes. But if product names are ever used in

            Any authenticated user (including cashiers) can add, edit, or

  Effect:   A cashier can delete all products, change prices, etc.
  Fix:      Add role check in each handler: `if (role !== 'admin' && role !== 'manager') throw new Error('Forbidden')`

SEC #3: NO RATE LIMITING ON PRODUCT CREATION [SEVERITY: LOW]
  Problem:  No limit on how many products can be created per minute. A
            malicious user (or buggy script) could flood the DB.
  Risk:     Low — Electron is local-only, no network exposure.

CURRENT PRODUCTS TABLE:
  CREATE TABLE products (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    price       DECIMAL(10,2) NOT NULL,
    cost_price  DECIMAL(10,2) DEFAULT 0,        -- Added by migration
    category    TEXT,                            -- DEPRECATED: always = family
    family      TEXT,
    description TEXT,
    barcode     TEXT UNIQUE,
    image       TEXT,                            -- Base64 encoded
    unit        TEXT DEFAULT 'unit',             -- Added by migration
    stock       INTEGER DEFAULT 0,
    min_stock   INTEGER DEFAULT 0,
    supplier    TEXT DEFAULT '',                 -- Added by migration
    vat_rate_id INTEGER DEFAULT NULL,            -- Added by migration
    price_type  TEXT DEFAULT 'ttc',              -- Added by migration
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP
  );

  Notes:
  - `category` is redundant with `family` — always set to same value
  - `image` stores base64 — should store file path instead
  - No `is_active` / soft-delete column — products are hard-deleted
  - No `sort_order` column for manual ordering
  - `barcode` UNIQUE constraint can cause silent failures on collision

PRODUCT_FAMILIES TABLE:
  CREATE TABLE product_families (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL UNIQUE,
    description TEXT,
    icon        TEXT,                            -- Added by migration
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
  );

  Notes:
  - Clean table, no issues
  - `description` is never shown in the UI
  - `icon` is stored but only shown in the family management dialog

CATEGORIES TABLE (UNUSED):
  CREATE TABLE categories (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL UNIQUE,
    description TEXT,
    color       TEXT DEFAULT '#3B82F6',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
  );

  Notes:
  - This table exists in the DB schema but is NEVER used by any UI
  - Completely dead schema. Should be removed or integrated.
