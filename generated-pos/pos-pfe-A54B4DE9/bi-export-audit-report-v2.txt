C. EXCLUSION JUSTIFICATIONS
----------------------------

  users:
    - User account data (roles, PIN status, login tracking) is NOT already
      covered by shifts.
    - However, user activity is comprehensively captured in audit_logs
      (LOGIN_SUCCESS, USER_CREATE/UPDATE/DELETE, PASSWORD_CHANGE).
    - Sales reference users via user_id with denormalized cashier_name.
    - Audit_logs records who did what; shifts records who managed the drawer.
    - Adding users would expose password hashes and PIN config — not suitable
      for BI export without careful field filtering.
    - DECISION: EXCLUDED. User identity is sufficiently denormalized into
      sales (cashier_name) and audit_logs (user_name). Direct user table
      export is a security risk for minimal analytical gain.

  held_orders:
    - Stores on-hold carts as JSON blobs (items TEXT field).
    - Data is EPHEMERAL — rows are DELETED immediately after restore.
    - The restore operation is a "move" (select + delete), not a copy.
    - At any given time, held_orders contains only in-flight holds with
      near-zero historical analytical value.
    - Completed held orders become sales (captured in sales + sale_items).
    - DECISION: EXCLUDED. Data lifecycle is too short for BI; useful
      information is already in sales/sale_items after conversion.

  user_sessions:
    - Tracks login/logout times and session duration per user.
    - Primarily operational (active session management).
    - Audit_logs already records LOGIN_SUCCESS and LOGOUT events with
      timestamps, covering the same analytical narrative.
    - DECISION: EXCLUDED. Duplicative with audit_logs tracking.

  user_modules:
    - Permission/role matrix per user per module.
    - Static RBAC configuration — not analytical data.
    - Changes are recorded in audit_logs (USER_UPDATE).
    - DECISION: EXCLUDED. Configuration data, not analytical.

  settings / security_settings:
    - Key-value pairs for app config (locale, business info, receipt design).
    - Security policy (lockout threshold, password rules).
    - Static configuration — extremely low analytical value.
    - Changes are recorded in audit_logs (SETTINGS_UPDATE, etc.).
    - DECISION: EXCLUDED. Configuration data, not analytical.

  printer_configs / department_printer_routes:
    - Printer hardware setup and routing rules.
    - Purely operational configuration — no analytical value.
    - DECISION: EXCLUDED. Operational config only.

  table_zones:
    - Restaurant table zone names, colors, sort order.
    - Denormalized zone name already available in tables.zone column.
    - DECISION: EXCLUDED. Sufficiently covered by tables dataset.

  recent_logins:
    - Simple log of user_id + login_at timestamps.
    - Audit_logs already captures LOGIN_SUCCESS with full detail.
    - DECISION: EXCLUDED. Duplicative with audit_logs.

D. X REPORT — FIX VERIFIED
----------------------------

  Root causes identified and fixed:

  1. No shift fallback logic:
     - Before: returned "No open shift found" when no shift was open.
     - After: falls back to the last closed shift (same pattern as Z Report).
     - File: ipc-reports-handlers.cjs, lines 506-511.

  2. Frontend-backend data contract mismatch:
     - Before: handler returned nested {data: {sales: {total, revenue},
       drawer: {cashSales, cardSales}}} but UI read flat totalSales,
       totalRevenue, cashTotal, cardTotal directly — all undefined -> 0.
     - After: handler returns flat fields matching UI expectations:
       totalSales, totalRevenue, cashTotal, cardTotal, byPaymentMethod[],
       byCashier[].
     - File: ipc-reports-handlers.cjs, lines 557-588; Reports.jsx lines 371-381.

  3. Missing cashier aggregation:
     - Before: UI rendered "by cashier" section but handler never fetched it.
     - After: handler queries sales grouped by user_id JOIN users.
     - File: ipc-reports-handlers.cjs, lines 547-553.

  4. Payment method field name:
     - Before: SQL used 'revenue' alias; UI expected 'total'.
     - After: SQL uses 'total' alias.
     - File: ipc-reports-handlers.cjs, line 529.

  5. UI error handling:
     - Before: no error state; xReportData.error displayed as totalSales=0.
     - After: error message shown in a dedicated UI state.
     - File: Reports.jsx, lines 1474-1478.

F. NEW DATASET JUSTIFICATIONS
-------------------------------

  audit_logs:
    - WHY: Full security and compliance audit trail. Every user action is
      recorded: logins, CRUD operations, shift opens/closes, settings changes,
      backups, password changes, user management.
    - SOURCE: audit_logs table, populated from 11 INSERT sites across 7 files
      (ElectronAuthManager, ipc-app-handlers, ipc-cash-register-handlers,
      ipc-customer-handlers, ipc-hardware-handlers, ipc-database-handlers,
      ipc-supplier-handlers).
    - 27 distinct action_type values, all populated during normal POS usage.
    - NOT duplicative: no existing dataset captures user activity timeline.
    - VALUE: Compliance, security auditing, user behavior analysis.

  vat_rates:
    - WHY: Completes the sales dimension model. Products reference
      vat_rate_id, and sale_items store the resolved vat_rate percentage.
      Without vat_rates in the export, the FK from products has no
      corresponding dimension table.
    - SOURCE: vat_rates table, queried on every page load and during sale
      transaction for tax calculation.
    - NOT duplicative: the numeric vat_rate on sale_items is the resolved
      value at time of sale; vat_rates provides the active rate definitions.
    - VALUE: Enables joining products.vat_rate_id for tax analysis.
