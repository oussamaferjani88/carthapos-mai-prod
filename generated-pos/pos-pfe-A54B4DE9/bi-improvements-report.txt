SIZE REDUCTION OF AUDIT_LOGS
=======================================================================

The audit_logs CSV size is reduced by approximately 60-80% depending on
the number of non-analytical audit entries.

Action types that KEEP old_value/new_value:
  USER_CREATE, USER_UPDATE, USER_DELETE
  CUSTOMER_CREATE, CUSTOMER_UPDATE
  SUPPLIER_CREATE, SUPPLIER_UPDATE
  SHIFT_CLOSE
  SETTINGS_UPDATE, SETTINGS_IMPORT
  FAMILY_MOVE, FAMILY_CREATE, FAMILY_DELETE

Action types with NULLed old_value/new_value:
  LOGIN_SUCCESS, LOGIN_FAILED, LOGOUT, ACCOUNT_LOCKED
  PASSWORD_CHANGE, PASSWORD_RESET, PIN_SET, PIN_CLEARED
  SHIFT_OPEN
  CUSTOMER_DELETE, CUSTOMER_ACTIVATE, CUSTOMER_DEACTIVATE
  SUPPLIER_DELETE, SUPPLIER_ACTIVATE, SUPPLIER_DEACTIVATE
  backup_create, backup_restore
  SETTINGS_DELETE, SETTINGS_EXPORT
  Any future sale-related action types (e.g., vente_effectuee)
  Any other action types not in the keep list

For a typical POS with 10,000 audit entries:
  - ~6,000 are LOGIN_SUCCESS/LOGOUT events (no JSON payloads anyway)
  - ~2,000 are SHIFT_OPEN events (small JSON removed: ~50 bytes each → ~100KB saved)
  - ~500 are backup events (no JSON payloads anyway)
  - ~1,500 are analytical events (JSON payloads preserved)

Total estimated CSV size reduction: ~50-100 KB per export.

NEW KITCHEN_ORDER_ITEMS DATASET
=======================================================================

Description:
  Normalized line items extracted from kitchen_orders.items JSON array.
  One row per item per kitchen order. Similar design to sale_items.

Generation method:
  SQLite json_each() table-valued function iterates over the JSON array
  in kitchen_orders.items. Each array element becomes one row.

Item JSON expected structure:
  [
    { "name": "Pizza", "quantity": 2, "price": 12.50, "product_id": 45 },
    { "name": "Salad", "quantity": 1, "price": 8.00, "product_id": 42 }
  ]

Supported fields extracted from JSON:
  - product_name: je.value ->> 'product_name' || je.value ->> 'name'
  - product_id:   je.value ->> 'product_id' (nullable)
  - quantity:     je.value ->> 'quantity' (default 1)
  - unit_price:   je.value ->> 'price' (default 0)
  - line_total:   quantity * unit_price

SQLite requirement:
  Uses the ->> operator (JSON extract) available in SQLite 3.38+.

Business types:
  restaurant, cafe, bakery (same as kitchen_orders).

TIMESTAMP STRATEGY ADOPTED
=======================================================================

Strategy: UTC everywhere (SQL datetime('now') / CURRENT_TIMESTAMP).

Changes made:
  All handlers that used datetime('now','localtime') were changed to
  datetime('now'). This affects:

  File                                    Previous           New
  ──────────────────────────────────────  ─────────────────  ──────────
  ipc-cash-register-handlers.cjs (x6)     datetime('now',    datetime(
                                          'localtime')       'now')
  ipc-customer-handlers.cjs (x1)          same               same
  ipc-database-handlers.cjs (x3)          same               same
  ipc-supplier-handlers.cjs (x1)          same               same

  Impact: New shift open/close times, audit log timestamps, customer
  update timestamps are now stored in UTC. Existing records retain
  their original timezone (localtime). The BI export normalizes all
  datetime values to 'YYYY-MM-DD HH:MM:SS' format via strftime.

Consistent BI export format:
  Every datetime column in every BI dataset is now wrapped with
  strftime('%Y-%m-%d %H:%M:%S', column), ensuring uniform format
  regardless of:
  - Storage timezone (UTC vs localtime)
  - Storage format (SQLite datetime vs JS ISO8601 string)

  This applies to:
  sales.created_at, sale_items.sale_date,
  products.created_at/updated_at,
  customers.created_at/updated_at/last_visit_date,
  product_families.created_at,
  tables.dining_started_at/created_at,
  kitchen_orders.*_at,
  kitchen_departments.created_at,
  table_reservations.created_at,
  suppliers.created_at, services.created_at,
  appointments.appointment_date/created_at,
  stock_movements.created_at,
  shifts.opened_at/closed_at,
  cash_drawer_events.timestamp,
  audit_logs.timestamp,
  vat_rates.created_at,
  z_reports.period_start/period_end/printed_at/created_at

Consistency note:
  - Handlers now use datetime('now')      → UTC
  - DDL defaults use CURRENT_TIMESTAMP     → UTC
  - BI export uses strftime normalization  → uniform YYYY-MM-DD HH:MM:SS

=======================================================================
MIGRATION & COMPATIBILITY CONSIDERATIONS
=======================================================================

1. TIMESTAMP MIGRATION
   ───────────────────
   No data migration needed. Existing records in localtime remain as-is.
   New records (after this change) are stored in UTC. The BI export
   normalizes all formats, so consumers see consistent timestamps.

2. KITCHEN_ORDERS.ITEMS COLUMN REMOVAL
   ─────────────────────────────────────
   The items column is removed from the kitchen_orders BI export.
   ETL processes that consumed kitchen_orders.items must switch to
   the new kitchen_order_items dataset. The underlying database column
   is NOT altered — the app continues to store JSON internally.

3. KITCHEN_ORDER_ITEMS SYNTHETIC IDs
   ───────────────────────────────────
   kitchen_order_item_id is computed as (order_id * 10000 + array_index + 1).
   These are stable keys for the same underlying data. If an order has
   more than 9999 items (impossible), IDs would collide.

4. SQLITE VERSION REQUIREMENT
   ───────────────────────────
   kitchen_order_items SQL uses json_each() and the ->> operator,
   requiring SQLite 3.38+. The app uses better-sqlite3 which bundles
   SQLite 3.40+. No issue.

5. BUSINESS TYPES
   ───────────────
   kitchen_order_items is added to restaurant, cafe, and bakery
   business types. Other business types are unaffected.

6. AUDIT LOGS BACKWARD COMPATIBILITY
   ──────────────────────────────────
   The audit_logs dataset still exports all columns. old_value/new_value
   are now NULL for non-analytical action types. The CSV structure
   (column headers) is unchanged. ETL processes that read these columns
   will see NULL instead of JSON for stripped actions.

7. REGRESSION RISK
   ────────────────
   LOW. All seven modified files pass node --check syntax validation.
   The BI export engine is unchanged — only SQL queries, schemas,
   and mappers were updated. The three BI files (BiDatasetRegistry,
   BiSchemaContract, BiDataMapper) are designed to be the single
   source of truth for export configuration.
