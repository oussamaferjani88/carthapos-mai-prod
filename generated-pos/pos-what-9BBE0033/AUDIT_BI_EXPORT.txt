2. EXPORT FLOW (Step by Step)
================================================================================

  1. User clicks "Export BI" button in Reports.jsx (line 1805)
  2. setShowBiExport(true) -> BiExportModal opens
  3. User clicks "Generer l'export" in modal
  4. handleExport() -> window.electronAPI.exportBiData()
  5. preload.cjs -> ipcRenderer.invoke('bi:export')
  6. IPCBiExportHandler.runExport(options) executes:
     a. _loadAppConfig() -> reads app-config.json from disk
     b. Extracts modules[], theme.sector or theme.businessType
     c. Filters enabledModules (isEnabled !== false)
     d. dbManager.getDatabase() -> SQLite handle
     e. _collectSales(db) -> SQL JOIN sales LEFT JOIN customers -> mapSalesRows()
     f. _collectProducts(db) -> SQL SELECT products -> mapProductRows()
     g. _collectCustomers(db) -> SQL SELECT customers -> mapCustomerRows()
     h. _collectInventory(db) -> SQL SELECT products + subquery times_sold -> mapInventoryRows()
     i. IF module includes 'tables' -> _collectTables(db) -> mapTableRows()
     j. IF module includes 'kitchen' -> _collectKitchenOrders(db) -> mapKitchenOrderRows()
     k. IF module includes 'suppliers' -> _collectSuppliers(db) -> mapSupplierRows()
     l. IF module includes 'services' OR 'appointments' -> _collectServices(db) + _collectAppointments(db)
  7. BiValidator.validateAll(datasets) -> checks all rows against schema
  8. For each dataset -> _biRowsToCsv(key, rows) using BiSchemaContract.getColumnNames()
  9. metadata.json appended to files array
  10. _createZip(files, outputPath) -> writes to ~/Documents/CarthaPOS/BI_Exports/bi_export_{timestamp}.zip
  11. Returns { success, filePath, fileName, fileSize, metadata, stats }
  12. BiExportModal shows success card with file info

3. BUSINESS TYPE AWARENESS — CRITICAL FINDING
================================================================================

HOW THE SYSTEM CURRENTLY DECIDES WHAT TO EXPORT:

  // ipc-bi-export-handler.cjs:51
  const businessType = theme.sector || theme.businessType || 'retail';

PROBLEM: businessType is EXTRACTED but NEVER USED.

The variable businessType is computed at line 51 but only stored into metadata at
line 102. It has ZERO influence on:
  - Which datasets are collected
  - Which SQL queries are executed
  - Which CSVs are generated
  - Any conditional logic anywhere

MODULE GATING uses only module name matching (line 69-78):

  if (enabledModules.some(m => m.includes('tables')))
    datasets.tables = await this._collectTables(db);
  if (enabledModules.some(m => m.includes('kitchen')))
    datasets.kitchen_orders = await this._collectKitchenOrders(db);
  if (enabledModules.some(m => m.includes('suppliers')))
    datasets.suppliers = await this._collectSuppliers(db);
  if (enabledModules.some(m => m.includes('services') || m.includes('appointments'))) {
    datasets.services = await this._collectServices(db);
    datasets.appointments = await this._collectAppointments(db);
  }

VERDICT:
  - Module-level gating EXISTS but is INCOMPLETE — uses .includes() substring matching
  - Business-type awareness DOES NOT EXIST — businessType is metadata-only
  - Core datasets (sales, products, customers, inventory) ALWAYS export
  - No concept of "this dataset is wrong for this business type" exists anywhere

5. MODULE AWARENESS AUDIT
================================================================================

CURRENT MODULE GATING LOGIC (ipc-bi-export-handler.cjs:49-78):

  const enabledModules = modules
    .filter(m => m.isEnabled !== false)
    .map(m => m.name || m);

  Gating:
    m.includes('tables')         -> tables
    m.includes('kitchen')        -> kitchen_orders
    m.includes('suppliers')      -> suppliers
    m.includes('services') || m.includes('appointments') -> services + appointments


ISSUES FOUND:

  #   ID   Severity  Description
  ─── ──── ───────── ─────────────────────────────────────────────────────────
  M1  ---  HIGH      Substring matching is fragile. m.includes('kitchen') would
                     match 'kitchen-printer' AND any future module containing
                     'kitchen'. Same for 'tables' matching 'table-management'.
  M2  ---  MEDIUM    Missing module: loyalty-program. If loyalty is disabled,
                     customers.csv could/should exclude loyalty fields.
  M3  ---  LOW       Missing module: pos-core. Always enabled, never checked.
  M4  ---  LOW       Missing module: reports. If reports module is disabled,
                     the BI export should be blocked entirely.
  M5  ---  MEDIUM    services + appointments gated together. A salon has services
                     WITHOUT appointments. A clinic has appointments WITHOUT
                     services. Both are always exported together.
  M6  ---  LOW       No gift-cards module exists.


app-config.json Module Names vs Export Matching:

8. DATA MAPPING AUDIT
================================================================================

ARCHITECTURE: Two mapper patterns exist.

  Pattern A — Generic mapRow() (BiDataMapper.cjs:18-27):
    function mapRow(datasetKey, rawRow) {
      row[col.name] = rawRow[col.name] ?? rawRow[col.name.replace(/^[a-z]+_/, '')] ?? null;
    }
    This generic mapper strips prefix (e.g., sale_id -> tries rawRow['id']).
    Works as fallback but is NEVER ACTUALLY USED by the export handler.

  Pattern B — Specific mappers (e.g., mapSaleRow):
    Each dataset has its own mapper. Manually written and correct.

9. VALIDATION AUDIT
================================================================================

BiValidator LOGIC:

  validateDataset(key, rows, label):
    1. Check schema exists -> error if unknown
    2. Check if rows empty -> warning (not error)
    3. Check first 100 rows:
       a. All expected columns present -> error per missing column
       b. Required fields non-null -> warning per null required value
       c. Type hints (integer, real) -> warning per mismatch
    4. Check extra columns in first row -> warning


VALIDATION ISSUES:

  #   ID   Severity  Description
  ─── ──── ───────── ─────────────────────────────────────────────────────────
  V1  ---  MEDIUM    Empty dataset = warning, not error. Exporting an empty
                     sales.csv is allowed. A POS with zero sales generates a
                     valid export with 0-row CSVs for everything.
  V2  ---  LOW       Only checks first 100 rows. If row 101 has a missing
                     required field, it's silently missed.
  V3  ---  LOW       Type checking is basic. Number.isInteger(Number(val)) for
                     integer type — but Number('') is 0 which passes.
                     Empty string in integer column passes validation.
  V4  ---  MEDIUM    No cross-dataset validation. No check that
                     sale_items.product_id references an existing products.id.
  V5  ---  LOW       No date format validation. datetime type columns are not
                     validated. Any string passes.
  V6  ---  OK        Errors block export, warnings don't. Good design.
  V7  ---  LOW       Empty required string. name is required for products but
                     mapper defaults to '' (empty string). '' is not null so
                     it passes validation. Technically valid but wrong.

11. SCALABILITY ASSESSMENT
================================================================================

CURRENT ARCHITECTURE STRENGTHS:

  1. Clean separation — Schema, Mapper, Validator, Handler are separate files
  2. Schema contract — BiSchemaContract is the single source of truth
  3. CSV generation is schema-driven — Uses getColumnNames() for header + row
  4. Module gating exists — Even if incomplete, the pattern is there


CURRENT ARCHITECTURE WEAKNESSES:

  #   ID   Severity  Description
  ─── ──── ───────── ─────────────────────────────────────────────────────────
  SC1 ---  MEDIUM    Adding a new dataset requires changes in 4+ files:
                     BiSchemaContract (schema), BiDataMapper (mapper),
                     BiValidator (labels), handler (collector + SQL + gating).
                     Not DRY.
  SC2 ---  HIGH      No dataset registry pattern. No central registry that says
                     "this dataset exists, belongs to this module, requires this
                     SQL, uses this mapper." Each dataset is ad-hoc wired.
  SC3 ---  HIGH      Module gating uses substring matching. m.includes('kitchen')
                     is fragile. Should use exact module name matching or a
                     datasets config.
  SC4 ---  MEDIUM    No dynamic dataset discovery. If someone adds a schema to
                     BiSchemaContract, they also need to write a collector, SQL,
                     mapper, and gating logic. Nothing auto-discovers.
  SC5 ---  OK        CSV generation tied to schema contract. Adding a column to
                     schema auto-includes it in CSV output.
  SC6 ---  LOW       ZIP is hand-rolled (300+ lines of buffer manipulation).
                     Works but fragile.
  SC7 ---  MEDIUM    All queries are sequential, not parallelized. Could be
                     3-5x faster with Promise.all().
