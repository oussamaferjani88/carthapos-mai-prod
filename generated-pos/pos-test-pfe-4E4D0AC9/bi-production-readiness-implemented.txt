R1: FIX TIMEZONE COMPARISON IN BACKFILL (REQUIRED)
=======================================================================

File: src/electron/ElectronDatabaseManager.cjs:1907-1908, 1915-1916

Change: Replaced datetime string comparison with unix timestamp comparison
        using strftime('%s', ...).

Before:
    AND shifts.opened_at <= sales.created_at
    AND (shifts.closed_at IS NULL OR shifts.closed_at >= sales.created_at)

After:
    AND strftime('%s', shifts.opened_at) <= strftime('%s', sales.created_at)
    AND (shifts.closed_at IS NULL OR strftime('%s', shifts.closed_at) >= strftime('%s', sales.created_at))

Rationale:
  shifts.opened_at is stored in local time (datetime('now','localtime'))
  sales.created_at is stored in UTC (DEFAULT CURRENT_TIMESTAMP)
  Lexicographic comparison of 'HH:MM:SS' strings fails when UTC offset > 0:
    local '09:00' vs UTC '08:00' → '0' > '0' by hour → false negative
  strftime('%s') converts both to unix epoch (integer), which is
  timezone-independent.

Safety:
  ✓ Idempotent — same semantics, different comparison method
  ✓ No false positives — the old code was too strict (only misses), never
    too loose. The fix keeps it correct.
  ✓ Backward compatible — only changes comparison mechanism

=======================================================================

File: src/electron/handlers/ipc-cash-register-handlers.cjs:98-103

Change: Added this.changes === 0 check after UPDATE in caisse:close-shift.

Before:
    function(err) {
      if (err) { reject(err); } else {
        try {
          // audit log, cash drawer...
          resolve({ success: true, difference: diff });

After:
    function(err) {
      if (err) { reject(err); return; }
      if (this.changes === 0) {
        resolve({ success: false, warning: 'Shift is already closed', difference: 0 });
        return;
      }
      try {
        // audit log, cash drawer...
        resolve({ success: true, difference: diff });

Behavior:
  - If the shift was already auto-closed (or manually closed earlier),
    the handler returns { success: false, warning: 'Shift is already
    closed', difference: 0 } instead of silently succeeding.
  - Backward compatible: existing callers that check 'success' will see
    false and can handle it; those that ignore the response continue
    working.
  - No audit_log or cash_drawer_entry is created for a no-op close.

R3: COMPUTE PAYMENT TOTALS FROM SALES TABLE
=======================================================================

File: src/electron/handlers/ipc-reports-handlers.cjs

3A. Z Report (lines 705-737)

Change: Compute cash_sales/card_sales/other_sales from the sales table
        instead of reading shift.cash_sales/shift.card_sales/shift.other_sales.

Added computation (after paymentMethods query):
    const cashPaymentMethods = ['cash', 'espèces', 'especes'];
    const cardPaymentMethods = ['card', 'carte'];
    let computedCashSales = 0;
    let computedCardSales = 0;
    let computedOtherSales = 0;
    for (const pm of paymentMethods) {
      const method = (pm.payment_method || '').toLowerCase().trim();
      if (cashPaymentMethods.includes(method)) {
        computedCashSales += pm.revenue;
      } else if (cardPaymentMethods.includes(method)) {
        computedCardSales += pm.revenue;
      } else {
        computedOtherSales += pm.revenue;
      }
    }

Updated zReport object:
    cash_sales: shift.cash_sales || 0   →   cash_sales: computedCashSales
    card_sales: shift.card_sales || 0   →   card_sales: computedCardSales
    other_sales: shift.other_sales || 0 →   other_sales: computedOtherSales

Updated closingExpected:
    - (shift.card_sales || 0) - (shift.other_sales || 0)
    → - computedCardSales - computedOtherSales

3B. X Report (lines 585-624)

Change: Same pattern applied to X Report for consistency.

Added computation (uses pm.total — X Report field name is 'total'):
    let xCashSales = 0, xCardSales = 0, xOtherSales = 0;
    for (const pm of paymentMethods) {

Rationale:

  close time (or 0 for auto-closed shifts). The sales table always has

Safety:
  ✓ More accurate — uses actual sale records, not user estimates
  ✓ No regression — sales table always has the definitive payment data
  ✓ closingExpected remains correct: opening_float + total_revenue - computed_card - computed_other
    = opening_float + computed_cash (the cash that should be in the drawer)

R4: ADD AUDIT_LOG ENTRY FOR AUTO-CLOSE
=======================================================================

File: src/electron/handlers/ipc-cash-register-handlers.cjs:38-53

Change: When auto-close fires (this.changes > 0 in caisse:open-shift),
        look up the closed shift and insert a SHIFT_CLOSE audit log entry.

Added code:
    db.get(
      `SELECT id, user_name FROM shifts
       WHERE user_id = ? AND status = 'closed'
       ORDER BY closed_at DESC LIMIT 1`,
      [data.user_id],
      (aErr, closedShift) => {
        if (!aErr && closedShift) {
          try {
            db.run(
              `INSERT INTO audit_logs (timestamp, user_id, user_name, action_type, entity_type, entity_id, notes)
               VALUES (datetime('now','localtime'), ?, ?, 'SHIFT_CLOSE', 'shift', ?, ?)`,
              [data.user_id, closedShift.user_name || '', closedShift.id,
               `Caisse automatiquement fermée pour l'ouverture d'une nouvelle caisse`]
            );
          } catch (e) { /* non-critical */ }
        }
      }
    );

Behavior:
  - Only fires when this.changes > 0 (actual auto-close occurred)
  - Fire-and-forget: does not block new shift creation
  - Gracefully handles missing shift data (no crash if SELECT returns
    nothing)
  - Report-safe: previously, only SHIFT_OPEN was logged for the new
    shift; now SHIFT_CLOSE for the old shift provides full traceability

REMAINING RISKS
=======================================================================

1. LOW — Multi-shift auto-close audit
   If a user somehow has multiple open shifts (legacy), the auto-close
   closes all of them, but the audit_log entry only records the most
   recently closed one. Acceptable for an edge case that should not
   exist in practice.

2. LOW — Z Report for auto-closed shift
   If a user explicitly generates a Z Report for an auto-closed shift
   (by selecting shift_id), the shift status update within the
   transaction (line 769) will affect 0 rows. The z_reports row is
   still inserted with correct computed values from sales table.
   The UPDATE is a no-op — no data corruption.

3. INFORMATIONAL — closingExpected semantic shift
   closingExpected now uses sales-computed card/other totals instead of
   user-provided shift.card_sales. This is strictly more accurate. The
   closingExpected formula is now:
     opening_float + total_revenue - computed_card_sales - computed_other_sales
   which equals opening_float + computed_cash_sales.
